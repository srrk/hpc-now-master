deliberate misconfigurations

Pre-applied · Discover through measurement — not instruction

Both misconfigurations are applied before the lab starts. You are not told what they are. You discover them by running the diagnostic commands. This is the point.

Misconfiguration 1 THP set to [always] on all compute nodes. Transparent Huge Pages compaction causes pauses up to 4,200 μs during memory operations — stalling MPI ranks mid-computation. Discover with: cat /sys/kernel/mm/transparent_hugepage/enabled
Misconfiguration 2 MPI job submitted without --cpu-bind. Ranks migrate freely across both NUMA nodes (CPUs 0–71). Remote memory accesses cost 2.1× more than local. Discover with: taskset -cp <PID> — shows affinity list 0-71

01 Admin Baseline
15 minutes Checklist item 37

Confirm the cluster is healthy at the scheduler level. Read the NUMA topology before any job runs. Document the THP misconfiguration as the before state.

Cluster state check

head node
# Confirm all nodes are available
sinfo -N
squeue   # should be empty at lab start

Read NUMA topology — SSH to compute node first

compute node
ssh compute-dy-c5-18xl-1

# Read the hardware NUMA topology
numactl --hardware

Expected numactl output — two NUMA nodes

available: 2 nodes (0-1)
node 0 cpus: 0 1 2 ... 17 36 37 ... 53
node 0 size: 72000 MB
node 1 cpus: 18 19 20 ... 35 54 55 ... 71
node 1 size: 72000 MB
node distances:
node   0   1
  0: 10  21
  1:  21 10

Distance 10 = local (1×). Distance 21 = remote (2.1×). An unbound rank allocating memory on the wrong NUMA node pays this 2.1× penalty on every memory access.

Check and record THP state — from head node

head node
exit   # back to head node

# Check THP on all compute nodes simultaneously
pdsh -w compute-[0-1] "cat /sys/kernel/mm/transparent_hugepage/enabled"

# Record in report
echo "=== THP STATE BEFORE ===" >> ~/lab_m3_report.txt
pdsh -w compute-[0-1] "cat /sys/kernel/mm/transparent_hugepage/enabled" >> ~/lab_m3_report.txt

Expected THP output — misconfiguration confirmed

compute-dy-c5-18xl-1: [always] madvise never
compute-dy-c5-18xl-2: [always] madvise never

Both nodes show [always]. This is the before state. The fix comes in Task 3.

task 2 of 6

02 Profile the Unbound Job
20 minutes Checklist items 13, 14, 16

Submit the unbound MPI job. Profile it with perf stat, numastat, and taskset. Understand what each tool shows and why the numbers are bad.

Submit job and find your PIDs

head node
# Submit the unbound job (runs 15 minutes)
sbatch /home/scripts/mem_stress_unbound.sh

# Watch until ST=R — Ctrl+C to exit
watch -n 5 squeue

# Note your JOBID and compute node
squeue -u $USER -o "%i %N %t"

# SSH to your compute node
ssh compute-dy-c5-18xl-1

# Find YOUR job's PIDs — not other learners' jobs
scontrol listpids <YOUR_JOBID>

# Get mem_stress rank PIDs specifically
ps aux | grep mem_stress | grep -v grep

Wait 2 minutes after job starts before profiling

THP compaction and NUMA memory pressure take time to build up. Profiling in the first 30 seconds will not show the full effect. Wait until you see the job printing output lines before attaching perf stat.

Step A — Raw perf stat · read the output · understand what you are seeing

compute node · attach to mem_stress rank PID
sudo perf stat -e instructions,cycles -p <MEM_STRESS_PID> sleep 30

Expected output — memory stalled

Performance counter stats for process id '<PID>':

  12,356,141,706   instructions   #   0.12   insn per cycle
101,196,841,174   cycles

      30.001 seconds time elapsed

IPC ≈ 0.12 means the CPU is severely stalled — issuing instructions faster than memory can feed it. The random access pattern across a 4GB working set defeats the hardware prefetcher entirely. Every access goes to DRAM.

IPC · unbound + THP on 0.12 memory-stalled · DRAM bound · expected range 0.08 – 0.20

task 3 of 6

03 Remediate THP Cluster-Wide
10 minutes Checklist item 15

Fix THP on all compute nodes with a single pdsh command. One command. Both nodes. Simultaneously. This is what cluster admin work looks like.

head node · fix THP cluster-wide
exit   # back to head node if still on compute node

# Fix THP on ALL compute nodes simultaneously
pdsh -w compute-[0-1] \
  "echo never | sudo tee /sys/kernel/mm/transparent_hugepage/enabled"

# Verify — both nodes must show [never]
pdsh -w compute-[0-1] \
  "cat /sys/kernel/mm/transparent_hugepage/enabled"

# Record in report
echo "=== THP STATE AFTER ===" >> ~/lab_m3_report.txt
pdsh -w compute-[0-1] \
  "cat /sys/kernel/mm/transparent_hugepage/enabled" >> ~/lab_m3_report.txt

Expected output — fixed

compute-dy-c5-18xl-1: always madvise [never]
compute-dy-c5-18xl-2: always madvise [never]

The admin lesson here

This pdsh command fixes the entire cluster in one operation. Every learner on every compute node benefits. Admin actions are cluster-wide — not per-user, not per-job. No reboot required. Takes effect immediately.

task 5 of 6

05 STREAM Memory Bandwidth Benchmark
15 minutes Checklist item 41

Run STREAM as an independent node health check. This is separate from the job — it tells you whether the memory subsystem is performing within specification regardless of what jobs are doing.

What STREAM is and why it comes last

STREAM measures raw memory bandwidth — how fast data moves between CPU and DRAM. It is not a SLURM job. It runs directly on the compute node. It answers one question: is this node's memory hardware healthy? It validates that the IPC improvement you saw was real infrastructure work — not a fluke.

head node · run STREAM on compute node
exit   # back to head node

# Run STREAM — OMP_NUM_THREADS=36 = one full NUMA node on c5.18xlarge
ssh compute-dy-c5-18xl-1 \
  "cd /home/apps && OMP_NUM_THREADS=36 ./stream | grep Triad"

# Record in report
echo "=== STREAM TRIAD ===" >> ~/lab_m3_report.txt
ssh compute-dy-c5-18xl-1 \
  "cd /home/apps && OMP_NUM_THREADS=36 ./stream | grep Triad" \
  >> ~/lab_m3_report.txt

Expected output

Triad:    85234.6     0.020718    0.020717    0.020726

Expected Triad for c5.18xlarge with 36 threads: 80,000–100,000 MB/s. If result is more than 10% below this range — flag for investigation. Two most likely causes: THP still enabled on this node, or a memory subsystem issue.

06 Cluster-Wide Verification and Admin Summary
10 minutes Checklist item 37

Confirm all fixes are applied across all nodes. Write a plain-language admin summary — the human deliverable of the lab. A researcher should understand it without knowing what THP or IPC means.

head node · cluster-wide verification
# Verify THP correct on ALL nodes
pdsh -w compute-[0-1] \
  "cat /sys/kernel/mm/transparent_hugepage/enabled" | sort

# Verify SLURM daemon healthy on all nodes
pdsh -w compute-[0-1] \
  "systemctl is-active slurmd" | sort
head node · write admin summary
cat >> ~/lab_m3_report.txt << 'EOF'

=== ADMIN SUMMARY ===
# Write 1 paragraph in plain language suitable for ticket closure.
# Cover: what was wrong, what you changed, what improved, STREAM result.
# A researcher with no HPC background should understand it.

EOF

What makes a good admin summary

State the symptom, the root cause in plain terms, the remediation action, and the measurable outcome. Example: "User reported slow MPI job. Investigation found two infrastructure issues: (1) memory page management was misconfigured — fixed cluster-wide; (2) CPU scheduling was not optimised for the workload — fixed at job resubmission. Performance improved ~2× on identical hardware. Memory bandwidth benchmark confirms hardware is healthy."

key numbers reference

IPC · unbound + THP on 0.08 – 0.20 · memory-stalled · random access defeats prefetcher
IPC · bound + THP off 0.18 – 0.35 · improved · ~2× contrast on c5.18xlarge
THP compaction pause Up to 4,200 μs per event · fires mid-job · all ranks stall at MPI barrier
NUMA distance local 10 · 1× cost · same socket
NUMA distance remote 21 · 2.1× cost · cross-socket · every access
STREAM Triad · c5.18xlarge 80,000 – 100,000 MB/s expected with 36 threads · flag if >10% below
Working set 4GB per rank · 16GB total for 4 ranks · strided + random access pattern
perf command sudo perf stat -e instructions,cycles -p <MEM_STRESS_PID> sleep 30 · LLC-load-misses not supported on c5.18xlarge — omit
Why ~2× not 4–5× Random access pattern overwhelms DRAM latency on both bound and unbound runs. Binding reduces cross-NUMA penalty but random access remains the bottleneck. Signal is real and honest.
