What a GPU node actually is

A GPU node is an ordinary server with accelerator cards bolted into it. That phrasing matters, because almost every operational problem in this session comes from forgetting the "ordinary server" half.

  • Host CPUs and memory. The machine still runs Linux, still has NUMA nodes, still schedules processes.
  • Accelerator devices. One, on the node you will log into. Production cluster GPU nodes carry two, four or eight, which is why you will also read the captured state of a four-card node — see the next panel. Each device has its own memory, entirely separate from host memory.
  • The bus between them. PCIe. Every byte a device reads from host memory crosses it, and how a card is attached decides how far that journey is.
  • Direct device-to-device links, where present. Some node types have dedicated card-to-card interconnect. Many do not. Finding out which you have is task 5.
  • Network adapters. Also on PCIe, also attached somewhere specific, which matters the moment a job spans nodes.

An accelerator is not a peripheral the operating system manages for you. It is a second computer in the box, reached across a bus, with its own memory and its own driver — and the administrator's job is mostly about the seam between the two.

Two nodes, and you can only log into one

Your live node has one accelerator. Everything you run today, you run on that. But a single card cannot show you how cards relate to each other, so the lab also ships the captured state of a four-card node — real output, from real hardware, sitting in /opt/lab/evidence/ as plain files.

Every captured file opens with a header saying which node it came from, how many devices it had, and when it was taken. Read that header first, every time. Mistaking another machine's output for your own is a real operational error, not a lab inconvenience — it is how people end up reporting a fault on a healthy node.

Reading captured state is the normal case, not the exception. When a node is down you cannot log into it. When a vendor sends you a support bundle, it is files. When a colleague escalates at two in the morning, you get a paste. Working out what a machine is from output somebody else collected is a skill you will use more often than the skill of running the commands yourself.

Steps that read the bench carry a captured strip above the command. Steps without one run on your own node.

The five-layer stack, bottom to top

This is the spine of the session. Each layer has a version, and each version constrains its neighbours.

  • 1 · Device firmware. On the card itself. Rarely touched, occasionally the answer.
  • 2 · Kernel driver. A kernel module that owns the device. This is the layer that breaks most often, because a kernel update can leave it unbuilt and the devices simply vanish.
  • 3 · User-space runtime. The library applications actually call. Ships with the driver and is tied to it.
  • 4 · Toolkit and libraries. The compiler and the mathematical and communication libraries. Installed separately from the driver, and this is where version confusion lives.
  • 5 · The application. The molecular dynamics code, the solver, the CFD package — compiled against a specific toolkit version, for a specific set of device architectures.

The relationship that catches everyone: a driver supports toolkit versions up to a maximum, and newer drivers support older toolkits. So a node can have a driver advertising support for one toolkit version while a completely different toolkit version is installed, and a user's application compiled against a third. All three numbers are real, all three are different, and only one of them governs whether the application runs.

Compute capability — the one that is not a version number

Alongside the version chain there is a separate axis: the device's compute capability, which describes its hardware generation. It is written like a version — 7.5, 8.0, 9.0 — but it is a property of the silicon and cannot be upgraded.

A compiled CUDA application contains machine code for a list of architectures, fixed when it was built. If your device's generation is not on that list, the application will start, initialise, report the devices as present, and then fail the moment it tries to run anything on one.

Every version in your table can agree and the thing can still not run, because compatibility and architecture support are different questions that fail in different ways and at different moments. Task 3 has you check both, on two supplied binaries.

Not every accelerator is for every workload

Accelerators are specialised, and the specialisation is in the silicon. The headline number on a datasheet is usually single-precision throughput, because that is what graphics and rendering work uses.

Most classical HPC does not. Molecular dynamics, computational fluid dynamics, finite-element analysis and linear algebra at scale run in double precision, and a card's double-precision rate can be anywhere from one half to one sixty-fourth of its single-precision rate depending on what it was designed for.

A card with excellent single-precision figures and crippled double-precision is a perfectly good card — for a workload that is not yours. Task 2 has you measure both rates on this node and work out which kind of card you are looking at, which is the question nobody asks until a research group has already been told the cluster is slow.

Telemetry, read comparatively

The vendor management tool reports utilisation, memory, power draw, temperature, clock speeds, error counters and which processes hold each device. Task 2 has you record it idle and under load.

None of these numbers means anything absolutely. They mean something against the other three devices in the same box, and against what the same device read yesterday. A device at 40 °C and 20 W idle is healthy; the same device at 70 °C idle has something running on it, and that something is usually somebody's forgotten process holding memory nobody can reclaim.

Two comparisons are available to you and you need both. Against time: your own device idle, then the same device under load — which you measure live. Against peers: four devices under one load — which you read from the bench. A single card can only ever give you the first, and an administrator who has only ever had the first will miss the one card in eight that is quietly throttling.

This node is shared, and read-only to you

One node for the whole room, and one card in it. Everything in tasks 1, 3, 4 and 5 is a read, so there is no contention worth worrying about — and the evidence bench is a directory of files, which everyone can read at once.

Task 2's measurements are different — they load the device deliberately, and there is one device to load. They run behind a lock, so one person measures at a time and the rest wait a moment. If somebody else's load is running while you take your idle reading, your idle reading is wrong, which is itself the lesson about measuring on shared infrastructure. With a single shared card it matters more than it would with four.

Working alone?

Allow two to three hours rather than sixty minutes. Do tasks 1, 2 and 3 in order — task 4 is unanswerable without the table from task 3, and task 5 wants the transfer figure you measure at 2.3 to compare its captured numbers against.

Each task ends with a Stop holding the point of the task and the answers to the questions it asks. Read them.

2What this silicon is good at14 min

Telemetry idle and under load on your own device, the same reading across four devices on the bench, host-to-device transfer rate, and the single- against double-precision throughput — which together say what workload this card suits.

Why three measurements rather than one

Telemetry tells you whether a device is healthy, and on a multi-card node whether the cards agree with each other. You measure the first on your own card and read the second from the bench. Transfer rate is the number a user actually feels, because data has to get onto the device before anything can happen to it. Single against double precision tells you what the silicon was built for, and it is the measurement that decides whether this card suits a classical HPC group at all.

The live measurements run behind a lock. If somebody else is measuring, yours waits. Watch theirs in the meantime — one card, one set of numbers, and they will be the same as yours. The bench reads are files and need no lock.

Your precision ratio
If that ratio came out large — many times, not two — this node's cards are not built for double precision. Their double-precision units are a small fraction of their single-precision ones, deliberately, because they were designed for workloads that do not need it.
Why that is the finding that matters

Classical HPC runs in double precision. Molecular dynamics, computational fluid dynamics, finite-element work, linear algebra at scale — all of it. A research group handed a node of these cards for a double-precision code would get a fraction of the performance the datasheet's headline number implies, and would report that the cluster is slow.

A card with a ratio near 2:1 is an HPC accelerator. A ratio of thirty or sixty to one is a card built for single-precision work. Both are good cards. Only one of them is the right purchase for a chemistry group, and buying the wrong one is a mistake an administrator is often the first person in the organisation able to detect — because it is visible in two commands and nowhere else.

Compare, and never against zero

On the captured node the four cards should have moved together under load. One sitting noticeably cooler, drawing less power, or clocked lower on the same work is the thing to notice: either it was not given equal work, or it is throttling, and both are worth knowing. If all four tracked each other, record that — that is what a healthy baseline looks like.

Your own card gave you the other comparison, and it is the one you will have most days. Idle against load, the same device, an hour apart or a month apart. Plenty of estates run single-accelerator nodes — visualisation hosts, licence servers with a card in them, development boxes — and on those this is the only comparison there is, which is exactly why the reading has to be written down. A number with nothing to compare it to becomes a baseline the moment you record it, and stays useless until you do.

Idle is a reading, not a formality

Memory still in use with no process listed is the classic shape of a leaked allocation from a crashed job. Nothing reclaims it until the driver is reset or the node reboots, and the next user gets a device with less memory than it should have and no explanation. Check your idle row again.

And the transfer rate

Device-to-device being far higher than host-to-device is the whole reason data is staged onto a card once and left there. A code that copies across PCIe on every iteration is bounded by the slowest number in your table, not the fastest — and that is a conversation to have with the user, not a fault to escalate.

3The stack, layer by layer12 min

Every layer of the accelerator software stack as installed, with its version and where you found it — and a verdict on two supplied binaries.

Why this is the most valuable thing you will produce today

Five layers, five versions, five different commands. No single command tells you all of it, which is precisely why so few sites have it written down — and why "works on my machine" tickets take days.

Two of these numbers are routinely confused with each other, and a third axis is not a version at all. Finding all of them separately, and knowing which governs what, is the heart of this session.

The two numbers you compared at 3.2 and 3.3
The header's toolkit number is a ceiling — the newest the driver could support. The installed toolkit is what is on disk. Neither one decides whether a given binary runs. A user who reads only the header and concludes "this node has toolkit X" is wrong, and will build against X, and it may well work anyway because of how the compatibility rules fall. Which is the worst outcome available: right result, wrong reasoning, and no idea why it breaks next time.
What actually decided it

The architecture list inside the binary, against the compute capability of the silicon. That is not a version-compatibility question at all, which is why it fails differently — later, on first execution, with a message about no suitable code being available rather than anything about versions.

Version compatibility asks whether these pieces can talk to each other. Architecture support asks whether the compiled code inside the application includes anything your devices can execute. Both can be checked in advance. Only one of them is checked by anybody.

The command to remember

cuobjdump --list-elf works on any CUDA binary — a user's own build, a vendor's package, something extracted from a container image. It is the two-minute answer to a class of ticket that otherwise takes days, and almost nobody on a service desk knows it exists.

The thing to take away

You have just produced, in twelve minutes, the artefact that answers most of this module's tickets. Keep it, date it, and regenerate it after every driver or toolkit change — because a table that is six months stale is worse than none, in that people trust it.

What separates a good classification from a guess

A named layer. "Version problem" is not actionable; "the binary contains machine code for architectures this node's devices are not among" tells somebody exactly what to change. Your table gives you the vocabulary to be that specific, which is most of its value.

On the one you could not settle

Saying so is correct, provided you name the missing fact and the question. The failure mode is not uncertainty — it is inventing certainty and sending a user to rebuild something that was never the problem. One precise question costs them an hour. A wrong confident answer costs them a week.

And the reply the user eventually gets

Each of these ends with somebody telling a researcher what to do next, and your table is what lets that sentence be specific. "Your binary was built for architectures <X> and these devices are <Y>; rebuild with that architecture added, or use the site build" is an answer. "It is a compatibility issue" is not.

5Topology, and what it costs7 min

The device-to-device link type between every pair of cards on a four-card node, read from its captured topology matrix, and a written statement of what that means for a job using more than one of them.

Why this is last, and why it is read rather than run

Everything so far has treated accelerators as independent things. On a multi-card node they are not. A job using two of them makes them talk to each other, and how they are connected decides how expensive that conversation is.

Your own node has one card, so it has no pairs — a topology grid of one device against itself tells you nothing, and the runbook is not going to pretend otherwise. The four-card matrix on the bench does tell you something, and it is real output from real hardware.

Reading a topology matrix out of a file is also the realistic case. The node whose topology you need is usually the one with a job failing on it, which is the one you have been asked to keep your hands off. The matrix is a thing you receive far more often than a thing you run.

5.1 Your own node's affinity, which is still worth having

One device — but the CPU and NUMA columns are real, and yours
nvidia-smi topo -m
Ignore the grid. Read the two columns to the right of it.
  • CPU affinity — which host cores sit nearest this card. A process pinned to the wrong cores pays for it on every transfer, and nothing reports that it is happening.
  • NUMA affinity — which memory node is local to the card. Compare it against the NUMA count you recorded at 1.5.
  • The grid itself is one cell wide. That is the honest output of a single-card node, and it is why the next step reads somebody else's.

What the matrix said
Whatever code appeared, the legend inside that file defines it — and if there were no direct device-to-device links, that is the node's honest answer and the common one. On a node without them, every byte exchanged between two cards travels out over PCIe, through the host, and back in. A job that moves a lot of data between devices pays that on every exchange, and no tuning inside the application removes it.
What you would tell a user

Two things, and they are the useful output of this task. A job that fits on one device should stay on one device — splitting it across four on a node like that can be slower than not splitting it at all. And a job that genuinely needs four devices should have them inside one node rather than spread across two, because as slow as the host path is, the network is slower.

On having read it rather than run it

You have just answered a hardware question about a machine you never logged into, from four files and a legend. That is the ordinary shape of the work. The node you need to characterise is usually the broken one, the busy one, or the one in a facility where you have no account. What made it answerable was that the capture was complete and said where it came from.

Which is the other half of the lesson, and it points back at you. A support bundle without its provenance is a bundle nobody can use — and the next one somebody cannot use may well be one you collected. Date it, name the node, say how many devices it had.

The thread running through all five tasks

Every answer today came from reading something that was already being reported, with no privilege and no changes to anything. That is the lesson of the session, and of the module. The hard part of accelerator administration is not access or tooling. It is that the information is freely available and nobody writes it down, so every ticket starts from nothing.

—Glossary
compute capability
A device's hardware generation, written like a version. A property of the silicon; cannot be changed. Decides whether a compiled binary's machine code can run on it.
cuobjdump
The toolkit utility that reads what is inside a compiled CUDA binary, including which architectures it contains.
deviceQuery
The standard device-properties tool. Reports multiprocessor count, cores, clocks, memory width and capability — things the management tool does not.
double precision · FP64
64-bit floating point. What classical HPC computes in. A card's FP64 rate relative to FP32 says what it was designed for.
ECC
Error-correcting code on device memory. Corrected and uncorrected counts are in the full dump from 1.6; interpreting them is beyond this session.
evidence bench
A directory of output captured from hardware the lab does not provide live — real output from a real node, read as files. Used here because accelerator time is the constraint.
fatbinary
The container inside a CUDA executable holding machine code for one or more architectures. What cuobjdump reads.
GFLOP/s
Billions of floating-point operations per second. Quoted separately for single and double precision, and the two can differ by a factor of sixty.
kernel driver
The kernel module that owns the device. Layer 2, and the layer that breaks most often, usually after a kernel update.
link width
How many PCIe lanes a card negotiated. Below maximum is a real fault with a performance cost and no warning.
NUMA node
A group of CPUs with their own local memory. A card is attached nearer one group than another, which affects transfer speed.
NVLink
Dedicated direct device-to-device interconnect, present on some node types and absent from most. Appears in the topology matrix when present.
PCIe
The bus connecting devices to the host. Where device-to-device traffic goes when there is no direct link.
persistence mode
Whether the driver stays initialised when no process is using a device. Off means a startup cost on every job.
provenance header
The opening lines of a captured file, stating which node it came from, how many devices it had and when it was taken. A capture without one cannot safely be used, because nothing in the output itself says which machine it describes.
SM · multiprocessor
A streaming multiprocessor — the device's unit of parallel execution. Their number and the cores in each set the card's throughput.
toolkit
The compiler and libraries, installed separately from the driver. The number in the management tool's header is the newest the driver supports, not what is installed.
topology matrix
The grid showing how every device connects to every other, plus CPU and NUMA affinity. Its legend defines the codes.
