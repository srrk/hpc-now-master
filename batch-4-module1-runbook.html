how this hour runs

Watch, then annotate

The drawing is the work. The commands are how we find what goes on it.

Your instructor drives a shared terminal. Every command appears on his screen first, with the real output. You have your own shell and you are welcome to run the light commands alongside — but the annotation is what you are actually here to do, and it is what you submit.

Two kinds of command in this runbook. Most are plain reads you can run yourself on the login node — id, sinfo, findmnt, ip. A few reach a compute node through the scheduler, and those are marked instructor drives this. Please do not run those: twelve people asking the scheduler for the same node at once turns an anatomy lab into a queueing exercise, and this cluster has exactly two compute nodes.

Read. Do not act. This is a live shared system. Nothing in this hour changes node or job state, and nothing needs a change-log entry — because nothing changes anything. If you deviate from that, it becomes one, and a conversation.

Some components are not here, and finding that out is the point. This facility is missing several things a mature site would have. When we cannot find something, write it on the Gaps sheet along with what you would have asked the incumbent team. Your notes are read above all for what you recorded as missing. An inventory with an honest gap beats one that is complete because you guessed.

By the end you should be able to point at your own annotation and say, for each component: what it is, which host it runs on, which network it talks over, and what stops working if it stops.

section 1

Establish what the login node is — and is not

The host you land on is not the machine.

Enterprise IT analogy

A shared jump host. Nobody would confuse it with the estate behind it — but at a shell prompt on an unfamiliar cluster, almost everyone does, because it is the only host they have seen. The load you are about to read is people typing, not work being done.

hostname
who                  # who else is logged in right now
w
uptime               # load average
nproc                # how many cores this host has

Look at who. Those are your colleagues, in this room, on this host, right now. That is the first fact about a shared facility, and it is easy to forget an hour later when you are tempted to run something heavy here.

Now put the load average next to nproc. Whatever load exists comes from shells and editors, not from computation. No real work runs here. The login node exists so you can reach the cluster, prepare work and submit it. Everything that matters happens elsewhere, and you have not seen any of it yet.

On your drawingThe login node — its hostname, its core count, how many people are on it
Gaps sheetThere is only one login node here. What would a second one have been for?

section 2

Enumerate the fleet from the scheduler's inventory

The authoritative list of what exists belongs to the scheduler.

Enterprise IT analogy

Your CMDB records what someone believed was true when they wrote it. The scheduler records what is answering right now. On a cluster the second one wins every argument, and the gap between them is where a surprising number of incidents live.

2.1Ask what partitions exist

sinfo

Note what you get. Now ask the same question differently:

sinfo -a

You just saw more partitions the second time. That is not a bug and it is worth ten seconds of your attention. Some partitions on this facility carry an access restriction, and the scheduler hides a partition you are not permitted to use. Run sinfo without -a and you get an honest answer to the wrong question — "what can I use" rather than "what exists".

Every command from here on uses -a. If you are ever handed a cluster and told it has fewer partitions than it does, this is why.

2.2Read the fleet, and the policy behind it

sinfo -a -N -l                     # one line per node, with detail
sinfo -a -h -o "%R|%l|%D|%T"       # partition | time limit | nodes | state
scontrol show partition            # the full policy behind every partition

Read the time limits as policy rather than configuration. A partition with a short ceiling exists for a reason. One with an access list exists for a different reason. Somebody decided each of these, and you are reading their intent.

Note also how many nodes are actually online against how many each partition could hold. A fleet is visibly not uniform, and some of it is not running at all.

Other schedulers, same idea. This facility runs Slurm. The equivalent inventory query exists under other names in PBS Professional and OpenPBS, Spectrum LSF and Grid Engine derivatives. If you already know one of those, say so in the debrief — the room needs the mapping.

On your drawingEvery partition, its time limit, its node count, and which ones you cannot use

section 3

Find the control plane and name its daemons

This is what makes it a cluster rather than a rack of Linux hosts.

Enterprise IT analogy

A control plane with a primary, a standby, and a state store behind it — a cluster manager, a hypervisor control cluster, a domain controller pair. The parts are familiar. What is unfamiliar is what happens to the workload when the control plane stops, and the answer here is not what your instinct says.

3.1Ask the controller about itself

You cannot log in to the controller, and you do not need to.

scontrol ping
scontrol show config | grep -i "SlurmctldHost\|SlurmUser\|ClusterName"

scontrol ping names the controller and says whether it is responding — and if a standby were configured, it would name that too.

There is no standby controller on this facility. That is a finding, not an omission on your part. Write it on the Gaps sheet, and next to it write what a standby would have protected against. Plenty of real facilities run a single controller and accept the exposure deliberately — knowing the exposure exists is the operator's job; pretending it does not is how it becomes an outage nobody planned for.

3.2Look for the accounting service

scontrol show config | grep -i "AccountingStorage"
sacct

Read what comes back from both. The accounting daemon would keep the record of every job that has ever run here — who, what, how long, how much — in a database behind it. This facility does not have one.

Gaps sheet. Then work out what that costs: no historical usage, no per-project reporting, no answer to "what did this group consume last quarter". A later module is entirely about that question.

Note the difference between the two commands you just ran. One told you the configuration says none; the other failed when you tried to use it. An absence you can demonstrate is worth more than one you were told about.

3.3Find the per-node daemon

The controller decides. Something on each compute node actually runs the work, and it is a different daemon.

Instructor drives this. Watch his screen — please do not run these yourself.

# On a compute node, through the scheduler
srun -p standard --time=00:01:00 systemctl is-active slurmd
srun -p standard --time=00:01:00 hostname

# And on the login node — compare
systemctl is-active slurmd

Active on the compute node, absent from the login node. That asymmetry is the difference between the two roles, stated by the system rather than by a diagram.

Look also at the compute node's name. It tells you which partition it belongs to and whether it is permanently online or launched on demand — the naming is not decorative.

On your drawingController host, standby (ABSENT), accounting (ABSENT), and where the per-node daemon runs
Hold this questionWhat happens to a running job if the controller stops? Do not guess — it comes up in the debrief

section 4

Separate the three networks

You assume one network with VLANs. There are three, and confusing them costs an incident.

Enterprise IT analogy

Production, storage, and a lights-out management network. You already run this separation. The difference here is the middle one: the fabric is not carrying storage traffic between servers, it is carrying the application itself — thousands of small messages a second between ranks of one running job, where latency matters more than throughput.

4.1Management — the one you are on

ip -br addr
ip route

This is the network carrying your login, the scheduler's control traffic, and the monitoring data — everything except the workload itself.

4.2The fabric — the one the workload runs on

Instructor drives this. The fabric adapter is on one specific node.

srun -p accel --time=00:02:00 fi_info -p efa
srun -p accel --time=00:02:00 ip -br addr

You are looking for an adapter reporting an active fabric provider, and the interface it presents. Note both.

Then compare the addressing on that node against your own on the login node. Different subnets, different purposes.

Only one node on this facility carries a fabric adapter. On a production cluster every compute node would, because a fabric with one endpoint cannot do the thing fabrics exist for — connecting ranks of a job spread across many nodes. What you are seeing here is the adapter and the software stack, not a working interconnect. That is a legitimate thing to write on the Gaps sheet, and the interconnect module takes the whole subject apart properly.

4.3Out-of-band — the one you cannot reach

There is a third path: the one an operator uses when a node answers on no other network. A BMC, a lights-out card, a serial console — or, on a cloud-hosted facility like this one, a console API rather than a network at all.

You cannot reach it, and you are not supposed to. Your instructor will describe what it is here and who holds it. What goes on your drawing is that the path exists, what it is called, and what it is for — a node that will not answer, at three in the morning, when the alternative is a walk to the datacenter.

On your drawingThree rails: management subnet, fabric type and where it exists, out-of-band path and who holds it

section 5

Map the storage hierarchy from the client side

Several filesystems, different protection models — and which one a job writes to is an operational decision.

Enterprise IT analogy

Tiered storage with different backup and retention policy per tier. Familiar. The unfamiliar part is a filesystem built so a thousand clients can write to it at once by splitting metadata from data across separate servers — and the price of that design is that it is not where you keep anything you want to still have next month.

5.1What is mounted here

findmnt -o TARGET,SOURCE,FSTYPE --noheadings
df -hT

Read the type column, not the path. Paths are named by whoever installed the system; the type tells you what the thing actually is. You should see at least two different filesystem types among your home, scratch and project areas — and one of them is not a general-purpose network filesystem.

That one is a parallel filesystem. Its whole design is the split you cannot see from here: metadata handled separately from data, so many clients can write at once without queueing behind a single server. Note its type on your drawing; the storage module builds on it.

5.2The comparison that matters — login versus compute

Instructor drives this. Watch, then compare against what you got in 5.1.

srun -p standard --time=00:01:00 findmnt -o TARGET,FSTYPE --noheadings
srun -p standard --time=00:01:00 ls -ld /local

Put the two outputs side by side. The difference between the hosts is the most informative thing in this lab. An area present on the compute node and absent from the login node is node-local — visible to that machine alone, invisible to every other node, and gone when the job ends.

Be precise about what you just saw. On this facility /local is a directory on the compute node's root disk, not a separate device — which is why findmnt does not list it. On a production cluster it would be real node-local storage with its own mount line. We are showing you that the area exists and behaves differently from shared storage; we are not pretending it is more than it is. Write that distinction on your drawing rather than smoothing it over.

For every area you found, fill in a row. Some columns you can read, some you must ask about, some you will leave blank and record as a gap.

section 6

Trace identity to its source

One user is one numeric identity everywhere — and something specific breaks when that is untrue.

Enterprise IT analogy

Directory-backed accounts against local ones. You know what happens when a server drops out of the domain and starts resolving names locally. The cluster version has a sharper edge, because files written by a job carry the numeric identity the compute node believed at the time — and that number outlives the job.

6.1Three places, one identity

# 1 — here, on the login node
id

# 3 — as recorded on shared storage, numerically
ls -ln /scratch/$USER /projects/$USER

The -n matters: it shows raw numbers rather than names, which is the only way to see what is actually stored. Names are a lookup; numbers are the fact.

Instructor drives this — the second of the three places.

# 2 — inside a job, on a compute node
srun -p standard --time=00:01:00 id

All three must agree. Note your UID and GID on your drawing.

6.2Where does the answer come from?

getent passwd $USER
getent group $(id -gn)
grep -E "^passwd|^group" /etc/nsswitch.conf

That last file names the sources consulted, in order. Read it carefully. If it lists only local files, identity is held separately on each host and something is keeping those files in step — ask what. If it names a directory service, identity is centrally held and each host asks.

Both designs work. They fail differently, and the difference is what you are recording. On this facility it is the first of the two — which means the thing keeping the hosts consistent is a build process, not a running service. Write down what that implies when a new node joins the fleet at three in the morning.

If your UID on the compute node differed from your UID here, that would be a real defect worth stopping for — a file written by your job on shared storage would carry a number that no longer means you, so it comes back unreadable, owned by a user that may not exist, and no amount of retrying fixes it.

section 7

Read two nodes' hardware honestly

Enough literacy to read a spec sheet critically. Not an architecture class.

Enterprise IT analogy

Reading a server's actual configuration rather than the line item on the purchase order. Familiar work. The new idea is locality: on these machines memory and devices attach to a specific socket, not to the machine as a whole, and a process on the wrong socket pays for every access. Nobody notices on a web server. Everybody notices here.

Instructor drives this whole section. There are two compute nodes and thirteen of us.

7.1The thin compute node

srun -p standard --time=00:02:00 lscpu
srun -p standard --time=00:02:00 free -h
srun -p standard --time=00:02:00 lsblk

From lscpu, take four numbers: sockets, cores per socket, threads per core, NUMA nodes. Multiply the first three and compare against what the scheduler reported for this node in section 2. They should agree. When they do not, one of the two is lying to you, and finding out which is a genuine skill.

7.2The accelerator node

srun -p accel --time=00:02:00 lscpu | grep -E "Socket|Core|NUMA|Model name"
srun -p accel --time=00:02:00 free -h
srun -p accel --time=00:02:00 nvidia-smi
srun -p accel --time=00:02:00 nvidia-smi topo -m

Two nodes of materially different shape, in the same fleet, under the same scheduler. That is what "the fleet is not uniform" means in practice, and it is why the scheduler needs to know each node's attributes rather than assuming they are interchangeable.

The topology matrix in that last command is worth a moment. It shows which devices share a bus and which must cross between sockets to talk to each other. A job placed without regard to that pays for it, every message, for the length of the run.

On your drawingSockets, cores, memory, NUMA and devices — for both node shapes, side by side
Be ready to sayWhich two nodes differ, and in exactly which dimension

section 8

Find where the cluster is watched from

One number, traced from where it is produced to where somebody looks at it.

Enterprise IT analogy

An agent on every host, a time-series store, a dashboard. Structurally identical to what you already run. What differs is what is worth alerting on: a node at 100% CPU is the desired state here, not an incident — and the signals that matter, like a node quietly running slower than its neighbours, are not on any default dashboard.

8.1The node-side collector

systemctl is-active amazon-cloudwatch-agent
ps -ef | grep -i "cloudwatch\|amazon-ssm" | grep -v grep

Something on this host is collecting and shipping measurements. Find it, name it, and note which network it ships over — you established that network in section 4.

8.2The dashboard

Your instructor will show the dashboard consuming those measurements. Watch for one metric you can trace all the way: produced by the collector on a specific host, shipped over the management network, stored, and drawn on the screen in front of you. One number, source to display. That is the whole of the observation layer in a sentence.

8.3What the dashboard does not know

Node metrics are only one input. The scheduler has its own view — what is queued, what is waiting, how long — and neither of these comes from a node agent:

squeue -h -t pending | wc -l      # queue depth right now
sinfo -a -h -o "%F"                # allocated/idle/other/total across the fleet

Those two numbers are among the most useful things you can know about a facility. Ask whether anything on this cluster is joining them to the node metrics — and if not, that is a gap, and most of the observability module.

On question two, hold your answer loosely. Most people say the controller, and there is a good case for it. There is also a case that for a researcher running one tightly-coupled job across hundreds of nodes for days, the worse failure is a single compute node quietly degrading — because every other node in that job waits on the slowest one. Whose work you are protecting changes which host is critical. That reframing is the point of the question.
