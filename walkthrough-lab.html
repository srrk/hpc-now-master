EFA — Elastic Fabric Adapter — is the hardware interconnect between the two compute nodes. Raw bandwidth is not the differentiator here: both EFA and standard Ethernet on c5n.9xlarge top out at around 50 Gbps. The difference is latency. EFA bypasses the OS kernel using RDMA, cutting inter-node message latency from ~150 µs (Ethernet/TCP) to ~10–20 µs. For MPI workloads that exchange messages thousands of times per simulation timestep, that 10× gap is the difference between a 6-hour run and a 3-day run. You will measure it directly in Section 5.

How each traffic type actually travels

A common misconception: EFA is not a general fast lane for all traffic. It is exclusively used by MPI processes that explicitly request it. All storage I/O — including FSx Lustre — travels over standard Ethernet/TCP. The performance differences between storage tiers come from how many servers are in the path, not from which network transport is used.

section 0

Connect to the cluster

Enterprise IT analogy

You are SSH-ing into a jump host. The headnode is the single managed entry point for the whole cluster — identical in function to a bastion server in a corporate datacenter. Everything you run, every job you submit, every file you inspect, goes through this node first.

Open a terminal and connect with your assigned username and the HeadNode IP from your instructor.

ssh <your-username>@<HEADNODE-IP>

Enter the password when prompted: hpcnow2026

If SSH refuses with "host key verification failed" — this happens because each lab deployment brings up a fresh cluster at the same IP or hostname, but with a new host key that doesn't match what your laptop remembered from a previous session.

Clear the stale entry and reconnect normally:

# Remove the stale host key for this IP (run on your laptop, not the cluster)
ssh-keygen -R <HEADNODE-IP>

# Then connect as normal
ssh <your-username>@<HEADNODE-IP>

If you want to skip host key checking entirely for the duration of the lab session — useful if the IP might change mid-session — use the one-liner below. Do not use this on production systems.

ssh -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null \
    <your-username>@<HEADNODE-IP>

A successful login shows a prompt like this:

[<your-username>@ip-172-31-xx-xx ~]$

That ip-172-31-* hostname is the HeadNode's private AWS address. You are on the cluster.

Orient yourself

Stepping into a new home.

Enterprise IT analogy

Your first day in a new datacenter — you walk the floor, open the rack doors, read the cable labels. You build a mental map before you touch anything. Do the same here, but with commands instead of a floor plan.

1.1Who am I and where am I?

whoami          # your username
hostname        # HeadNode hostname

1.2What hardware is under the hood?

nproc
lscpu | grep -E "^CPU\(s\)|Model name|Thread|Core|Socket"

The HeadNode (c5n.large) has 2 vCPUs and 5.25 GiB RAM. It is the manager, not the workhorse. The compute nodes are orders of magnitude larger — you will see them next.

1.3View the compute fleet

sinfo -o "%N %C %m %f"

Output columns: node name · CPUs (allocated/idle/other/total) · memory (MiB) · features. You should see two nodes, each with 36 CPUs, 192,000 MiB RAM, and the efa feature tag.

scontrol show node compute-01    # full details for one node

Look for CfgTRES=cpu=36,mem=192000M and AvailableFeatures=efa.

1.4Explore the shared tools directory

ls /opt/hpc-tools/
ls /opt/hpc-tools/bin/
ls /opt/hpc-tools/sample-jobs/

Everything under /opt/hpc-tools lives on the shared ParallelCluster filesystem. It is visible on both compute nodes without copying anything — that is what shared storage means in practice.

1.5Check your PATH

which ior iozone osu_latency xhpl

All four should resolve immediately. The /etc/profile.d/hpc-tools.sh script configured these paths during cluster bootstrap.

section 2

The storage tour

Familiar tiers, radically different performance characteristics.

Enterprise IT analogy

Your datacenter has a SAN, a NAS, and local SSDs. Each tier has a different speed, capacity, and cost profile. HPC clusters are identical in concept — but the speed gap between tiers is much wider, and choosing the wrong tier for a workload is one of the most common performance mistakes in HPC operations.

2.1See all three tiers at once

df -h | grep -E "/home|/efs|/fsx|Filesystem"
MountTechnologyTypical use
/homeNFS (EBS)Home directories, scripts, small output files
/efsAmazon EFSShared data, checkpoints, moderate I/O
/fsxFSx LustreHigh-throughput parallel I/O, job scratch space

2.2Explore each tier

# Your home directory — NFS mounted from the HeadNode
ls -la ~
echo "Hello from $(hostname)" > ~/test-home.txt
cat ~/test-home.txt

# EFS — shared across the whole cluster
ls /efs
mkdir -p /efs/$USER
echo "EFS write from $(hostname)" > /efs/$USER/test-efs.txt

# FSx Lustre — the fast scratch filesystem
ls /fsx
lfs df -h /fsx        # Lustre-specific disk usage
lfs getstripe /fsx    # see how files are striped across OSTs

lfs is the Lustre filesystem client tool — think of it as df with HPC superpowers. The getstripe output shows Object Storage Targets (OSTs): the parallel storage spindles that give Lustre its throughput.

2.3Write a file and see it from both compute nodes

echo "Written on headnode at $(date)" > /fsx/shared-test.txt

# Run a command on all nodes simultaneously via Slurm
srun --nodes=2 --ntasks-per-node=1 cat /fsx/shared-test.txt

Both compute nodes print the same file without any copying, rsync, or SFTP. All nodes read the same bytes from the same Lustre OSTs simultaneously — this is what parallel shared storage means on a real cluster.

Key distinction from Module 1, slide 24 — NFS (your /home) serialises all I/O through one server over one Ethernet port. Lustre stripes files across multiple storage servers in parallel. That is why FSx can deliver hundreds of GB/s where NFS tops out at a few hundred MB/s. You will measure this gap directly in Section 4.

section 3

Your first Slurm job

The scheduler as a service request system.

Enterprise IT analogy

In ITSM, you submit a service request ticket — it enters a queue, a system picks it up when resources are available, executes the task, and writes output to a log you can retrieve later. Slurm does exactly the same thing. The "resource" is CPU cores on a compute node rather than a human technician, but the model is identical: submit, queue, execute, log.

3.1Read the job script before submitting it

cat /opt/hpc-tools/sample-jobs/01-hello-cluster.sh

The #SBATCH lines are Slurm directives — structured metadata embedded in the script that tells the scheduler exactly what resources to allocate:

DirectiveMeaning
--nodes=2Allocate 2 compute nodes
--ntasks-per-node=1Run 1 process per node
--output=%x-%j.outWrite stdout to <jobname>-<jobid>.out

3.2Submit the job

cd ~
sbatch /opt/hpc-tools/sample-jobs/01-hello-cluster.sh

Note the job ID printed: Submitted batch job 1234

3.3Watch the queue

squeue              # all jobs across all users
squeue -u $USER     # only your jobs

Both compute nodes are configured with MinCount=2 — they are always running. Your job should transition from PD (pending) to R (running) within seconds.

3.4Read the output

cat hello-cluster-<JOBID>.out

You will see hostname output from both compute nodes, and a listing of your home directory retrieved from a compute node — confirming that /home NFS is visible everywhere in the cluster.

3.5Check job accounting

sacct -j <JOBID> --format=JobID,State,Elapsed,CPUTime,NodeList

This is the HPC equivalent of your ITSM ticket audit log — who ran what, when, on which resources, for how long. Every completed job has a permanent record.

section 4

IOR storage benchmark

Numbers, not brochure claims.

Enterprise IT analogy

Running a storage acceptance test before signing an SLA — you want real throughput numbers, not vendor specs. IOR (Interleaved Or Random) is the HPC standard for this. It runs across all your MPI ranks simultaneously: 72 processes on 2 nodes all reading and writing at the same time. A single-client tool like dd will never show you what a filesystem can actually deliver under real HPC load.

4.1Submit the IOR job

sbatch /opt/hpc-tools/sample-jobs/02-ior-benchmark.sh

This runs IOR against all three storage tiers in sequence. Allow 3–5 minutes to complete.

squeue -u $USER     # watch it run

4.2Read the results

ls ~/ior-results-*.txt
cat ~/ior-results-<JOBID>.txt

What to expect

Tier Write Read
/home (NFS) ~200–500 MB/s ~200–500 MB/s
/efs (EFS) ~500 MB/s–1 GB/s ~500 MB/s–1 GB/s
/fsx (Lustre) ~1–3 GB/s ~2–5 GB/s

Why such a difference? NFS serialises all 72 MPI processes through the HeadNode's single Ethernet connection. FSx Lustre serves all 72 processes in parallel from multiple Object Storage Targets — each process gets its own I/O path. That is the "parallel filesystem" concept from Module 1, materialised as actual MB/s numbers.

section 5

EFA latency demo

Measuring the fabric that makes tightly-coupled workloads possible.

Enterprise IT analogy

In a call centre handling a complex escalation, agents need to consult each other constantly. If inter-agent communication is slow, throughput collapses even if each individual agent works quickly. In HPC, MPI processes on different nodes exchange messages thousands of times per second. The latency of those exchanges is the same bottleneck — and this is exactly why InfiniBand was developed, as Rajesh walked you through in Module 1, slides 26–28. EFA is AWS's implementation of the same principle.

You will run the identical latency test twice — once over standard Ethernet (TCP), once over EFA. Both paths share the same ~50 Gbps physical network on c5n.9xlarge. What changes is the software path: Ethernet goes through the OS kernel and TCP stack; EFA goes directly from one process's memory to another's, bypassing the kernel entirely. The bandwidth numbers look similar. The latency numbers do not.

5.1Ethernet baseline — the slow path

sbatch /opt/hpc-tools/sample-jobs/03-osu-latency-ethernet.sh
cat osu-latency-ethernet-<JOBID>.out

Look at the latency column for small messages (1–8 bytes). You will see values around 100–200 µs.

5.2EFA — the fast path

sbatch /opt/hpc-tools/sample-jobs/04-osu-latency-efa.sh
cat osu-latency-efa-<JOBID>.out

Small message latency drops to 10–20 µs — roughly a 10× improvement on the same two physical nodes over the same physical network.

5.3Understand what you're seeing

Size (bytes)   Ethernet (µs)   EFA (µs)   Ratio
           1        ~150          ~12       ~12×
           8        ~150          ~12       ~12×
          64        ~155          ~13       ~12×
        1024        ~160          ~15       ~10×

This is not a configuration trick. EFA bypasses the OS kernel entirely using RDMA — Remote Direct Memory Access. One MPI process writes directly into another process's memory on a remote machine, with no kernel context switches, no buffer copies, no TCP stack processing.

For a simulation where 72 MPI processes exchange boundary condition data 10,000 times per simulation timestep: the difference between 150 µs and 12 µs is the difference between a 3-day run and a 6-hour run. That multiplier is why the network fabric is infrastructure-critical in HPC.

5.4Bonus — EFA peak bandwidth

sbatch /opt/hpc-tools/sample-jobs/05-osu-bandwidth-efa.sh
cat osu-bandwidth-efa-<JOBID>.out

Peak bandwidth should approach 50 Gbps — the full line rate of the c5n.9xlarge EFA network adapter.

section 6

HPL Linpack demo

The benchmark that ranks supercomputers — running on your two-node cluster.

Enterprise IT analogy

Every server vendor quotes SPEC benchmarks. HPL Linpack is the HPC equivalent — it is the benchmark behind the TOP500 list that ranks the world's fastest supercomputers. You are about to run the same benchmark code (at a much smaller scale) on your own cluster, and read the same GFLOPS metric that defines where a machine sits in the global HPC hierarchy.

HPL solves a dense system of linear equations using LU factorisation. It exercises every layer of the HPC stack simultaneously: floating-point throughput, memory bandwidth, inter-node MPI communication over EFA, and scratch I/O on FSx. That comprehensive coverage is why it is a meaningful benchmark.

6.1Look at the problem configuration

cat /opt/hpc-tools/hpl/HPL.dat
ParameterValueMeaning
N50000Matrix size: 50,000 × 50,000 doubles ≈ 20 GiB/node
NB192Block size: tuned for L3 cache on c5n.9xlarge
P2Process grid rows
Q36Process grid columns — 2 × 36 = 72 MPI ranks total

N=50000 uses roughly 80% of available RAM across both nodes, which is the standard HPL tuning target. Going higher risks OOM; going lower leaves performance on the table.

6.2Submit the job now

sbatch /opt/hpc-tools/sample-jobs/07-linpack-demo.sh

This will take 15–25 minutes. Submit it now, then continue reading through the explanation below while it runs.

squeue -u $USER    # check status periodically

6.3While you wait — what is actually happening

HPL breaks the N×N matrix into NB×NB blocks and distributes them across the P×Q process grid. Each of the 72 MPI ranks owns a subset of blocks. At every step of the factorisation:

01Each rank performs Gaussian elimination on its local block — CPU-bound, using OpenBLAS DGEMM (the fastest dense matrix routine available on this hardware).
02The pivot row is broadcast to all ranks in the same row of the process grid — EFA bandwidth.
03Boundary data is exchanged with neighbouring ranks — EFA latency.

All three bottlenecks — floating-point throughput, network bandwidth, network latency — are exercised simultaneously and continuously. That is why HPL is a meaningful benchmark and not just a stress test.

The job also uses /fsx for scratch, so FSx Lustre is under load at the same time. You are benchmarking the entire stack.

6.4Read the result

cat linpack-demo-<JOBID>.out

Look for the WR (Warm Run) line near the bottom of the output:

WR11R2R4      50000   192     2    36         xxx.xx    x.xxxe+03

The last two columns are time in seconds and Gflops — billions of floating-point operations per second.

Expected result

Your cluster 3,000 – 5,000 Gflops (3–5 TFLOPS)
Modern laptop ~100–200 Gflops for comparison
World #1 (2024) ~1,000,000,000 Gflops 1 ExaFLOP

Your two-node cluster sits between a laptop and a national supercomputer — but it runs the exact same benchmark code as every machine on the TOP500 list. The number at the end is a real number, on real hardware, produced by you.
