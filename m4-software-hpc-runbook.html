how to use this runbook

When do you use avail vs spider?

Lab 3 / 4 · ~30 minutes · Guided + Prompted

Library Diagnostics — Reading ldd Output

Build ldd fluency before the troubleshooting lab. Concepts: FC-SWE-06 (dynamic linking) · FC-SWE-07 (ABI vs API)

Setup. ldd (list dynamic dependencies) shows every shared library a binary needs and whether the dynamic linker can currently find each one in LD_LIBRARY_PATH. A pre-compiled binary ~/lab/m4/app is used throughout. It requires libfoo.so.1 — available as libfoo/1.0 (compatible) and libfoo/2.0 (incompatible ABI).

Ex 1

Run ldd on a clean binary — read every line

module purge
module load gcc/11.3.0
ldd ~/lab/m4/app
Expected output
        linux-vdso.so.1 (0x00007fff...)
        libfoo.so.1 => not found
        libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f...)
Record your observation
Libraries showing “=> /path”:
Libraries showing “=> not found”:

FC-SWE-06 — the binary carries references, not library code. At runtime the dynamic linker walks LD_LIBRARY_PATH for each listed name. “=> not found” means the name was not found in any directory on the current LD_LIBRARY_PATH. This is an environment problem, not an installation problem.

What changed in ldd output?

“Found” in ldd means the file exists at that path and the linker can load it. Loading libfoo/1.0 prepended its lib directory to LD_LIBRARY_PATH. The linker found libfoo.so.1 there.

Ex 3

module unload libfoo/1.0
module load libfoo/2.0

        libfoo.so.1 => /opt/sw/libfoo/2.0/lib/libfoo.so.1 (0x00007f...)

Expected: app crashes
./app: symbol lookup error: ./app: undefined symbol: foo_compute_v1
Record the critical detail
ldd shows libfoo.so.1 as:
But running app produces:
How can the library be “found” and the app still crash?
Common misread — read this before continuing

ldd found libfoo.so.1 in the v2.0 path. The file is there.

“Found” means the linker located a file with the right soname. It does not mean the file contains the expected symbols. libfoo v2.0 removed foo_compute_v1. The binary was compiled against v1.0’s ABI and expects that symbol. v2.0 is there. The symbol is not. This is FC-SWE-07: same soname (libfoo.so.1), different binary contract.

Explanation — FC-SWE-06 + FC-SWE-07
1. NOT a missing library. ldd shows libfoo.so.1 is FOUND at /opt/sw/libfoo/2.0/lib/.
   If it were missing, ldd would show "=> not found". The file exists and is loadable.

2. YES, wrong version at the binary interface level. The app was compiled against
   libfoo v1.0, which exported the symbol foo_compute_v1. libfoo v2.0 removed that
   symbol (the ABI changed). The file name (libfoo.so.1) and soname are identical
   between versions — only the exported symbols differ. This is FC-SWE-07: same API
   surface, different binary contract.

3. The operator can restore libfoo/1.0 as an available module (if it still exists on
   the system) so the researcher can load that version. Rebuilding the application
   against libfoo/2.0's new ABI requires engineering work — access to source code,
   knowledge of the API changes, and a full recompile.

4. "The library was updated and its binary interface changed; your application was
   built against the previous version — we can either restore the old version for
   you or arrange a rebuild against the new one."

FC-SWE-07 — ABI vs API. Same soname, different binary contract. ldd finds the file; the dynamic linker loads it; the symbol lookup fails. This class of failure is only diagnosable with ldd. Without Lab 3, Scenario C in Lab 4 would look like an installation problem. It is not.

Explanation — FC-SWE-07
1. ABI mismatch (FC-SWE-07). The app was compiled against libfoo v1.0, which
   exported the symbol foo_compute_v1. libfoo v2.0 changed its binary interface
   (ABI) and removed that symbol. The file (libfoo.so.1) is found because both
   versions use the same soname. But v2.0 does not contain the symbol the app
   needs. ldd confirms the file; the dynamic linker loads it; the symbol lookup
   fails at startup.

2. The library’s binary interface changed between v1.0 and v2.0. The application
   binary was not changed — but the library it depends on was, silently, at
   the binary level. The researcher is correct: they changed nothing.

3. If libfoo/1.0 still exists on the instance, the operator can make it available
   as a loadable module so the researcher can pin to it. If it has been removed,
   or if the application must use v2.0, rebuilding the application against v2.0’s
   new ABI is required — that needs engineering access to source code.

4. Engineering note:
   "app binary at ~/lab/m4/app was compiled against libfoo v1.0 (symbol
   foo_compute_v1 expected). libfoo/2.0 removed that symbol. Researcher needs
   either libfoo/1.0 restored as a loadable module, or a rebuild of app against
   libfoo/2.0’s current ABI. ldd ~/lab/m4/app with libfoo/2.0 loaded confirms
   the library is found but the symbol is absent."

5. Researcher response:
   "The library was updated last week and its internal interface changed; your
   application was built against the previous version — we are investigating
   whether we can restore the old version or will need to arrange a rebuild."

FC-SWE-07 — ABI mismatch. ldd finds the file; the symbol lookup fails. This is only diagnosable with ldd. Without Lab 3, this failure looks identical to a missing library installation. It is not — and the response to the researcher depends entirely on understanding that distinction.
