00 Setup — Verify before you benchmark
↑ Slides: Healthy Baseline · 4.1

Run

# Check all compute nodes are ready sinfo # Check perf is usable — must be 1 NODES=$(sinfo -h -N -o '%N' | tr '\n' ',' | sed 's/,$//') pdsh -w $NODES 'sysctl kernel.perf_event_paranoid' # Check THP state — record what you see pdsh -w $NODES \ 'cat /sys/kernel/mm/transparent_hugepage/enabled' # Check NUMA topology on compute node ssh $(sinfo -h -N -o '%N' | head -1) 'numactl --hardware'

Observe

sinfo: 2 nodes · STATE = idle perf_event_paranoid = 1 ← must be 1 before benchmarking THP: [always] madvise never ← note this — you will fix it later numactl distances: node 0 1 0: 10 21 ← distance 21 = 2.1× slower than local

If perf_event_paranoid shows 2

Stop. Tell Rajesh. Do not submit the benchmark until this is fixed — perf stat will return empty output.

What it means

Two nodes are available. perf will work. THP is armed on every compute node — this is the misconfiguration you will investigate and fix during the lab. The NUMA distance of 21 means any memory allocated on the wrong node costs 2.1× more to access.

01 Submit — Get the job running
↑ Slides: Lab Objective · Slide 16

Run

# Inspect the job script before submitting cat /opt/hpc-tools/sample-jobs/lab3-benchmark.sh # Copy to your working directory and submit mkdir -p ~/lab3 cp /opt/hpc-tools/sample-jobs/lab3-benchmark.sh ~/lab3/ sbatch ~/lab3/lab3-benchmark.sh # Wait until ST = R before proceeding watch -n 2 squeue -j <JOBID>

Observe

Submitted batch job 12345 JOBID ST NODELIST 12345 R compute-dy-c5n4xlarge-[1-2]

Notice — no --cpu-bind or --mem-bind in the job script

This is the misconfiguration. The default job script has no binding flags. You will discover the consequences in sections 02 and 03.

What it means

Job is running across both compute nodes. Do not proceed until ST shows R. You cannot attach profiling tools to a queued job.

02 Process Affinity — Did the binding hold?
↑ Slides: 4.2 Provocation · 4.2 Lab Moment

Run

# SSH to the first compute node ssh $(sinfo -h -N -o '%N' | head -1) # Find a running MPI rank — note the PID ps aux | grep osu_alltoall | grep -v grep # Check CPU affinity of that rank taskset -cp <PID>

Observe

pid 12456's current affinity list: 0-15 # 0-15 = rank is unpinned — can run on any of 16 CPUs # Healthy would show a single CPU: "affinity list: 4"

What it means

The binding failed. SLURM applied no cpu-bind because the job script had no --cpu-bind=cores flag. The CFS scheduler is free to migrate this rank between any of the 16 CPUs. Every migration invalidates the CPU cache. IPC drops from 1.5 to 0.3.

03 NUMA — Is memory on the wrong node?
↑ Slides: 4.3 Provocation · 4.3 Lab Moment

Run

# Still on the compute node, using the same PID numastat -p <PID> | tee /tmp/numa_output.txt

Observe

Per-node process memory (MBs) for PID 12456 Node 0 Node 1 --------- --------- Heap 234.56 89.23 Stack 2.34 0.00 Private 1024.00 312.45 --------- --------- Total 1260.90 401.68 ← non-zero = NUMA imbalance

What it means

401MB is on the wrong NUMA node. The job's ranks are running on Node 0 CPUs — but 401MB of their memory was allocated on Node 1. Every access to that memory crosses the NUMA boundary at 2.1× the latency of a local access. No error message. No warning. Just slower.

04 THP — Is it armed on all nodes?
↑ Slides: 4.4 Provocation · 4.4 Lab Moment

Run

# Return to head node first exit # Check THP state cluster-wide in one command NODES=$(sinfo -h -N -o '%N' | tr '\n' ',' | sed 's/,$//') pdsh -w $NODES \ 'cat /sys/kernel/mm/transparent_hugepage/enabled'

Observe

compute-dy-c5n4xlarge-1: [always] madvise never compute-dy-c5n4xlarge-2: [always] madvise never

What it means

THP is armed on every compute node. The bracket shows the active state. [always] means the kernel will attempt to promote 4KB pages to 2MB pages automatically — firing a compaction event mid-job. Every MPI rank waits during compaction. This is a cluster-wide configuration problem, not a per-job issue. You will fix it in section 07.

05 Profiling — Four tools, one sequence
↑ Slides: 4.6 Provocation · 4.6 Lab Moment

Run

# Resubmit if the previous job has finished sbatch ~/lab3/lab3-benchmark.sh # SSH back to compute node ssh $(sinfo -h -N -o '%N' | head -1) # Find PID again ps aux | grep osu_alltoall | grep -v grep # Tool 1 — IPC: is the CPU doing useful work? sudo perf stat -p <PID> sleep 15 \ 2>&1 | tee /tmp/perf_output.txt # Tool 2 — NUMA already done — /tmp/numa_output.txt # Tool 3 — CPU placement: are ranks on the right CPUs? mpstat -P ALL 1 5 | tee /tmp/mpstat_output.txt # Tool 4 — Storage: is I/O the bottleneck? iostat -xdm 2 5 | tee /tmp/iostat_output.txt

Observe

perf stat: instructions per cycle: 0.31 ← below 0.5 = memory stalled cache-misses: 7.99% ← above 5% = cache thrashing mpstat (look at %usr per CPU): CPU 0-7: ~99% usr ← ranks here CPU 8-15: ~0% usr ← should be idle, check these iostat (look at await, not %util): await: 0.42ms ← under 1ms = storage is NOT the bottleneck %util: 89% ← ignore this number in HPC context

Storage util at 89–100% is not an incident

In HPC, high %util means the storage is working at full speed — that is correct. Read await. Under 1ms on this filesystem means storage is not the bottleneck. Do not raise an alert for %util alone.

What it means

IPC = 0.31 confirms the job is memory-stalled, not compute-bound. The CPU is waiting for data from memory on every instruction cycle. Combined with the NUMA result from section 03 — 401MB on the wrong node — the root cause is clear: the job is paying the 2.1× NUMA latency penalty on every remote memory access. Storage is ruled out. I/O is not the bottleneck.

06 cgroups — Read the enforcement boundary
↑ Slides: 4.7 Provocation · 4.7 Lab Moment

Run

# On the compute node — find the SLURM cgroup ls /sys/fs/cgroup/system.slice/ | grep slurm # Read the memory limit for this job # Replace 12345 with your JOBID cat /sys/fs/cgroup/system.slice/\ slurmstepd.scope/job_<JOBID>/memory.max # Check open file limit ulimit -n

Observe

memory.max = 8589934592 = 8GB ← from #SBATCH --mem=8G ulimit -n = 1024 ← default · too low for parallel I/O jobs

What it means

SLURM has placed a hard 8GB memory wall around this job. If the job exceeds it, the OOM killer fires silently — no stack trace, no useful error. The raw bytes (8589934592 ÷ 1073741824 = 8GB) is the translation you need to make. The open file limit of 1024 is the default — a parallel I/O job with multiple ranks writing simultaneously can exhaust this quickly.

07 pdsh — Fix the cluster, not the node
↑ Slides: 4.8 pdsh · 4.4 Lab Moment

Run

# Return to head node exit # Disable THP on all compute nodes simultaneously NODES=$(sinfo -h -N -o '%N' | tr '\n' ',' | sed 's/,$//') pdsh -w $NODES \ 'echo never > /sys/kernel/mm/transparent_hugepage/enabled && \ echo never > /sys/kernel/mm/transparent_hugepage/defrag' # Verify cluster-wide — one command, all nodes pdsh -w $NODES \ 'cat /sys/kernel/mm/transparent_hugepage/enabled'

Observe

compute-dy-c5n4xlarge-1: always madvise [never] compute-dy-c5n4xlarge-2: always madvise [never]

What it means

Both nodes fixed in one command. This is the HPC admin's operational unit — the cluster, not the node. pdsh runs the command on every node simultaneously. The bracket has moved from [always] to [never]. Every job submitted from this point forward runs without THP compaction risk.

08 Resubmit — Apply the fix and compare
↑ Slides: 4.2 Lab Moment · 4.3 Lab Moment

Run

# Inspect the fixed job script cat /opt/hpc-tools/sample-jobs/lab3-benchmark-fixed.sh # Copy and submit cp /opt/hpc-tools/sample-jobs/lab3-benchmark-fixed.sh ~/lab3/ sbatch ~/lab3/lab3-benchmark-fixed.sh # Wait for R state, then SSH to compute node watch -n 2 squeue -j <FIXED_JOBID> ssh $(sinfo -h -N -o '%N' | head -1) # Repeat the key checks ps aux | grep osu_alltoall | grep -v grep taskset -cp <NEW_PID> numastat -p <NEW_PID> | tee /tmp/numa_fixed.txt sudo perf stat -p <NEW_PID> sleep 15 \ 2>&1 | tee /tmp/perf_fixed.txt

Observe

taskset: affinity list: 4 ← single CPU, binding held numastat Node 1 Total: 0.00 ← all memory local perf stat IPC: 1.47 ← compute bound, healthy

What it means

Three signals changed. Binding held — rank is on a single CPU. Memory is local — Node 1 is zero. IPC recovered — the job is now compute-bound rather than memory-stalled. The two flags --mem-bind=local and --cpu-bind=cores fixed the NUMA imbalance and the affinity failure together.

Troubleshooting

perf stat returns all zeros

Run sysctl kernel.perf_event_paranoid on the compute node. If it shows 2 — tell Rajesh. It should have been pre-set to 1 by the cluster bootstrap.

numastat -p shows "no such process" or permission denied

You must be on the same node as the running MPI rank. Confirm with ps aux | grep osu_alltoall. If empty — the job has finished. Resubmit and run numastat immediately after the job reaches R state.

Job stays in PD (pending) and never starts

Run squeue -j <JOBID> -o "%.18i %.9P %.8j %.2t %R" to see the reason. If a previous job is still running — scancel <old_jobid> first.

pdsh hangs on first run

SSH host key checking is blocking pdsh. Run: for n in $(sinfo -h -N -o '%N'); do ssh-keyscan -H $n >> ~/.ssh/known_hosts 2>/dev/null; done — then retry.

taskset shows a single CPU even without --cpu-bind in the job script

Check scontrol show partition compute | grep CpuBind. If the partition has a CpuBind default set, SLURM applies it regardless. This is correct behaviour — note it in your report.

THP still shows [always] after the pdsh fix

The pdsh command may have failed silently. Run pdsh -w $NODES 'sudo sh -c "echo never > /sys/kernel/mm/transparent_hugepage/enabled"' and check again.

Benchmark finishes too fast to profile

Edit your copy of the job script and change -i 100 to -i 1000. Resubmit. This gives you more time to attach profiling tools while the job runs.
