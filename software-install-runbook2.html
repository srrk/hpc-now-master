—Before you startread once · 6 min

The problem this lab is about

On your laptop you install software with the distribution's package manager. One command, one version, done. On a cluster almost none of that works, for four reasons.

  • The software is not packaged. Scientific applications ship as source tarballs from a research group's web page, not from a distribution repository.
  • Versions matter, and several are needed at once. One group's results depend on version 2.1; another needs 3.0 today. Both must exist.
  • You are not root. Cluster nodes are shared. Nobody gets to install into /usr.
  • The machine that runs the job is not the machine you typed on. Anything installed in the wrong place is invisible to the job.

Every tool in this lab exists because of those four facts. You will meet the problem first, by hand, and then meet each tool as an answer to it.

The two programs you will install

hwloc — "hardware locality". It reads the machine's layout: how many processor sockets, how many cores on each, how the caches are shared, which memory belongs to which socket, and which network cards and devices are attached where. On a cluster that layout decides how fast a job runs, so almost every HPC tool depends on hwloc underneath.

likwid — a set of performance tools built on top of hwloc. You will only use one of them, likwid-topology, which prints the machine layout in a readable form. It is the same command in all six rungs.

likwid needs hwloc to work. That single dependency is the reason this lab teaches anything — one package needing another is where all the difficulty in software management comes from.

Three things every installed program needs

When you type a command, the shell has to find it. When that program starts, the system has to find the libraries it was built against. Neither happens by magic.

  • PATH — a list of directories the shell searches for commands. If your program's bin directory is not on it, you get command not found.
  • LD_LIBRARY_PATH — a list of directories the system searches for shared libraries at the moment a program starts. If your program's lib directory is not on it, you get cannot open shared object file. This one catches everybody, because the command is clearly there and it still will not run.
  • --prefix — not an environment variable, but the flag that decides where a program installs itself. --prefix=/somewhere means binaries land in /somewhere/bin, libraries in /somewhere/lib, manuals in /somewhere/share/man. Get this wrong and everything else fails downstream.

In rung 1 you set the first two by hand. In rungs 2 to 5 something else sets them for you. That is the whole ladder.

What "build from source" means

Most of these tarballs use a convention called autotools, which is three commands in a fixed order:

  • ./configure — looks around the machine, finds what is available, and writes the build instructions to match. This is the step that quietly decides what your program will and will not be able to do.
  • make — compiles the source into binaries and libraries, inside the build directory.
  • make install — copies the results to wherever --prefix said.

Not everything uses autotools. likwid does not, and rung 1 shows you what that is like.

Working alone?

You can. Allow three to four hours rather than two, and stop wherever you like — the safe resume points are at the end of each rung.

Rungs 1 and 2 must be done in order, because rung 2 uses what rung 1 built. Rungs 3, 4 and 5 are independent of each other and of rung 1.

Each rung ends with a Stop. Those contain the point of the rung and the answers to the questions asked in it. Read them; they are not optional.

0Orientation8 min

You know who you are here, what machines exist, and where software is allowed to live.

Why this rung exists

A cluster is not one machine. There is a login node, which is what you connect to and where you edit files and compile things. There are compute nodes, which are separate computers that actually run the jobs, and which you never log into directly.

They share some filesystems and not others. Knowing which is which is the difference between software that works and software that mysteriously does not, so it is the first thing to establish anywhere.

0.1 Who am I

whoami && id   # hpcadmins should be in your groups

0.2 What machines exist

hostname      # you are on the login node
sinfo -N -l   # the compute nodes are other machines

Stop · rung 0read before going on
  • /apps and /home are shared: the second df shows them mounted from head, the login node.
  • The s in drwxrwsr-x: anything you create under /apps belongs to hpcadmins.
  • You are not root, and today you will not need to be.
The point

/apps and /home are shared storage. The login node and every compute node see the same files at the same path. The login node keeps them on its own disk — that is the first df — and every compute node mounts them from it over the network: head:/apps in the second df means “/apps on the machine called head”, which is the login node you are typing on. Anything you install anywhere else — /tmp, /usr/local, /opt — exists on one machine only, and a job running on another will not find it.

That is why there is a /apps at all, and it is the most common first mistake on any cluster: install somewhere local, test it interactively where it works, submit a job, and get No such file or directory for a file you are looking straight at.

The setgid bit

The s in drwxrwsr-x means files you create inherit the directory's group — hpcadmins — rather than your own. Colleagues can read your work without you doing anything, which is what makes a shared software tree practical.

You are not root

And you will not need to be. Everything today is done as yourself, which is how it works at a real site — you will almost never be given root on a production cluster.

1Build it yourself32 min

hwloc and likwid built from source, installed under your own name, and running in a Slurm job that you taught to find them.

Why this rung exists

This is the baseline: no tools at all. You are the package manager. You unpack the source, configure it, compile it, decide where it goes, and then teach every job you ever submit how to find it.

Everything you do here works. It is also the rung you will keep coming back to, because sooner or later somebody needs software nobody has written a recipe for. The point is not that this is wrong — it is to feel exactly what it costs, so that the next four rungs mean something.

Two things to watch as you go: how many lines of environment setup you end up writing, and whether anything ever warns you that something is missing.

1.1 Unpack hwloc

Build in local scratch — install to shared storage
mkdir -p /tmp/$USER-build && cd /tmp/$USER-build
tar xf /apps/tarballs/hwloc-2.11.2.tar.gz && cd hwloc-2.11.2

Compiling makes thousands of small temporary files. Doing that on the shared filesystem is slow and rude to everyone else, so you build in local scratch and install to shared storage. Only the install location has to be shared.

1.2 Configure it

--prefix decides where it lands. The most important flag today.
./configure --prefix=/apps/software/$USER/hwloc/2.11.2
Read the summary block before moving onconfigure ends by listing what it found on this machine and what it will therefore support. Find the XML input / output line — it says basic, not full. Nobody asked you: configure looked for a library, did not find its headers, and quietly chose a smaller option. Write that line down. You will see the library's name again at rung 3.

1.3 Build and install

1.4 Check it landed

1.5 Unpack likwid

cd /tmp/$USER-build && tar xf /apps/tarballs/likwid-5.4.1.tar.gz && cd likwid-5.4.1

1.6 Find the lines you have to change

No ./configure here. You edit a file.
grep -n "^PREFIX\|^ACCESSMODE\|^BUILDDAEMON\|^BUILDFREQ\|^INSTALL_CHOWN\|^#HWLOC_" config.mk

likwid's authors wrote their own build system instead of using autotools. There is no ./configure to interrogate the machine — you tell it what is true by editing config.mk by hand. This is common in scientific software and it is one of the reasons "just build it from source" is rarely just anything.

1.7 Edit config.mk

What changes, and why — reference only; the next box makes the edits for you
PREFIX = /apps/software/<you>/likwid/5.4.1   # your username, spelled out

BUILDFREQ = false                            # needs root
INSTALL_CHOWN =                              # was -g root -o root
HWLOC_INCLUDE_DIR = /apps/software/<you>/hwloc/2.11.2/include  # delete the # first

Why this rung exists — and what Lmod is

Rung 1 left you with four export lines that you must repeat in every job script, and that every colleague must be told about. Multiply by fifty packages and four versions each and it stops being workable.

Lmod is an environment module system. For each installed package you write one small file — a modulefile — that says what that package needs added to the environment. Users then type module load likwid and Lmod makes those changes. module unload reverses every one of them exactly, which plain export cannot do.

A modulefile is written in Lua and is usually five to ten lines. It is a contract: the person who installed the software writes down how to use it, once, and nobody has to know afterwards.

Watch for this: the binary does not change in this rung. Only how you reach it changes.

2.1 Make room for your modulefiles

mkdir -p /apps/modulefiles/$USER/{hwloc,likwid}

Lmod finds modulefiles by directory layout: <somewhere>/<package>/<version>.lua. That is why the package name is a directory and the version is the filename — it is how module load likwid/5.4.1 knows where to look.

2.2 Install the one you have been given

cp /apps/tarballs/examples/hwloc-2.11.2.lua /apps/modulefiles/$USER/hwloc/2.11.2.lua
sed -i "s/USERNAME/$USER/g" /apps/modulefiles/$USER/hwloc/2.11.2.lua   # your username where the file says USERNAME

2.3 Read it before you write your own

cat /apps/modulefiles/$USER/hwloc/2.11.2.lua
You should see
-- hwloc 2.11.2 · hand-written modulefile
whatis("hwloc 2.11.2 — hardware locality")

local base = "/apps/software/<you>/hwloc/2.11.2"

prepend_path("PATH",            pathJoin(base, "bin"))
prepend_path("LD_LIBRARY_PATH", pathJoin(base, "lib"))
prepend_path("MANPATH",         pathJoin(base, "share/man"))

-- prepend_path does what your export lines did in rung 1,
-- and Lmod reverses every one on `module unload`.

Read it against what you typed in rung 1. prepend_path is the same operation as export PATH=new:$PATH — add to the front, keep what was there. pathJoin just glues directory names together safely. There is nothing exotic here; it is your four export lines, written down where they belong.

2.4 Write likwid's — the one that has a dependency

Paste it — the last line is the one that matters
cat > /apps/modulefiles/$USER/likwid/5.4.1.lua <<'EOF'
-- likwid 5.4.1 · hand-written modulefile
whatis("likwid 5.4.1 — performance tools")

local base = "/apps/software/USERNAME/likwid/5.4.1"

prepend_path("PATH",            pathJoin(base, "bin"))
prepend_path("LD_LIBRARY_PATH", pathJoin(base, "lib"))
prepend_path("MANPATH",         pathJoin(base, "man"))

-- likwid needs YOUR hwloc (step 1.7): loading likwid loads hwloc first
depends_on("hwloc/2.11.2")
EOF
sed -i "s/USERNAME/$USER/g" /apps/modulefiles/$USER/likwid/5.4.1.lua   # your username where the file says USERNAME

The last line is the one hwloc's file does not have. You built likwid against your hwloc (step 1.7), so it cannot start unless hwloc's library is on LD_LIBRARY_PATH first — in rung 1 that was your second pair of export lines. depends_on loads hwloc whenever likwid is loaded; prereq would only check, and fail, pushing the work back onto the user.

The version is pinned in that linedepends_on("hwloc/2.11.2") names a version. Write depends_on("hwloc") and Lmod loads whichever hwloc it finds first — which on a real cluster carrying four hwloc versions is a support ticket waiting to happen.

2.5 Register your modulefile directory

module use /apps/modulefiles/$USER   # add your modulefiles to the places Lmod looks
module --ignore_cache avail   # what Lmod can load now (--ignore_cache: your files are new)

module use adds a directory to MODULEPATH, which is the list of places Lmod looks — the same idea as PATH, for modulefiles. --ignore_cache is needed because Lmod caches what it found last time, and your files are new.

2.6 Load it and check the chain

module purge && module load likwid
module list   # should show TWO modules, not one
which likwid-topology lstopo

cat > $HOME/m7sx/stage2.sh <<'EOF'

#SBATCH --output=/home/USERNAME/m7sx/stage2_out.txt

sed -i "s/USERNAME/$USER/g" $HOME/m7sx/stage2.sh   # your username where the file says USERNAME

2.8 Submit it

The point

Lmod fixed the environment, not the software. It is the same binary you built in rung 1, carrying the same gap. A module system makes software usable, shareable and reversible — genuinely valuable, and the single biggest quality-of-life improvement on any cluster.

But it operates entirely on paths. It has no idea what is inside the software, it did not build anything, and it will never tell you that something is missing. That limit is precisely what rung 3 addresses.

3Spack22 min

The same command, installed by a tool that worked out the dependencies itself — with a visibly different result.

Why this rung exists — and what Spack is

Rungs 1 and 2 both assumed you know what the software needs. You decided hwloc was the only dependency, because that was the only one you were told about.

Spack is a source package manager built for HPC. It carries a recipe for each package describing its dependencies, its options, and how to build it. You ask for likwid and Spack works out the full set of packages required — the dependency graph — then builds or fetches each one in the right order.

Two ideas worth having before you start:

  • Concretization. Before building anything, Spack turns your loose request ("likwid") into a fully specified plan: exact versions, exact compiler, exact options, for every package in the graph. You can read that plan before committing to it, which is what step 3.2 does.
  • The binary cache. Building everything from source would take hours. A cache holds pre-built results, so most of the graph arrives in seconds. Anything not in the cache is compiled for real — you will see both happen.

3.1 Enter the Spack environment

. /apps/spack/share/spack/setup-env.sh

3.2 Read the plan before building anything

[b] from the binary cache · [e] already on the system · - built here, from source

Before you move onFind hwloc in that list, then look at what hwloc itself depends on. One of those names should look familiar from step 1.2. Hold that thought until the Stop.

3.3 Install it — watch this one happen

Why

Go back to the XML line from step 1.2: basic. hwloc reads and writes its picture of the machine as XML, and does it properly with a library called libxml2. Its headers were not on the login node, so configure found nothing, quietly chose a smaller built-in option, and carried on. Nothing failed, and nothing said so.

Now look back at spack spec from step 3.2: libxml2 is in hwloc's graph. Spack's recipe for hwloc names that dependency, so it was built first and hwloc was built against it. You did not have to know any of that. Spack even supplied the library path you had to set by hand with LIBRARY_PATH in step 1.8 — its compiler wrapper adds one for every dependency.

That is the argument for dependency management, and it is worth more than the time it saved. A build that fails is annoying. A build that succeeds and quietly does less is the one that costs you six months later, when somebody asks why the numbers are wrong.

Why this rung exists — and what EasyBuild is

EasyBuild is the other widely used HPC software build tool, and you will meet it at European sites especially. It solves the same problem as Spack and organises it differently.

Its central idea is the toolchain: a named bundle of compiler, MPI library and mathematics libraries — foss, intel, GCCcore and so on. You choose a toolchain, and everything is built against it. A recipe is called an easyconfig, one file per package per version per toolchain.

Nothing is built in this rung — a full toolchain takes hours. You are reading the plan and comparing it with Spack's.

4.1 Load EasyBuild

module purge && module use /apps/easybuild/modules/all

  • The version and the toolchain are in EasyBuild's filename. A different version is a different file, written by somebody and reviewed.
  • Why nothing is installed here: every [ ] in EasyBuild's plan would be built first — the GCC 14.2.0 compiler itself among them. That is hours of compiling, from sources on the internet this cluster cannot reach. Spack's plan used the compiler already on the system ([e] gcc@11.5.0).
The point

Spack asked "what does this need?" EasyBuild asked "what toolchain is this for?"

Toolchain-first gives a coherent, reproducible set where everything at a site is built against the same compiler and MPI. That consistency is why large centres favour it, and why their software stacks are easy to reason about.

Graph-first gives flexibility: combine a package built today with one built last year, mix compilers, vary options per package. That is why smaller and faster-moving sites favour Spack.

Neither is wrong. They optimise for different problems, and most administrators end up able to read both.

Why this rung exists — and what a container is

Every rung so far installed software onto this cluster, against this cluster's operating system, compiler and C library. Move to a different machine and you build it again.

A container is a single file holding an entire filesystem — a whole Linux distribution, the application, and every library it needs. When you run a command "inside" it, the program sees that filesystem instead of the host's. The kernel is still the host's; everything above it is not.

Apptainer is the container runtime built for HPC. It differs from Docker in ways that matter here: an image is one ordinary file you can copy about, it runs as you rather than as root, and it does not need a daemon. It was called Singularity until 2021 — you will meet both names, same lineage.

This rung changes nothing about the cluster. Somebody built the image months ago on a different machine.

Three rungs, three versions: 5.4.1 because you chose it, 5.5.1 because Spack did, 5.2.2 because whoever built the image did. None of them is wrong. Only one of them was your decision.
The point

The image was built by somebody else, months ago, on a different machine, and it carries its own operating system and C library. That is why it behaves identically here, on a colleague's cluster, and on a laptop. For reproducing a result years later, nothing else comes close.

And what it did not solve

You cannot see inside it without going looking. You did not choose what is in it. If something in it is wrong or out of date you cannot fix it — you ask whoever built it, and wait. It may not use this cluster's network hardware or GPU drivers properly, because it does not know about them.

Every rung trades control for convenience. This one trades the most of both, which makes it excellent for a fixed, finished application and a poor choice for something you are still developing.

A colleague needs a package that exists nowhere except as a tarball on a research group's website, and needs it next week. Which rung, and why?

There is no single right answer, and that is the point. Rung 1 gets it working today and costs you every time it is rebuilt. Rung 3 costs an afternoon writing a recipe and pays back from the second install onwards. The deciding questions are how many people need it, how often it changes, and whether anyone will have to reproduce the result later.
The point of the whole lab

You climbed the ladder in one direction, once. In real work you choose a rung per package, and the higher rungs are not simply better — each one takes decisions away from you as well as work.

Rung 1 is not obsolete. It is where you end up whenever nobody has written a recipe yet, which happens constantly in research computing. The difference is that you now know what it costs, what it silently gets wrong, and what the alternatives buy you.

—Glossary
binary cache
A store of pre-built packages. Spack fetches from one instead of compiling, which turns hours into seconds.
concretization
Spack turning a loose request into a fully specified plan — exact versions, compiler and options for every package in the graph.
container · image · .sif
A single file holding a whole filesystem: an operating system, an application and its libraries. .sif is Apptainer's image format.
dependency graph · DAG
The set of packages something needs, and what those need in turn. "Directed acyclic graph" — it has a direction and no loops.
depends_on
The Lmod function that loads another module. Contrast prereq, which only checks and fails.
easyconfig
EasyBuild's recipe file. One per package, per version, per toolchain.
LD_LIBRARY_PATH
Directories searched for shared libraries when a program starts. Missing entries give cannot open shared object file.
LIBRARY_PATH
Directories the linker searches for libraries while a program is being built. Its run-time partner is LD_LIBRARY_PATH.
Lmod
The environment module system. module load applies a package's environment changes; module unload reverses them.
login node · compute node
The machine you connect to, and the separate machines that run jobs. They share filesystems, not processes.
modulefile
A small Lua file describing what one package needs added to the environment.
MODULEPATH
Directories Lmod searches for modulefiles. The same idea as PATH, for modules.
PATH
Directories the shell searches for commands. Missing entries give command not found.
prefix
The directory a package installs into. --prefix=/x puts binaries in /x/bin, libraries in /x/lib.
setgid bit
The s in drwxrwsr-x. New files inherit the directory's group rather than the creator's.
shared filesystem
Storage mounted by every node at the same path. Here, /apps and /home.
spec
Spack's description of one concrete installation — package, version, compiler, options, dependencies. Saved as JSON alongside the install.
toolchain
EasyBuild's named bundle of compiler, MPI and mathematics libraries, e.g. foss, intel, GCCcore.
