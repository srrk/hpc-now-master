—Before you startread once · 6 min

Why a cluster has five filesystems instead of one

Your laptop has one disk and every file goes on it. A cluster has several storage systems, each built for a different job, and putting a file in the wrong one is the most common cause of slow jobs and lost work.

They differ along four axes, and you will be filling in all four today:

  • Speed, and for what. A system fast at streaming one huge file can be slow at touching ten thousand small ones, and the reverse.
  • Size and quota. How much you get, and whether the limit is per user or per project.
  • Backup. Whether a copy exists elsewhere. Users assume everything is backed up. On a real cluster most of it is not.
  • Purge. Whether files are deleted automatically after a while.

Those four things together are a "tier". A tier is a contract, not a device — and today you will meet two tiers that live on exactly the same hardware and differ in every policy.

What a parallel filesystem is

Home directories here are NFS: one server holds the files and every machine mounts it. Simple, and it does not scale — one server, one bottleneck.

A parallel filesystem splits the job across machines. This cluster runs Lustre, which has three kinds of participant:

  • MDT — metadata target. Holds the directory tree: names, permissions, timestamps, and which data servers hold which parts of each file. Every file operation starts here.
  • OST — object storage target. Holds the actual file contents. There are several, and one file can be spread across them.
  • Client. Every login and compute node. It talks to the MDT to find a file and to the OSTs to read it.

That split is the whole reason for the behaviour you will measure in task 2. Reading a big file engages several OSTs at once and goes fast. Creating ten thousand small files is ten thousand conversations with the one MDT, over the network, and goes slowly.

Striping, in one paragraph

When a file is written to Lustre it is cut into pieces and spread across OSTs. How many OSTs, and how big each piece is, is the file's stripe layout. A big file spread across four OSTs can be read four times faster than one sitting on a single OST. A small file spread across four OSTs is slower than one that is not, because now four servers must be contacted instead of one.

You are not changing any striping today. Task 5 asks what you would need to know before advising someone else to.

Three ways to find out what is true

Nobody is going to tell you what the tiers are. You will work them out from three kinds of evidence, and knowing which to reach for is half the skill:

  • The system itself. findmnt, df, quota, lfs — what the machine reports about its own storage, right now.
  • What the site publishes. /opt/site/storage/ holds what this cluster tells its users. Real, and like all site documentation, incomplete.
  • Operational records. Logs and reports from the systems that actually do the work — the purge job, the backup system.

None of the three is complete on its own. That is not a flaw in this lab; it is what the job is like.

1The storage fact sheet20 min

A table with one row per filesystem and seven columns: path, backing technology, capacity, quota, backup, purge, and how you found out.

Why this task exists

When a user asks "where should I put my data?", this table is the answer. Most sites do not have one written down, which is why most users guess — and why the first thing anybody asks a new administrator is a question the administrator cannot answer either.

The backup column is the one that matters most and is hardest to find. Quota and purge are usually published. Backup status usually lives in the backup system's own records, somewhere else entirely, and is the column people forget. Watch for that as you go.

1.1 Find out what is mounted

findmnt -t nfs,nfs4,lustre,xfs,ext4 -o TARGET,SOURCE,FSTYPE,OPTIONS
df -hT | grep -v tmpfs

Two views of the same thing. findmnt tells you the type and where it comes from; df tells you how big it is and how full. Between them you have the first three columns for everything mounted here.

1.2 Read what the site publishes

cat /opt/site/storage/README
cat /opt/site/storage/policy.md
Read the policy page carefully, then check it against the machineIt is what this site tells its users. Note any column it does not cover — that gap is the point of this task.

1.8 Node-local storage

You cannot see this from the login node — ask a compute node

srun -n1 bash -c 'ls -la /local; hostname'

Check your sheet against these
  • Five rows. If you have four, you have missed the one you cannot see from the login node.
  • A backup value for every row, and at least one of them is "no".
  • Two of your rows share a filesystem. Did you notice which?
Project and scratch are the same Lustre filesystem. Same MDT, same OSTs, same capacity pool. They differ in quota, in backup and in purge — which is to say they differ in every column that matters to a user and in none that matters to the hardware. A tier is a contract, not a device. That is the single most useful idea in this session.
On the backup column

The site policy page does not state backup status at all. It lives in a separate file, written by the system that does the backing up. That is where it lives on most real clusters, and it is why the most common mistake in this task is a complete-looking fact sheet with that column blank or guessed.

Look at when the last backup ran, as well as whether one exists. A user hearing "yes, home is backed up" will assume nightly. Check whether that is what the timestamp says.

On node-local

It exists on every compute node, it is a different filesystem on each, and nothing you put there is guaranteed to survive the job. It is the only tier you cannot inspect from the login node at all, which is exactly why it gets left off fact sheets.

2Measure the difference15 min · capped

Numbers for the parallel filesystem and node-local storage, on a small-file workload and a large-file workload.

Why this task exists

Task 1 told you what the tiers are. This one shows why it matters, in numbers you measured yourself rather than numbers somebody told you.

The harness runs four things on each of two targets: create five thousand small files, stat them all, remove them all, then write and read back one large file. Small-file work is reported in files per second; large-file work in MiB per second.

Do not assume the same target wins both workloads. Which one wins each, and by how much, is the result — and how far apart those two margins are tells you where each tier belongs. Watch the ratios, not just the winners.

Submit this first and read on while it queues. Everyone gets a compute node to themselves so the measurement is not contaminated by a neighbour, which means there is a queue. The job takes about a minute once it starts.

Do not wait for itGo back to task 1, or ahead to task 3. Come back when squeue shows nothing for you.

cat $HOME/m4s1-bench/$(ls -t $HOME/m4s1-bench | head -1)

Stop · task 2read before going on
The two workloads had different winners. Now look at the two ratios.
  • Small-file: node-local won, by a factor of N. When this cluster was built, N was about 20. Write yours down.
  • Large-file: the parallel filesystem won. M is below 1 — it was about 0.25 for reading, meaning the parallel filesystem read the large file about four times faster than the local disk. It won the write too, but by how much depends on how many people were writing at the same moment: the filesystem's bandwidth is shared.
The interesting number is N ÷ M, not N or M. When this cluster was built it was about 80: the same two places to put a file, eighty times apart depending only on the shape of the work. Neither is "the fast one". Each is fast at something, and the size of the difference between the two gaps is the thing that tells you where each tier belongs. Your numbers will differ a little from these; the shape will not.
Why the two gaps differ

Small-file work is latency. Every create, stat and delete is a network round trip to a single metadata server shared by the whole cluster. Five thousand files is five thousand round trips. Node-local is a disk attached to the machine the job is on — no network, no shared server, no queue. Nothing the parallel filesystem can do closes that gap.

Large-file work is bandwidth. The parallel filesystem spreads the file across its object storage targets, behind a fast network, and moves the pieces at once. A node's local disk is one device — on this cluster a modest one, around 70 MiB/s writing and 150 reading — and nothing adds to it. For big sequential files the architecture is doing exactly what it was built for, and it wins outright.

On some clusters the local disks are fast enough to win both workloads. On this one they are not. That is exactly why you measure instead of assuming.

And what one node cannot show you

You measured with one client. The parallel filesystem exists for forty reading the same dataset at once, and its aggregate throughput rises as clients are added. A local disk serves exactly one node and does not rise at all — forty nodes need forty copies, and forty copies of a dataset nobody can share is not storage, it is forty problems.

So the trade reverses twice — once with the size of the files, which you just measured, and again with the number of nodes, which you cannot measure today. That is why the question is never "which is faster" but "faster at what, for how many". You will meet it for real the first time a user asks why their 200-node job is slow.

You should have found at least one component that is not in a normal state, and at least one target far fuller than its peers. They are not the same component. If you found both, and you can point at the file and line for each, you have read the bundle correctly.
The three things, and why they differ

A server reporting itself unhealthy is a hardware or software problem on that machine. Jobs touching its targets may hang.

A target the client cannot reach may be perfectly healthy — the problem could be the network between them, or this one client. Check whether other clients see it before concluding anything.

A target at 95% while its peers are at 50% is not a failure at all. It is an imbalance, usually caused by one very large file or by a striping choice, and lfs df reports the filesystem as full when any single target fills. Users will report "the filesystem is full" while most of it is empty.

Why inode counts matter separately

lfs df -h and lfs df -i can tell opposite stories. A filesystem with plenty of space can be completely unable to create another file because a metadata target has run out of inodes. That is a different emergency, with different symptoms, and it is why you ran both commands.

5Three questions about striping3 min

Three questions you would need answered before telling a user to change their stripe layout.

Why this task exists

Striping advice is the most commonly given and most commonly wrong piece of HPC storage guidance. "Stripe wider, it will be faster" is repeated everywhere and is false for most workloads — wider striping helps a few large files and actively harms many small ones.

The skill is not knowing the right stripe count. It is knowing that you cannot pick one without information you do not yet have, and knowing which information.

5.1 Write them

vi $HOME/course-repo/m4-s1/report.md   # section 5

Three questions. Each one should be something that, answered differently, would change your advice.

Stop · task 5read before going on
There is no fixed list, but a good set covers the shape of the data, the shape of the access, and what the change would cost. If your three questions could all be answered "it depends" without changing your advice, they are not the right three.
Things worth having asked

How big are the files, and how many? A thousand 2 MB files and one 2 TB file want opposite answers.

How are they read — one process reading one file, or many processes reading the same file at once?

Does the change apply to new files only? Striping is set when a file is created; changing a directory's layout does nothing to what is already in it, and users are routinely surprised by this.

How full is the filesystem, and how evenly? Wider striping on an unbalanced filesystem can make the imbalance worse.

—Glossary
archive
Storage for data you must keep but will rarely read. Retrieval is a request, not an instant read.
backup
A copy held elsewhere, from which files can be restored. Distinct from redundancy — RAID is not a backup.
client
Any machine that mounts the parallel filesystem. Every login and compute node here is one.
inode
The record describing one file — its name, owner, permissions and where its data lives. A filesystem can run out of these while still having free space.
lfs
The Lustre user command. lfs df, lfs quota, lfs getstripe.
Lustre
The parallel filesystem running here. Splits metadata and data across separate servers.
MDT · metadata target
Holds the directory tree. Every file operation starts here, which is why small-file work is slow on a parallel filesystem.
node-local
A disk physically attached to one compute node. Fast, private to that node, and erased when the job ends.
OST · object storage target
Holds file contents. Several per filesystem; one file can span many.
parallel filesystem
Storage spread across many servers so many clients can read and write at once.
purge
Automatic deletion of files past a certain age. Normal on scratch, and the reason scratch is not storage.
quota
A limit on space or file count. Can apply per user or per project, and the two can differ on the same filesystem.
scratch
Large, fast, not backed up, purged by age. For work in progress only.
stripe · stripe count
How many OSTs a file is spread across. Set when the file is created; changing a directory does not change existing files.
tier
A storage contract — capacity, quota, backup and purge taken together. Two tiers can share one filesystem.
