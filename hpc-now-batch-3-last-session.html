status of this draft

This is v0.9 — written before the environment was built. Every value in angle brackets — ⟨version⟩, ⟨hdf5-path⟩, ⟨head-node⟩ — is a placeholder. None of them has been observed on a real cluster yet.

The build produces VALIDATION.md, which contains the real captured output of every command below. v1.0 is this document with every placeholder replaced by a measured value. Until then, treat the shape of each output as correct and the exact strings as provisional.

Section timings are estimates too. The build records the real ones in TIMINGS.md. If a part runs long in testing, this runbook is what changes — not the clock on the day.

Part 1 of 5 · ~20 minutes

Build It

Nobody ships you a working binary. You get source, you configure it against what this machine actually has, and you build it. The awkward part is not the compiler — it is telling configure where a library lives when it is not where configure expects.

Slide anchor: Slide 8 — What an application is made of · Slide 9 — From a tarball to a running job.

Build from source The stack Library paths
1.1

Unpack the source

The tarball is already in your home directory. Unpack it and look at what you got — a source tree, a configure script, and no binary anywhere.

Commands
cd ~
tar xzf ior-⟨version⟩.tar.gz
cd ior-⟨version⟩
ls
# configure, Makefile.am, src/ — source, not software.
# Nothing here can run yet.
1.2

Configure — and tell it where HDF5 is

Configure inspects this machine and decides what it can build. HDF5 is installed, but the parallel build does not live in the default library path — it lives under a directory specific to the MPI it was built against. Configure will not find it on its own.

Install to a path on this machine for now. You will come back to that choice in Part 2.

Commands
./configure --prefix=⟨local-install⟩ --with-hdf5=⟨hdf5-path⟩
# --prefix     where the built binary will be installed
# --with-hdf5  where the parallel HDF5 library actually lives
What to look for at the end of the output
⟨configure summary — captured during build⟩
# Confirm the HDF5 line says found / enabled before you go further.
# If it does not, the build will succeed and then fail at run time —
# which is a much worse place to find out.

A library being installed and a build being able to find it are two different things. This is the single most common reason an HPC build fails, and it is why --with-… flags exist at all.

1.3

Build and install

Commands
make -j2
make install
ls ⟨local-install⟩/bin
# You now have a binary. You made it. It did not exist ten minutes ago.
1.4

Tell the machine where you put it

A binary the shell cannot find is the same as no binary. Same for the libraries it needs at run time — the linker recorded what it linked against, but the loader still has to be able to find it.

Commands
export PATH=⟨local-install⟩/bin:$PATH
export LD_LIBRARY_PATH=⟨hdf5-path⟩/lib:$LD_LIBRARY_PATH
which ior
ldd $(which ior) | grep -i hdf5
# The last command proves the binary is wired to the library you named.
# If it says "not found", the loader cannot see it — fix that now.
1.5

Run it — right here, on this machine

Four ranks, on the head node, writing to the parallel filesystem. No scheduler involved, no other machines involved. This is the smallest thing that counts as running a parallel application.

Commands
mkdir -p ⟨fsx-mount⟩/scratch/$USER
mpirun -n 4 ior -a HDF5 -w -t 1m -b 64m -o ⟨fsx-mount⟩/scratch/$USER/test.h5
Shape of the output
⟨IOR summary — captured during build⟩
access    bw(MiB/s)   ...
write     ⟨n⟩         ...
# Four ranks ran. They wrote one HDF5 file between them.
# Record the bandwidth — but see "What Is Real Here" before you
# believe the number means anything about production.

Everything so far happened on one machine. That is not what HPC is for. Part 2 is where it stops being a single-machine story.

Part 2 of 5 · ~18 minutes

Leave the Head Node — without a scheduler

A parallel application does not need a scheduler to run. It needs a process manager and a list of machines. You are going to prove that — and in doing so you will hit the most common failure in HPC operations, which is not a bug in anything.

Slide anchor: Slide 10 — What one command actually does.

Process manager Hostfile launch Software placement
2.1

Write a hostfile

A hostfile is a list of machines and how many slots each one has. That is the entire mechanism. No scheduler, no queue, no allocation — just names.

Commands
cat > ~/hosts <<'EOF'
⟨compute-node-1⟩ slots=4
⟨compute-node-2⟩ slots=4
EOF
cat ~/hosts
Confirm you can reach both, silently
ssh ⟨compute-node-1⟩ hostname
ssh ⟨compute-node-2⟩ hostname
# Both should answer immediately with no password and no host-key prompt.
# If either one prompts you, stop — mpirun will hang on that same prompt.
2.2

Launch across both machines

Eight ranks, four on each machine. Read the command carefully before you run it, because in a moment you are going to be asked what is missing from it.

Command
mpirun --hostfile ~/hosts -n 8 ⟨launcher-flags⟩ \
  ior -a HDF5 -w -t 1m -b 64m -o ⟨fsx-mount⟩/scratch/$USER/test8.h5
# ⟨launcher-flags⟩ — filled in from the build. These force the process
# manager to launch over SSH rather than handing off to the scheduler.
What actually happens
⟨error — captured during build⟩
... : error while loading shared libraries: ...
# It failed. Read the error before you read the next step.
# Which machine did it fail on? What could not be found?

Do not fix this yet. First answer the question: the command worked ten minutes ago on the head node, and nothing about the command changed. So what changed?

2.3

Work out why

Check whether the thing it is looking for exists where the ranks are actually running.

Commands
ls ⟨local-install⟩/bin        # on the head node — it is there
ssh ⟨compute-node-1⟩ ls ⟨local-install⟩/bin
# It is not there. You installed it to a path that only exists on the
# machine you were sitting on.

Nothing is broken. You built the software correctly, and you installed it correctly — to a directory that is local to one machine. The ranks on the other two machines have nothing to run. This is not a bug in MPI, in the scheduler, or in the filesystem, and every operator meets it in their first week.

2.4

Fix it the way a real site does

Do not copy the binary to every machine. Build it once, install it somewhere every machine can already see, and let them all read the same copy. That is what a shared applications directory is for — and it is why /apps exists at every facility you will ever work at.

Commands
cd ~/ior-⟨version⟩
./configure --prefix=⟨shared-apps⟩/$USER/ior --with-hdf5=⟨hdf5-path⟩
make -j2 && make install
export PATH=⟨shared-apps⟩/$USER/ior/bin:$PATH
ssh ⟨compute-node-1⟩ ls ⟨shared-apps⟩/$USER/ior/bin
# Now it is visible from there — same bytes, one copy, no distribution.

Same tarball. Same source. The only thing that changed is where the output landed.

2.5

Run it again — and check who was involved

Commands
mpirun --hostfile ~/hosts -n 8 ⟨launcher-flags⟩ \
  -x PATH -x LD_LIBRARY_PATH \
  ior -a HDF5 -w -t 1m -b 64m -o ⟨fsx-mount⟩/scratch/$USER/test8.h5
# -x exports your environment to the remote ranks. Without it they get a
# bare non-interactive shell that has never heard of your PATH.
Now — in a second terminal, while it runs
squeue
JOBID PARTITION NAME USER ST TIME NODES NODELIST(REASON)
# Empty. Eight processes are running across two machines right now,
# and the scheduler does not know this is happening.

Nothing in that command mentioned Slurm. The process manager launched the application; the scheduler was never asked. Hold on to that — Part 3 is about what the scheduler is actually for.

Part 3 of 5 · ~12 minutes

Now Hand It to the Scheduler

You have just run a parallel application across two machines without a scheduler. So what is the scheduler for? Not for launching. For deciding who gets the machines, and in what order, when more people want them than there are machines.

Slide anchor: Slide 5 — You submit it, then you leave · Slide 6 — One job, all the way through.

Batch submission Allocation Queueing
3.1

Wrap the same command in a batch script

Nothing about the application changes. You are only describing what it needs, and handing the description to something that owns the machines.

Create ~/run.sh
cat > ~/run.sh <<'EOF'
#!/bin/bash
#SBATCH --job-name=ior
#SBATCH --nodes=2
#SBATCH --ntasks=8
#SBATCH --output=%x-%j.out

export PATH=⟨shared-apps⟩/$USER/ior/bin:$PATH
export LD_LIBRARY_PATH=⟨hdf5-path⟩/lib:$LD_LIBRARY_PATH

srun ior -a HDF5 -w -t 1m -b 64m -o ⟨fsx-mount⟩/scratch/$USER/batch.h5
EOF
chmod +x ~/run.sh
# No hostfile. You did not name a single machine — you said "two nodes".
3.2

Submit it and walk away

Commands
sbatch ~/run.sh
Submitted batch job ⟨jobid⟩
# That returned instantly. Nothing is waiting for you.
squeue -u $USER
cat ior-⟨jobid⟩.out
# Same application. Same ranks. Same output. Different route.
3.3

Now ask for more than exists

This is the whole point of the part. There are two machines. Submit three jobs that each want both of them.

Commands
sbatch ~/run.sh; sbatch ~/run.sh; sbatch ~/run.sh
squeue
What you will see
JOBID  NAME  USER   ST  TIME  NODES  NODELIST(REASON)
⟨id1⟩  ior   yogi   R   0:04      2  ⟨node1⟩,⟨node2⟩
⟨id2⟩  ior   yogi   PD  0:00      2  (Resources)
⟨id3⟩  ior   yogi   PD  0:00      2  (Resources)
# One running. Two pending — and the reason is stated: Resources.
# Not "busy". Not "slow". The machines are taken.

A job does not share a node with another job. It reserves the machines and holds them until it exits. That is why there is a queue at all — and managing that queue fairly, across many users, is the entire job of the scheduler. It never had anything to do with launching your processes.

Part 4 of 5 · ~18 minutes

One File, or Many

Eight ranks have the same data to write. There are two ways to put it on disk, the application chooses which, and you live with the consequence. Same bytes both ways — and two completely different problems for your filesystem.

Slide anchor: Slide 11 — Everyone gets a file, or everyone shares one · Slide 12 — Which meter moved.

File per process Shared file Metadata vs bandwidth

This part is assessed. At the end you write one short paragraph: which meter moved, and why. Not which was faster — which meter moved.

4.1

Take a baseline of both meters

Two numbers, before you write anything. Space, and inodes. You will read both again afterwards.

Commands
mkdir -p ⟨fsx-mount⟩/scratch/$USER/patterns
lfs df -h  ⟨fsx-mount⟩
lfs df -i  ⟨fsx-mount⟩
# -h  bytes.   -i  inodes — the count of files, not their size.
# Write both down. They move independently.
4.2

Pattern one — a file per rank

Command
sbatch --wrap="srun ior -a POSIX -F -w -t 1m -b 64m \
  -o ⟨fsx-mount⟩/scratch/$USER/patterns/fpp" --nodes=2 --ntasks=8
# -F  file per process: each rank opens and writes its own file
Then count what landed
ls ⟨fsx-mount⟩/scratch/$USER/patterns/ | wc -l
lfs df -i ⟨fsx-mount⟩
# How many files? How far did the inode number move?
4.3

Pattern two — one shared file

Command
sbatch --wrap="srun ior -a HDF5 -w -t 1m -b 64m \
  -o ⟨fsx-mount⟩/scratch/$USER/patterns/shared.h5" --nodes=2 --ntasks=8
# No -F. All eight ranks write regions of ONE file, at the same time.
# That is only possible because HDF5 is doing the coordination.
Then count again
ls -l ⟨fsx-mount⟩/scratch/$USER/patterns/shared.h5
lfs df -h ⟨fsx-mount⟩
lfs df -i ⟨fsx-mount⟩
# One file. Same bytes as before. Where did the inode number go?

Eight ranks. Same data. One pattern produced eight files, the other produced one. The byte totals match. That difference is the entire part.

4.5

Write it up — assessed

One short paragraph. Answer three things, in your own words.

1 · Which meter moved for each pattern, and which one barely moved at all.

2 · You ran this at eight ranks. Scale it in your head to a thousand. What does each pattern do to the filesystem then?

3 · A researcher asks which one they should use. What do you need to know before you can answer?

There is no correct pattern. There is a correct question, and it is about how many ranks and how many files — not about which one is faster on a two-node cluster.

Part 5 of 5 · ~12 minutes

Make the Shared File Faster

The application chose to write one shared file. You cannot change that, and you should not want to. But where that file lives on the storage is yours — and it is the difference between one target doing all the work and all of them sharing it.

Slide anchor: Slide 13 — The application chose the pattern, you choose the layout.

Stripe count Layout inheritance The handback
5.1

Look at where the shared file actually lives

Command
lfs getstripe ⟨fsx-mount⟩/scratch/$USER/patterns/shared.h5
What to look for
lmm_stripe_count:  ⟨n⟩
	obdidx		 objid
	     ⟨n⟩	      ...
# How many object targets is this file spread across?
# Eight ranks wrote it — but how many targets received the bytes?
5.2

Change the layout and write it again

Set the stripe count on a new directory, then write the same file into it. Layout is inherited at creation — an existing file is never restriped by changing a directory.

Commands
mkdir -p ⟨fsx-mount⟩/scratch/$USER/wide
lfs setstripe -c 2 ⟨fsx-mount⟩/scratch/$USER/wide
lfs getstripe -d ⟨fsx-mount⟩/scratch/$USER/wide
sbatch --wrap="srun ior -a HDF5 -w -t 1m -b 64m \
  -o ⟨fsx-mount⟩/scratch/$USER/wide/shared.h5" --nodes=2 --ntasks=8
Then compare
lfs getstripe ⟨fsx-mount⟩/scratch/$USER/wide/shared.h5
# Now how many obdidx rows? Compare the bandwidth to 5.1.

The application did not change. The ranks did not change. The command did not change. You changed where the file lives — and that is the whole of the storage module, arriving from the other direction.

5.3

Record the comparison

On the size of the difference. This cluster has two object targets and a modest network path. The improvement will be real but small — on a production filesystem with many targets and a proper fabric it is a different order of magnitude entirely. The direction is the lesson; the magnitude is bottlenecked by the machine you are on.

instructor interventions

Traps a learner will hit on this cluster with this runbook. Each one names the moment to step in and exactly what to say — and, in two cases, what not to say.

Rajesh → learner Trap · "configure says it cannot find HDF5 — but you said it was installed"
WherePart 1.2 — learner omits --with-hdf5, or points at the wrong path
FixBoth statements are true. It is installed — under a directory specific to the MPI it was built against, not in the default library path. Have them run the ls ⟨hdf5-path⟩ from orientation again and pass that path.
TeachInstalled and findable are different properties. This is why every serious build system has --with-… flags, and why HPC sites run environment modules.
Rajesh → learner Trap · "it failed on the compute nodes — is the cluster broken?"
WherePart 2.2 — this is the designed moment. Do not shortcut it.
Do not say"You installed it to a local path." That is the answer, and they should reach it.
Say insteadOne question: "the command has not changed — so what has?" If that does not land, a second: "go and look for the binary on the machine it failed on."
Teach"It works when I run it here and fails when it runs there" is one of the most common tickets at any site. They should meet it once, in a room, with someone who can explain it.
Rajesh → learner Trap · "I installed it to shared storage and it STILL fails on the remote nodes"
WherePart 2.5 — learner omits the -x PATH -x LD_LIBRARY_PATH flags
FixThe binary is visible now, but the remote ranks start in a bare non-interactive shell that never read their profile — so PATH and LD_LIBRARY_PATH are not what they are on the head node. -x exports them to the launched processes.
TeachTwo separate things have to travel to the remote machine: the software, and the environment that finds it. Fixing one does not fix the other — and this is why batch scripts set their environment explicitly rather than relying on a login shell.
Rajesh → learner Trap · "squeue shows a job during my hostfile run"
WherePart 2.5 — the process manager handed off to the scheduler instead of using SSH
FixCheck ⟨launcher-flags⟩ is present and correct. Without it the launcher detects a scheduler and prefers it — which silently defeats the entire point of the part.
TeachWorth saying aloud even when it works: the launcher had a choice, and on a production cluster it usually makes the scheduler-aware one. We are forcing the other path today to show the two jobs are separable.
Rajesh → learner Trap · "the shared file was slower — so file-per-process is better?"
WherePart 4.4 / 4.5 — learner ranks the patterns on bandwidth alone
FixAt eight ranks, on two targets, that may well be true — and it is the wrong axis. Ask: "you created eight files. What is that number at a thousand ranks, and what has to create them?"
TeachThe pattern that wins on a laptop-sized run is the one that takes a metadata service down at scale. The assessed answer is about which meter moves, not which number was bigger today.
Rajesh → learner Trap · "I set the stripe count but the old file did not change"
WherePart 5.2 — learner runs setstripe on the existing directory and re-checks the old file
FixLayout is set at file creation and never retroactively. A directory's stripe setting only affects files created after it. The runbook uses a fresh directory for exactly this reason.
TeachA researcher who fixes their layout mid-project has fixed nothing for the data already written. They have to re-run, or copy. Tell them that before they celebrate.
