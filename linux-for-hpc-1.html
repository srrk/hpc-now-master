how to use this runbook

This is the first lab runbook for Linux for HPC. The Linux Fluency series ended at Lab 17. This runbook opens at Lab 18 and runs through Lab 20 — the three labs for Day 1 of Linux for HPC.

The depth shifts here. Linux Fluency was operational fluency — enough to operate a Linux host. Linux for HPC is reading fluency at the depth HPC operations requires. The exercises involve reading /proc entries, observing process state at thread level, sending signals, and interrogating resource limits across both enforcement layers. Every command is copy-pasteable. Compare output to Expected Output blocks — the interpretation matters as much as the command.

D-state is the theme of Section 18. Most exercises involve reading live process state from /proc. On a healthy lab instance you will not encounter genuine D-state processes — the exercises build the reading habits so the technique is available when D-state does appear in production.

Lab 18 / 20 · 20 minutes · Processes and /proc

Process States, Threads, Memory, File Descriptors

Follows: fork/exec/wait, process trees, R/S/D/T/Z states, ps -eLf threads, sessions, /proc as virtual filesystem, system-level entries, per-process entries including status, cmdline, environ, fd/, and stack.

Ex 1

Read the process table — identify states R, S, and Z

Run ps aux and read the STAT column. Find at least one process in S state (most processes) and at least one in R state (active). Check for Z state — any zombies on the system.

ps aux | awk '{print $8}' | sort | uniq -c | sort -rn
Expected output
Count of each STAT value. S and Ss dominate — sleeping daemons.
R or R+ may appear briefly. Z should be zero on a healthy system.

If Z appears: ps aux | awk '$8 == "Z" {print $1, $2, $11}'
to identify which process is the zombie and who its parent is.
Find D-state processes — should be empty on a healthy system
ps aux | awk '$8 == "D" {print $2, $11}'
echo "D-state count: $(ps aux | awk '$8 == "D"' | wc -l)"

On a healthy lab instance D-state count should be zero. If it is non-zero, read /proc/<pid>/wchan for each — this tells you what kernel subsystem the process is blocked in.

Ex 2

Read threads with ps -eLf — count threads in sshd

SSHD_PID=$(pgrep -o sshd)
echo "sshd main PID: $SSHD_PID"
ps -eLf | grep "^\S* \+${SSHD_PID} " | head -10
Expected output — read each column
UID     PID   PPID   LWP  C NLWP STIME CMD
root   1234      1  1234  0    1 Jan05 sshd: /usr/sbin/sshd -D

PID = process ID (shared by all threads of the same process)
LWP = Light Weight Process ID (thread ID — unique per thread)
NLWP = total thread count for this process
Multiple rows with the same PID = multiple threads
Check thread state individually via /proc/pid/task/
ls /proc/${SSHD_PID}/task/          # one directory per thread
for tid in /proc/${SSHD_PID}/task/*/; do
    state=$(awk '/^State:/{print $2, $3}' ${tid}/status 2>/dev/null)
    tid_num=$(basename $tid)
    echo "thread $tid_num: $state"
done
Expected output
thread 1234: S (sleeping)

Each thread has its own kernel state. A multithreaded process
can have some threads R, some S, some D simultaneously.
A thread stuck in D while others continue = confusing daemon symptoms.
Ex 3

Read /proc/meminfo — record MemFree vs MemAvailable

cat /proc/meminfo | grep -E 'MemTotal|MemFree|MemAvailable|^Cached:|Buffers|HugePages'
Expected output — read the distinction
MemTotal:       xxx kB   ← physical RAM installed
MemFree:        xxx kB   ← genuinely unused — usually small, that is correct
MemAvailable:   xxx kB   ← available for new allocations — includes reclaimable cache
Buffers:        xxx kB   ← filesystem metadata cache
Cached:         xxx kB   ← page cache — recently read/written file data
HugePages_Total: xxx     ← for MPI/IB memory registration

MemFree being small is NOT a problem.
MemAvailable being near zero IS a problem.
These are different questions about different things.

Record the values. Calculate: MemFree + Cached ≈ MemAvailable (approximately). The Cached field is what A5/T37 reads before and after dd with and without oflag=direct to demonstrate the page cache effect.

Ex 4

Read /proc/<pid>/status for a running daemon

SSHD_PID=$(pgrep -o sshd)
cat /proc/${SSHD_PID}/status
Expected output — read each field
Name:   sshd
State:  S (sleeping)       ← current kernel state
Pid:    1234
PPid:   1                  ← parent is systemd (PID 1)
TracerPid: 0               ← non-zero means strace/gdb is attached
Uid:    0 0 0 0            ← real, effective, saved, filesystem UIDs
VmPeak: xxxx kB            ← peak virtual memory size
VmRSS:   xxx kB            ← physical memory actually mapped NOW
Threads: 1                 ← thread count
voluntary_ctxt_switches: xxx    ← switched because it was done
nonvoluntary_ctxt_switches: xx  ← switched because it was preempted

VmRSS is the process's current physical memory footprint — what it has actually touched and had mapped to physical RAM. This is exactly what sacct's MaxRSS field captures for a completed Slurm job. A job that requests 16 GB but has a VmRSS peak of 4 GB is over-allocated.

Ex 5

Read /proc/<pid>/cmdline — make it readable

SSHD_PID=$(pgrep -o sshd)
tr '\0' ' ' < /proc/${SSHD_PID}/cmdline; echo
Expected output
sshd: /usr/sbin/sshd -D [listener] 0 of 10-100 startups

The cmdline entry is null-byte-delimited — tr converts to readable.
This is the exact binary and arguments at exec time.
Useful when ps truncates long command lines.
Compare to what systemctl cat shows
systemctl cat sshd | grep ExecStart

The cmdline from /proc and the ExecStart from the unit file should correspond. If they differ, the daemon was started differently than its unit file specifies — useful when debugging why a daemon has unexpected behaviour.

Ex 6

List /proc/<pid>/fd/ — count open file descriptors

SSHD_PID=$(pgrep -o sshd)
sudo ls -la /proc/${SSHD_PID}/fd/
Expected output
lrwxrwxrwx 1 root root 64 ... 0 -> /dev/null
lrwxrwxrwx 1 root root 64 ... 1 -> /dev/null
lrwxrwxrwx 1 root root 64 ... 2 -> /dev/null
lrwxrwxrwx 1 root root 64 ... 3 -> socket:[xxxxx]
lrwxrwxrwx 1 root root 64 ... 4 -> socket:[xxxxx]

FD 0/1/2 = stdin/stdout/stderr — /dev/null means the daemon
has no terminal attached, correct for a systemd-managed service.
FD 3+ = open files, sockets, pipes.

Count total open FDs:
sudo ls /proc/${SSHD_PID}/fd/ | wc -l

When a filesystem unmount fails with "device or resource busy," something has an open FD into it. lsof +D /mountpoint finds the holder. The FD entry in /proc is what lsof is reading.

Ex 7

Read /proc/<pid>/wchan for two different processes

for name in sshd chronyd; do
    pid=$(pgrep -o $name 2>/dev/null) || continue
    wchan=$(cat /proc/${pid}/wchan 2>/dev/null)
    echo "${name} (PID ${pid}): ${wchan}"
done
Expected output
sshd (PID 1234): poll_schedule_timeout
chronyd (PID 876): hrtimer_nanosleep

Each name is the kernel function the process is currently blocked in.
poll_schedule_timeout = waiting for network I/O (correct for sshd)
hrtimer_nanosleep = sleeping on a timer (correct for chronyd)

For a D-state process this would show the blocked subsystem:
nfs_wait_bit_killable = blocked on NFS
ldlm_lock_enqueue = blocked on Lustre
Checkpoint — Section 18 Type done in chat when this passes
awk '/^VmRSS/{print}' /proc/$(pgrep -o sshd)/status && echo "Section 18 complete"
Expected: VmRSS: <number> kB followed by Section 18 complete. This is the physical memory footprint of sshd — the same field sacct reports as MaxRSS for completed Slurm jobs.

Lab 19 / 20 · 15 minutes · Signals and lsof

Signal Delivery, Handlers, and File Descriptor Inspection

Follows: the signal table, SIGTERM/SIGKILL/SIGHUP/SIGCHLD operational use, why SIGKILL does not reach D-state processes, signal handlers at awareness level, lsof for open file inspection and unmount diagnosis.

Ex 1

Send SIGTERM to a test process — confirm clean exit. Send SIGHUP to sshd.

SIGTERM — polite termination
sleep 300 &
TESTPID=$!
echo "Test PID: $TESTPID"
ps -f -p $TESTPID                         # confirm it is running
kill $TESTPID                               # send SIGTERM (default)
sleep 1
ps -f -p $TESTPID 2>/dev/null || echo "Process exited cleanly"
Expected output
Process exited cleanly

sleep has no SIGTERM handler — it takes the default action (terminate).
A well-written daemon would complete in-flight work before exiting.
SIGHUP — reload without restart
SSHD_PID=$(pgrep -o sshd)
sudo kill -HUP $SSHD_PID                   # send SIGHUP
journalctl -u sshd -n 5 --no-pager
Expected output — sshd journal
... sshd[1234]: Received SIGHUP; restarting.
... sshd[1234]: Server listening on 0.0.0.0 port 22.

Your session remains active. SIGHUP reloaded the listener config
without terminating existing authenticated connections.
This is the daemon reload convention — not universal, verify per daemon.
Ex 2

Send SIGUSR1 to chronyd — observe how it interprets it

sudo kill -USR1 $(pgrep chronyd)
journalctl -u chronyd -n 10 --no-pager
Expected output
chronyd logs its interpretation of SIGUSR1 — typically a statistics
dump or a log level change depending on the version.

SIGUSR1 and SIGUSR2 have no fixed meaning — each daemon assigns its own.
This is why you verify what a daemon does with a signal before sending it.
Ex 3

SIGSTOP and SIGCONT — pause and resume a process, observe T state

sleep 300 &
TESTPID=$!
kill -STOP $TESTPID                         # send SIGSTOP — cannot be caught
ps aux | awk -v p=$TESTPID '$2==p {print $8, $11}'
Expected output
T sleep

State T = stopped. The process is not running and will not run
until it receives SIGCONT. SIGKILL does not resume it — only SIGCONT.
Unexpected T state on a compute node can contribute to CG hangs.
kill -CONT $TESTPID                          # resume
ps aux | awk -v p=$TESTPID '$2==p {print $8, $11}'
kill $TESTPID                               # clean up
Expected output after SIGCONT
S sleep

Back to S (sleeping). The process resumed and returned to waiting.
SIGSTOP/SIGCONT are uncatchable — unlike SIGTSTP (Ctrl-Z) which can be caught.
Ex 4

Use lsof -p to inspect a daemon's open files

sudo lsof -p $(pgrep -o sshd) 2>/dev/null | head -20
Expected output — read each column
COMMAND  PID USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
sshd    1234 root  cwd    DIR    8,1     4096    2 /
sshd    1234 root  txt    REG    8,1   902736 xxx /usr/sbin/sshd
sshd    1234 root  mem    REG    8,1  xxxxxx  xxx /lib64/libcrypto.so.x
sshd    1234 root    0r   CHR    1,3      0t0   5 /dev/null
sshd    1234 root    1w   CHR    1,3      0t0   5 /dev/null
sshd    1234 root    3u  IPv4 xxxxx      0t0  TCP *:ssh (LISTEN)

FD column: cwd=working dir · txt=executable · mem=memory-mapped lib
           0r/1w/2w=stdin/stdout/stderr · numbers=open file descriptors
TYPE: REG=file · DIR=directory · CHR=character device · IPv4=socket

The mem entries are shared libraries mapped into the process — this is how you identify which library versions a running process is actually using, which matters for diagnosing library version conflicts in A2.

Ex 5

Use lsof +D on a mounted filesystem

This exercise identifies which processes have open file descriptors into a filesystem — the technique used when a filesystem unmount fails with "device or resource busy."

df -h | grep -v tmpfs | head -5           # pick a real mounted filesystem
MOUNTPOINT=$(df --output=target / | tail -1)
sudo lsof +D $MOUNTPOINT 2>/dev/null | head -15
Expected output
COMMAND    PID   USER   FD   TYPE DEVICE SIZE/OFF  NODE NAME
systemd      1   root  cwd    DIR    8,1     4096     2 /
systemd      1   root  txt    REG    8,1  xxxxxxx  xxxx /usr/lib/systemd/systemd
sshd      1234   root  cwd    DIR    8,1     4096     2 /
...

Every process with an open FD into this filesystem is listed.
This is why unmounting / always fails — everything uses it.
lsof +D /mnt/specific_mount would show only users of that mount.

In A6, Lustre client unmount failures are diagnosed with exactly this command — lsof +D /lus/<mountpoint>. The holders must either close their FDs or be terminated before the unmount will succeed.

Ex 6

Read /proc/<pid>/stack — identify the kernel wait channel

This is the definitive D-state diagnostic tool. On a healthy system all processes will show sleep-related kernel functions. Read the top frame and identify the subsystem.

for name in sshd chronyd; do
    pid=$(pgrep -o $name 2>/dev/null) || continue
    echo "=== $name (PID $pid) ==="
    sudo cat /proc/${pid}/stack 2>/dev/null | head -5
    echo
done
Expected output
=== sshd (PID 1234) ===
[<0>] poll_schedule_timeout+0x4e/0x80
[<0>] do_select+0x6b1/0x790
...

=== chronyd (PID 876) ===
[<0>] hrtimer_nanosleep+0xec/0x1d0
...

Top frame identifies the kernel subsystem:
poll_schedule_timeout → waiting for I/O events (sshd listening)
hrtimer_nanosleep → sleeping on a timer (chronyd between polls)
nfs_wait_bit_killable → blocked on NFS (D-state diagnostic)
lustre_* or ldlm_* → blocked on Lustre (D-state diagnostic)

In A4 T36, when a Slurm node is stuck in CG state, sudo cat /proc/<pid>/stack on the stuck process is step three of the recovery procedure — after identifying the process with ps -eLf and reading wchan.

Checkpoint — Section 19 Type done in chat when this passes
kill -0 $(pgrep -o sshd) && echo "sshd is running" && echo "Section 19 complete"
kill -0 sends no signal — it only checks whether the process exists and is signalable. Exit code 0 means the process exists. This is how scripts check whether a daemon is alive without affecting it.

Lab 20 / 20 · 10 minutes · Resource Limits

Reading Limits and the Two-Layer Model

Follows: soft and hard limits, nofile/memlock/nproc/stack and their HPC rationale, /etc/security/limits.conf enforced via PAM for login sessions, systemd unit file limits for daemons, why both must be configured independently.

Ex 1

Read your login session's current limits

ulimit -a
Expected output — read the four that matter
open files                      (-n) 1024
max locked memory           (kbytes, -l) 64
max user processes              (-u) xxxx
stack size              (kbytes, -s) 8192

nofile (open files): default 1024 — too low for MPI at scale
memlock (locked memory): 64 kB — too low for InfiniBand RDMA
nproc: varies — too low if many parallel jobs
stack: 8192 kB (8 MB) — too low for some Fortran codes
Check hard limits — the ceiling without root
ulimit -Hn                          # nofile hard limit
ulimit -Hl                          # memlock hard limit
ulimit -Hu                          # nproc hard limit

The soft limit is what is currently enforced. The hard limit is the ceiling a non-root user can raise the soft limit to. On this lab instance both may be low — a properly configured HPC cluster has these set to 65536/unlimited in /etc/security/limits.conf.

Ex 2

Read the actual limits enforced on a running daemon via /proc

This is the definitive way to check what limits a daemon is actually running under — regardless of what limits.conf says.

SSHD_PID=$(pgrep -o sshd)
cat /proc/${SSHD_PID}/limits
Expected output
Limit                     Soft Limit   Hard Limit   Units
Max cpu time              unlimited    unlimited    seconds
Max file size             unlimited    unlimited    bytes
Max data size             unlimited    unlimited    bytes
Max stack size            8388608      unlimited    bytes
Max core file size        0            unlimited    bytes
Max resident set          unlimited    unlimited    bytes
Max processes             xxx          xxx          processes
Max open files            1024         4096         files
Max locked memory         65536        65536        bytes
...

Max open files = 1024 — this is what sshd can actually open.
This comes from sshd's systemd unit file, not from limits.conf.
limits.conf does NOT apply to systemd-managed services.

The two-layer model in action. Your login session's ulimit -n shows one number. /proc/$(pgrep -o sshd)/limits may show a different number for sshd. They are independent. limits.conf applies to login sessions via PAM. Systemd unit file LimitNOFILE= applies to the daemon. Both must be configured separately.

Ex 3

Read /etc/security/limits.conf and limits.d/

grep -v '^#' /etc/security/limits.conf | grep -v '^$'
ls /etc/security/limits.d/ 2>/dev/null && \
  grep -v '^#' /etc/security/limits.d/*.conf 2>/dev/null | grep -v '^$'
Expected output — may be empty on a minimal instance
On a minimal cloud instance: no entries (all defaults apply).
On a configured HPC system:
*  soft  nofile   65536
*  hard  nofile   65536
*  soft  memlock  unlimited
*  hard  memlock  unlimited

The * domain applies to all users.
@groupname targets a specific group.
These limits apply to SSH login sessions — not to systemd services.
Ex 4

Check for systemd drop-in limits on sshd or chronyd

systemctl cat sshd | grep -i 'Limit'
ls /etc/systemd/system/sshd.service.d/ 2>/dev/null || echo "No drop-ins"
systemctl show sshd --property=LimitNOFILE
Expected output
LimitNOFILE=infinity

Or if not set in the unit file:
LimitNOFILE=1024:4096   ← soft:hard from systemd defaults

systemctl show --property=LimitNOFILE shows the effective limit
that systemd applied when starting the service.
Compare this to /proc/$(pgrep -o sshd)/limits Max open files.

To raise the limit for a daemon, create a drop-in: /etc/systemd/system/sshd.service.d/limits.conf with [Service] and LimitNOFILE=65536. Then systemctl daemon-reload && systemctl restart sshd. This is separate from and does not affect /etc/security/limits.conf.

Ex 5

Explain why the daemon's limit may differ from your session's limit

Read the two values and write a one-sentence explanation of why they can differ.

echo "Login session nofile: $(ulimit -n)"
echo "sshd daemon nofile:   $(awk '/Max open files/{print $4}' \
  /proc/$(pgrep -o sshd)/limits)"
Expected output
Login session nofile: 1024
sshd daemon nofile:   1024

Or with a configured system:
Login session nofile: 65536
sshd daemon nofile:   65536

The values may be the same or different depending on whether
limits.conf and the systemd unit file have both been configured.
A site that only configures limits.conf will find its daemons
still running at default limits — the two layers are independent.
Checkpoint — Section 20 Type done in chat when this passes
cat /proc/$(pgrep -o sshd)/limits | grep 'Max open files' && echo "Section 20 complete"
Expected: a line showing the actual Max open files limit enforced on sshd, followed by Section 20 complete. Compare the number to your session's ulimit -n — they may differ because limits.conf and systemd unit files are independent enforcement layers.
