before you start

This runbook covers one session on a single AWS EC2 instance. Lab 1 you run yourself, from your own shell, with read-only access to a live provisioning server. Lab 2 is driven from the front of the room on the same server — follow along, but do not run its commands.

Every exercise is self-contained. Expected Output blocks show the structure of correct output; build identifiers, timestamps and byte counts will differ from what is printed here. The interpretation matters more than the exact strings.

Cost warning. The m5.2xlarge instance runs at approximately $0.38/hr. Run ./destroy.sh at the end of the lab day. An idle instance left over a weekend costs roughly $28.

how to connect

One hop, password authentication. You land in your own home directory on the provisioning server itself.

ssh <username>@mylab.hpc.now
# password: hpcnow2026

Your account is read-only against the provisioning tooling. You can inspect every object on this server — nodes, profiles, images, overlays, logs — and you cannot change any of them. That is deliberate: fourteen people editing one fleet image at once would produce a lesson about collisions rather than about provisioning.

sudo wwctl is permitted for the read subcommands listed in the command reference and refused for everything else. If a command is refused, that is the boundary working, not a broken environment.

what is on this box

This single instance is the whole cluster. It is the provisioning server: it hands out addresses, serves the boot files, holds the fleet image, exports the shared filesystem, and runs the scheduler that decides which nodes are eligible for work.

Two compute nodes, cn01 and cn02, run as virtual machines on this same box, on an internal network that has no route to the outside. They are not simulated. They power on with nothing, acquire an address by DHCP, fetch a bootloader, pull a kernel and a root image over the network, have host-specific files written over that image, and register with the scheduler. That chain is the subject of the session.

Neither node has a disk. Run lsblk on either one and there is nothing to mount.

the estate at a glance
host
mylab.hpc.now — provisioning server, boot server, NFS, scheduler controller
cn01
diskless compute node — IN SERVICE, do not disturb
cn02
diskless compute node — sandbox, reprovision target
internal net
10.31.0.0/24 — DHCP and network boot live here, no route out
image
rocky9 — one image, both nodes, held on this server

This server is not fresh out of the box. It has accumulated the sediment a real one does: more than one profile, a node record for hardware that no longer exists, an overlay entry someone commented out and never removed, and boot logs going back several days.

That is deliberate. A system with exactly one of everything makes attribute tracing trivial, because there is only one candidate answer. A system with history makes it real work.

There is no service processor here. On a real floor you power a node with ipmitool against its BMC — out of band, independent of whether the node's own operating system is alive. This estate has hpcops-power, which does the same job through the layer underneath these machines. Worth holding on to: the first node you meet that has stopped answering entirely is the one that teaches you why out-of-band power exists.

Lab 1 — hands on, everyone
Provisioning Server Tour
Establish, for certain rather than by assumption, where each property of a running node actually comes from.

You have been handed access to a provisioning server you did not build and told nothing about its history. Before anyone can safely change a fleet like this, they need to know which file or object is the real source of truth for each attribute of a running node — and whether changing it needs a reboot or a full image rebuild.

Eight exercises, then a trace file to complete and a self-check to run. Nothing in this lab changes anything; if a command you try is refused, you have found the read-only boundary.

Ex 1

List the node objects — then count what is actually running

wwctl node list reads a database. It tells you what this server believes exists. It does not check whether any of it is powered on.

sudo wwctl node list
sinfo -N
Expected output — note the row count
NODE NAME  PROFILES  NETWORK
cn01       compute   default:10.31.0.11
cn02       compute   default:10.31.0.12
cn07       compute   default:10.31.0.17

NODELIST  NODES PARTITION STATE
cn01          1  compute* idle
cn02          1  compute* idle

Three node objects. Two running machines. cn07 is a record for hardware that left the rack and took its reservation with it. Nothing on this server will ever tell you that unprompted — you have to notice.

Ex 2

Resolve one node fully — the difference between --long and --all

A node's own record holds very little. Most of what it is comes from the profiles it inherits. Only one of these two flags shows you the resolved result.

sudo wwctl node list cn01 --long
sudo wwctl node list cn01 --all
Expected output — the --all view, abridged
NODE  FIELD              PROFILE   VALUE
cn01  Profiles           --        compute
cn01  Kernel.Args        default   quiet crashkernel=no vga=791
cn01  ContainerName      compute   rocky9
cn01  SystemOverlay      default   site-system
cn01  RuntimeOverlay     default   site-runtime
cn01  NetDevs[default]   --        10.31.0.11
cn01  Ipmi.Ipaddr        --        (unset)

The PROFILE column is the answer to "where did this come from".
A value marked "--" was set on the node itself.

--long widens the table. --all resolves inheritance and shows you which profile each value arrived from. Only the second one answers today's question.

Ex 3

Walk the profile chain, and find the one assigned to nothing

Profiles inherit. The effective configuration of a node is the resolved chain, not any single file. There is more than one profile on this system and they are not all in use.

sudo wwctl profile list
sudo wwctl profile list compute --all
sudo wwctl profile list compute-legacy --all
Expected output — compare the two compute profiles
PROFILE NAME
default
compute
compute-legacy

compute         Kernel.Args     quiet crashkernel=no vga=791
compute         ContainerName   rocky9

compute-legacy  Kernel.Args     quiet crashkernel=no console=ttyS0
compute-legacy  ContainerName   rocky8

Two settings differ. No node references compute-legacy.

A profile that is defined but assigned to nothing is the residue of a hardware refresh that was never cleaned up. Decide for yourself whether you would delete it or leave it, and be able to say why.

Ex 4

Inspect the image — and note its build identifier

One image serves both nodes. It carries the kernel and the entire package set. Nothing host-specific is in it, and that distinction is the whole basis of the model.

sudo wwctl container list
sudo wwctl container exec rocky9 /bin/sh -c "rpm -qa | wc -l"
Expected output
CONTAINER NAME  NODES  KERNEL VERSION      SIZE
rocky9          2      5.14.0-503.el9      1.4 GiB

412

Write down the kernel version and the size. In Lab 2 you will watch both of them change, and the size delta is the thing that has to cross the network to every node in a real fleet.

Ex 5

The two overlays — written once, versus written at every boot

Anything that differs per node cannot live in a shared image. It is written over the image after the image is fetched, by one of two overlays with different lifetimes.

sudo wwctl overlay list
sudo wwctl overlay show site-system /etc/passwd.ww --render cn01
sudo wwctl overlay show site-runtime /etc/fstab.ww --render cn01
Expected output — the rendered fstab, note line 3
10.31.0.1:/home       /home    nfs  defaults  0 0
tmpfs                 /tmp     tmpfs defaults 0 0
# 10.31.0.1:/exports/proj-cfd  /proj  nfs defaults 0 0   # commented 11 Aug, reinstate?

The user accounts on a running node come from the SYSTEM overlay.
They are not in the image, and there is no directory service here.

A commented-out mount with a date and a question mark is somebody's unfinished change. It is also the exact line Lab 2 will reinstate — watch for it.

Ex 6

Ask the node itself — and confirm it has no disk

Everything so far has been the server's view. Now get the node's own view and reconcile the two. If they disagree, the node is right and the database is stale.

ssh cn01 lsblk
ssh cn01 uname -r
ssh cn01 findmnt -t nfs4,tmpfs,rootfs
ssh cn01 "getent passwd | tail -4"
Expected output — lsblk returns nothing at all
(no output from lsblk)

5.14.0-503.el9.x86_64

TARGET  SOURCE              FSTYPE  OPTIONS
/       rootfs              rootfs  rw
/home   10.31.0.1:/home     nfs4    rw,relatime
/tmp    tmpfs               tmpfs   rw

asamuel:x:4001:6100::/home/asamuel:/bin/bash
rmirza:x:4002:6100::/home/rmirza:/bin/bash

The root filesystem is rootfs — it is in memory. Power this node off and everything written outside /home ceases to exist. That is not a failure mode, it is the design.

Ex 7

Find where the address came from, and read the evidence of past boots

A stateless node has no address until something gives it one. That transaction is logged, and the log is the first place any provisioning fault is diagnosed.

sudo grep -A3 'host cn01' /etc/dhcp/dhcpd.conf
sudo journalctl -u dnsmasq --since '5 days ago' | grep -Ei 'DHCPACK|tftp|no address'
Expected output — five days of boots, one of them failed
host cn01 {
  hardware ethernet 52:54:00:07:00:01;
  fixed-address 10.31.0.11;
}

Aug 24 03:11:07 DHCPACK(virbr1) 10.31.0.11 52:54:00:07:00:01 cn01
Aug 24 03:11:09 sent /var/lib/tftpboot/undionly.kpxe to 10.31.0.11
Aug 26 22:40:52 DHCPACK(virbr1) 10.31.0.12 52:54:00:07:00:02 cn02
Aug 27 01:15:33 no address available for 52:54:00:07:00:07

The last line is a machine asking for an address it will never get.
Match that hardware address against the node objects from Ex 1.

The failed request belongs to cn07. A record that outlived its hardware still holds a reservation, and something on the network is still asking for it. Both halves of that are worth explaining out loud.

Ex 8

Find the terminus — a node that boots but never registers runs nothing

The boot chain does not end when the operating system is up. It ends when the scheduler will accept work on that node, and that is a separate handshake with its own failure mode.

sinfo
scontrol show node cn01 | grep -E 'State|BootTime|Reason'
ssh cn01 systemctl is-active slurmd
Expected output
PARTITION AVAIL TIMELIMIT NODES STATE NODELIST
compute*     up  infinite     2  idle cn01,cn02

   State=IDLE
   BootTime=2026-08-24T03:11:42
   Reason=(null)

active

The client that performs this handshake arrived inside the image.
Its configuration file arrived through an overlay.

Two different layers had to be correct for this one line of output. Be able to name both, because when a freshly provisioned node sits in DOWN it is almost always one of them.

complete the trace

A template is waiting in your home directory at ~/lab12-trace.yaml. It lists eleven attributes of a running compute node against blank answers. For each, record which object or file is the actual source of truth.

vi ~/lab12-trace.yaml
# one line per attribute; the accepted answers are layer names:
#   dhcp | image | profile | system-overlay | runtime-overlay | node-object

Three of the eleven are not layer names. They are values you have to read off this system: the image build identifier, cn02's hardware address, and the number of node objects in the database. You collected all three during the exercises above.

Lab 1 Checkpoint run this when your trace is complete
hpcops-check 12
hpcops-check 12 --hint

The check names which attributes are correctly attributed and which are not. --hint gives you the next unmet one — where to look, never the answer. If you break the file's structure rather than its content, hpcops-reset 12 restores a blank template in under a second and costs you nothing you had not written yourself.

Before Lab 2 begins. Run the trace once more against cn02 instead of cn01. Every attribute that comes out identical tells you what a shared image and a shared profile actually guarantee. Every one that differs was assigned per node rather than per fleet, and those are the ones that will bite you at scale.

Lab 2 — driven from the front, watch and question
Modify and Reprovision
Land four specific changes on one node and prove they reached that node and nothing else.

This is the request an operator gets dozens of times over a node's life, and it is the one most likely to go wrong in a way nobody notices until the wrong machine reboots. It runs on the shared server, so it is driven from the front of the room. Do not run these commands from your own shell — they will be refused, and if they were not, fourteen simultaneous image rebuilds would be the only thing anyone learned today.

Three things to watch for, and be ready to answer on.

First: each change is made twice — once so it is true on the running node, once so it is declared somewhere that survives the next boot. Watch which command does which. They are not the same operation and confusing them is the single most common provisioning error.

Second: cn01 is in service throughout. Nothing done here is allowed to touch it. Watch for the moment where it would have been easy to take it down by accident.

Third: the boot in step 6 is slow enough to narrate. Follow each stage as it happens and note where the time actually goes.

1

Read the change set before touching anything

Four changes: one package, one filesystem to mount at /proj, one SSH key principal to authorise, one kernel parameter to set. All four must land on cn02 and nowhere else.

cat /etc/hpcops/lab13-changeset
Expected output
PACKAGE   strace
MOUNT     10.31.0.1:/exports/proj-cfd  ->  /proj
KEY       svc-monitor
SYSCTL    kernel.numa_balancing = 0

Disabling NUMA balancing on a compute node is a real HPC setting, not a placeholder. Worth a moment on why a site would want the kernel to stop migrating pages between nodes underneath a running job.

2

Put the package inside the image, then rebuild it

On a diskless node the image is the only thing carrying packages. Installing on the running node would work until the next boot and then silently vanish, which is worse than not working at all.

sudo wwctl container exec rocky9 /bin/sh -c "dnf install -y strace"
sudo wwctl container build rocky9
sudo wwctl container list
Expected output — compare the size against Ex 4
Building container: rocky9
Created image for VNFS container rocky9: 1.4 GiB

CONTAINER NAME  NODES  KERNEL VERSION      SIZE
rocky9          2      5.14.0-503.el9      1.4 GiB

This one command has just changed the image that both nodes are configured to use. Nothing has moved yet — but the fleet's source of truth is now different from what cn01 is running.

3

Declare the mount and the kernel parameter in the every-boot overlay

Both of these are host-behaviour rather than host-identity, so they belong in the overlay that is rewritten at every boot. The mount line is the one that was commented out with a date — reinstate it.

sudo wwctl overlay edit site-runtime /etc/fstab.ww
# uncomment the proj-cfd line
sudo wwctl overlay edit site-runtime /etc/sysctl.d/90-hpc.conf.ww
# add: kernel.numa_balancing = 0

Setting a sysctl with sysctl -w on the running node would satisfy anyone watching the output and would not survive the reboot two steps from now. Declared and set are different states and the check tests both separately.

4

Authorise the key in the first-boot overlay

Identity material belongs in the overlay applied once at provisioning rather than rewritten every boot — a node that regenerates its trust on every reboot is a node whose fingerprint nobody can pin.

sudo wwctl overlay edit site-system /root/.ssh/authorized_keys.ww
# append the svc-monitor public key
sudo wwctl overlay show site-system /root/.ssh/authorized_keys.ww --render cn02

Ask yourself where this key would have to live if there were five hundred nodes and the key had to be rotated on a Friday afternoon. The answer is the same file — that is the point of the model.

5

Render the overlays — editing is not building

Overlay source files are templates. Until they are rendered, the change exists in the editor's output and nowhere a booting node can reach.

sudo wwctl overlay build
Expected output
Building overlay for cn01: site-system, site-runtime
Building overlay for cn02: site-system, site-runtime

Note that it built for both nodes. The overlays are now staged for cn01 too — and cn01 will not receive them, because it is not going to boot. Staged and delivered are yet another pair of different states.

6

Reboot cn02 and watch every stage of the chain

The node has no disk, so any reboot re-runs the entire chain from nothing. Watch the log on the left and the console on the right; the stages arrive in a fixed order and each one is a place a real fleet fails.

# terminal 1 — the evidence trail, live
sudo journalctl -u dnsmasq -u warewulfd -f

# terminal 2 — trigger it
ssh cn02 systemctl reboot

# if cn02 has stopped answering, the out-of-band path instead:
hpcops-power cycle cn02
Expected output — the chain, in order
DHCPDISCOVER(virbr1) 52:54:00:07:00:02
DHCPACK(virbr1) 10.31.0.12 52:54:00:07:00:02 cn02      <- address
sent /var/lib/tftpboot/undionly.kpxe to 10.31.0.12     <- bootloader
warewulfd: cn02 requested kernel                        <- kernel
warewulfd: cn02 requested container rocky9              <- root image
warewulfd: cn02 requested overlay site-system           <- identity
warewulfd: cn02 requested overlay site-runtime          <- behaviour
slurmctld: node cn02 returned to service                <- terminus

Seven stages, seven separate things that can fail independently. The image fetch is the one that dominates the clock, and it is the only one whose cost multiplies by node count.

7

Prove the blast radius — four changes on cn02, nothing on cn01

Verifying that a change landed is the easy half. Verifying that it landed nowhere else is the half that keeps a partition in service.

ssh cn02 "rpm -q strace; findmnt /proj; sysctl kernel.numa_balancing"
ssh cn01 "rpm -q strace; uptime -s"
Expected output — the second block is the important one
strace-5.18-2.el9.x86_64
TARGET SOURCE                       FSTYPE OPTIONS
/proj  10.31.0.1:/exports/proj-cfd  nfs4   rw,relatime
kernel.numa_balancing = 0

package strace is not installed
2026-08-24 03:11:42

cn01 has not rebooted since Monday. It is running the old image.
That is the correct outcome, not a missed step.

The fleet is now deliberately inconsistent, and somebody has to decide when cn01 catches up. That decision — not the rebuild — is the actual job.

Lab 2 Checkpoint run from the front — twelve criteria
hpcops-check 13

Each of the four changes is checked twice — true on the running node, and declared where it survives a boot. Then cn02's re-registration, and finally that cn01 has not moved: same boot, same packages, same mounts as at the start. On a clean pass it prints the measured time from image rebuild to cn02 returning to service.

The closing question. Break the measured round trip into its parts — the image rebuild, the network fetch, the boot itself, the scheduler handshake. Decide which one you would attack first if this were five hundred nodes instead of one, and be able to say what you would actually change to attack it.

the physical gap

Assigned alongside this session: a recorded walkthrough of an actual bare-metal deployment — racking, cabling, BMC configuration and first boot.

Today's estate keeps its networks apart in software. A real provisioning network is kept apart by separate cabling, separate switches and separate colour conventions, and that discipline does not show up on a screen. The same goes for the service processor you saw stood in for by hpcops-power: on a real floor that is a separate embedded computer with its own address, its own credentials and its own failure modes, reachable when the node it is attached to is entirely dead.

Watch for both, and bring back one concrete example of something you did today that would not be acceptable on a real floor.
