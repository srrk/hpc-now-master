Part 1 of 6 · ~5 minutes

Zone Orientation

Before you read health, before you benchmark — confirm what you are connected to. Every HPC cluster has multiple filesystem zones with different contracts. Read the map before you operate in it.

Slide anchor: Slide 3 — Four zones. Four contracts.

Item 19 — Filesystem zones
1.1

Confirm filesystem type per zone

Run df -T against all four zones simultaneously. The -T flag shows filesystem type — this is what distinguishes Lustre from NFS at a glance.

Command
df -T /fsx/scratch/$USER /home/$USER /fsx/project/$USER
What you will see

10.x.x.x:/    nfs      52428800   2097152   50331648   4% /home
# /fsx — Type: lustre. This is the parallel filesystem.
# /home — Type: nfs. This is NFS from the head node.

Record the filesystem type for each zone. Lustre and NFS have different performance characteristics, different backup policies, and different quota models. The type is the first thing you confirm.

Part 2 of 6 · ~10 minutes

Health Check

Before you touch anything on a shared filesystem, read its state. This is the habit. Two commands, run in order, every time. You are looking at target states and per-OST fill — two different windows into the same filesystem.

Slide anchor: Slide 10 — Two commands. One habit. · Slide 9 — LNet.

Item 24 — Health commands Item 5 — LNet Item 20 — OST fill monitoring
2.1

Check target states with lctl dl

Lists all Lustre client devices and their current state. On FSx the MGS and MDS are managed by AWS — you will not see them listed. What you do see are the OSC (Object Storage Client) connections to each OST.

Command
lctl dl
What to look for
  0 UP mgc MGC10.x.x.x@tcp ...    ← config client — UP is healthy
  1 UP osc fsxtest-OST0000... ACTIVE  ← OST 0 client — ACTIVE is healthy
  2 UP osc fsxtest-OST0001... ACTIVE  ← OST 1 client — ACTIVE is healthy
  # If you see INACTIVE or RECOVERING — note it and tell Rajesh immediately

RECOVERING looks like a temporary state. It is not always temporary. Note any non-ACTIVE state before proceeding.

2.2

Check per-OST fill with lfs df -h

Shows per-OST capacity and utilisation. The aggregate row at the bottom is the number monitoring dashboards typically show. The per-OST rows are what actually matters for job failures.

Command
lfs df -h /fsx/scratch/
What to look for
UUID                   bytes        Used   Available Use% Mounted on
fsxtest-OST0000_UUID   600.0G       4.0G     596.0G   1% /fsx[OST:0]
fsxtest-OST0001_UUID   600.0G       4.0G     596.0G   1% /fsx[OST:1]
filesystem_summary:    1.2T         8.0G       1.2T   1% /fsx
# Two OST rows — one per target
# Compare OST-level fill against the aggregate — are they balanced?

Slide 11 — The aggregate showed 70% and everything looked fine. One OST was at 98%. This is where that slide becomes real. Read per-OST, not just the summary.

2.3

Check LNet NID

Returns the Network Interface Descriptor of this node — the address LNet uses for all Lustre traffic. On FSx the transport is EFA (Elastic Fabric Adapter). On-prem this would show InfiniBand (@o2ib) or TCP (@tcp).

Command
lctl list_nids
What you will see
10.x.x.x@tcp
# Format: IP@transport
# On this FSx cluster: TCP transport (EFA abstracted by AWS)
# On-prem InfiniBand: 10.x.x.x@o2ib

Part 3 of 6 · ~15 minutes

Stripe Diagnosis

Read the configuration before you write anything. Your scratch directory has been provisioned with a deliberate stripe misconfiguration. Diagnose it using lfs getstripe, benchmark it using IOR, then read the Layout EA on the file IOR wrote. You are building the before half of the before/after evidence.

Slide anchor: Slides 7, 8 — Stripe count and stripe size. Slide 6 — Layout EA.

Item 22 — Stripe count Item 23 — Stripe size Item 33 — IOR benchmark

Note on stripe_count on this cluster. This lab has 2 OSTs. When you run lfs setstripe -c 4 in Part 4, Lustre will silently cap the stripe count at 2 — the number of available OSTs. lfs getstripe will show stripe_count: 2, not 4. This is correct behaviour. On a production cluster with 900 OSTs, -c 4 would stripe across 4 distinct OSTs.

3.1

Read the directory stripe configuration

lfs getstripe on a directory shows the stripe configuration that will be inherited by all new files written into it. This is the Layout EA default for the directory.

Command
lfs getstripe /fsx/scratch/$USER/
What you will see
/fsx/scratch/shefali/:
stripe_count:  1       stripe_size:   1048576   stripe_offset: -1
# stripe_count: 1 — all data lands on a single OST
# stripe_size: 1048576 — 1MiB chunks
# stripe_offset: -1 — OST chosen automatically by Lustre

stripe_count=1 means no fan-out. All I/O serialises through one OST regardless of how many OSTs exist. This is the misconfiguration.

3.2

Run IOR — before fix

The IOR job script is already in your home directory. It writes and reads a test file in your scratch directory and reports aggregate bandwidth. Submit it now and wait for it to complete.

Commands
sbatch ~/ior_before.sh
watch squeue -u $USER
# Wait for the job to show COMPLETED
# Ctrl+C to exit watch
cat ~/results/ior_before.txt
What to look for in the output
access    bw(MiB/s)  IOPS   Latency(s)  block(KiB)  xfer(KiB)
------    ---------  ----   ----------  ----------  ---------
write     ~50        ...    ...         ...         ...
read      ~50        ...    ...         ...         ...
# Record the write bandwidth — this is your before number
# The plateau here is the single-OST ceiling
3.3

Inspect the Layout EA on the file IOR wrote

Run lfs getstripe on the specific file IOR created. This shows the actual stripe layout — which OST indices received data, how many objects were created. This is reading the Layout EA directly off the MDT.

Commands
ls /fsx/scratch/$USER/
# Find the IOR test file — it will be named testfile or similar
lfs getstripe /fsx/scratch/$USER/ior_testfile
What you will see
/fsx/scratch/shefali/ior_testfile:
lmm_stripe_count:  1
lmm_stripe_size:   1048576
lmm_layout_gen:    0
lmm_stripe_offset: 0
	obdidx		 objid		 objid		 group
	     0	      12345	    0x3039	             0
# obdidx 0 only — all data on OST 0000
# One object. One OST. The misconfiguration is visible at the file level.

This is what the MDS held in the Layout EA. The MDS knew where every byte of this file lives — on OST 0000 only. This is why lfs getstripe is the diagnostic tool, not ls or stat.

Part 4 of 6 · ~20 minutes

Stripe Fix and Verification

Fix the stripe configuration, verify it applies to new files — not existing files — and benchmark again. The delta between your before and after IOR numbers is your evidence. Not intuition. Numbers.

Slide anchor: Slide 13 — Same filesystem. Same hardware. Different stripe. 4× different bandwidth. · Slide 22 — The delta is your evidence.

Item 22 — Stripe count Item 23 — Stripe size Item 33 — IOR benchmark
4.1

Fix the stripe configuration on your scratch directory

lfs setstripe at directory level changes the default stripe config for all new files written into it. Existing files are not restriped — they keep the configuration they were written with.

Command
lfs setstripe -c 4 /fsx/scratch/$USER/
# -c 4 requests stripe across 4 OSTs
# FSx has 2 OSTs — Lustre will use 2 (the maximum available)
# The command succeeds — stripe count is capped silently at 2
4.2

Verify the directory config changed

Command
lfs getstripe /fsx/scratch/$USER/
What you should see now
/fsx/scratch/shefali/:
stripe_count:  2       stripe_size:   1048576   stripe_offset: -1
# stripe_count: 2 — confirmed. Lustre capped at 2 (max OSTs available).
4.3

Write a new file and verify it gets the new stripe

This step is critical. It proves that the directory stripe fix applies to new files — and that the old IOR file is NOT retroactively restriped. Both facts matter operationally.

Commands
dd if=/dev/zero of=/fsx/scratch/$USER/newfile bs=1M count=100
lfs getstripe /fsx/scratch/$USER/newfile
What you will see on the new file
lmm_stripe_count:  2
	obdidx		 objid
	     0	      ...
	     1	      ...
# Two OST indices — 0 and 1. Data distributed across both OSTs.
Now check the OLD IOR file
lfs getstripe /fsx/scratch/$USER/ior_testfile
What you will see on the old file
lmm_stripe_count:  1
	obdidx		 objid
	     0	      ...
# Still stripe_count: 1. The old file was NOT restriped.
# Fixing the directory changes future files only.
# Data already written must be copied to benefit from the new config.

This is the operationally important point. If a researcher fixes their stripe config mid-project, their existing output files are unaffected. Only new writes get the new layout. They need to re-run the job — not just change the config.

4.4

Run IOR — after fix

The ior_after.sh script writes to the same target path. Because the directory now has stripe_count=2, the new test file will be written with the new configuration. Compare the bandwidth to Part 3.

Commands
sbatch ~/ior_after.sh
watch squeue -u $USER
# Wait for COMPLETED
cat ~/results/ior_after.txt

Part 5 of 6 · ~10 minutes

Space Awareness

You have written data. Now find it the Lustre way. lfs find knows about Lustre block allocation in a way that standard find does not. This is the tool you reach for when scratch fills up and you need to identify the offending files fast.

Slide anchor: Slide 12 — Not df. Not du. · Slide 11 — The aggregate number lies.

Item 21 — lfs find Item 20 — OST fill monitoring
5.1

Find your files by block usage with lfs find

The --blocks filter uses Lustre's own block accounting — it knows how many 512-byte blocks a file actually occupies on the OSTs, including sparse files. Standard find has no equivalent filter.

Command
lfs find /fsx/scratch/$USER --blocks +1 --type f
# --blocks +1 means: files using more than 1 block (i.e. any non-empty file)
# Adjust the threshold: --blocks +102400 means files larger than 100MB
Compare with standard find
find /fsx/scratch/$USER -type f
# Returns the same files but cannot filter by Lustre block usage
# find -size uses apparent file size, not allocated Lustre blocks
# On a parallel filesystem these can differ significantly for sparse files

When scratch fills: lfs find with --blocks and --uid filters is how you identify which user owns the space. Not df. Not du. lfs find.

5.2

Re-read per-OST fill after your writes

Run lfs df -h again. Your IOR writes and dd writes will have changed the per-OST fill. Observe which OST received more data and whether the distribution is balanced.

Command
lfs df -h /fsx/scratch/
# Compare OST 0000 and OST 0001 fill percentages
# Are they balanced? Does stripe_count=2 distribute more evenly than stripe_count=1?
OSTFill % after writesBalanced?
OST 0000
OST 0001

instructor interventions

False confidence traps expected in this lab — per learner. Interventions below are for Rajesh only. Do not share with learners.

Vasu Stripe = RAID stripe → redundancy mental model
When Step 3.1 — when Vasu sees stripe_count=1 and interprets it as a redundancy risk
Spring "Vasu — in NetApp what does stripe width mean for your redundancy design? Is that the same thing happening here?"
After Stripe count in Lustre controls parallelism — how many OSTs serve this file simultaneously. Redundancy lives in the RAID beneath each OST. These are completely separate concerns. stripe_count=1 is a performance problem, not a data safety problem.
Praneeth Virtualisation instinct — suggest abstracting the storage layer
When Part 4 — when Praneeth suggests that a storage virtualisation layer could handle this automatically
Spring "What would a virtualisation layer do with the stripe configuration? Who would set it — and when?"
After Stripe configuration is workload-specific — a large parallel write needs stripe_count=16, a small sequential write needs stripe_count=1. No virtualisation layer can make that decision automatically. The admin sets it per directory based on the workload expected to land there.
Shefali Developer vs operator diagnostic frame
When Part 4 — when Shefali correctly diagnoses but frames lfs setstripe as a user-facing configuration, not an admin operation
Spring "Who sets this in a production cluster — the researcher or the admin? And when — before the job runs or after?"
After In production, admins pre-configure directory stripe settings appropriate to the expected workload. Researchers may set it themselves on their own scratch directories if they know what they need. But when a performance problem is reported, the admin diagnoses and recommends — and in many sites, applies — the fix.
Tanobir Linux process model — reach for df before lfs df

Spring "What does that output tell you about individual OST fill? Can you see OST 0000 and OST 0001 separately?"
After df -h shows the FSx mount as a single filesystem — one aggregate line. lfs df -h shows per-OST rows. The aggregate is what monitoring dashboards typically surface. The per-OST breakdown is what matters for diagnosing job failures and capacity problems. Always run lfs df -h on a Lustre filesystem.

Common wrong paths across all learners — redirect language:

Wrong path: Learner runs df -h instead of lfs df -h
Redirect: "What does that tell you about individual OST fill? Run the Lustre-aware version."

Wrong path: Learner fixes directory stripe, reruns IOR, checks the old file and expects it to show stripe_count=2
Redirect: "New stripe config applies to new files. What does lfs getstripe show on the file IOR wrote in Part 3? Still stripe_count=1?"
