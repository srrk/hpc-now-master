Part 1 of 6 · ~5 minutes

Zone Orientation

Before you read health, before you benchmark — confirm what you are connected to. Every HPC cluster has multiple filesystem zones with different contracts. Read the map before you operate in it.

Slide anchor: Slide 3 — Four zones. Four contracts.

Item 19 — Filesystem zones
1.1

Confirm filesystem type per zone

Run df -T to see filesystem types. The -T flag distinguishes Lustre from NFS at a glance. Two runs — one from the head node, one from a compute node — will show you where the NFS zone actually lives.

Command — on the head node
df -T /fsx/scratch/$USER /home/$USER 2>/dev/null
What you will see on the head node
Filesystem            Type       1K-blocks     Used  Available Use% Mounted on
10.x.x.x@tcp:/xxxxxxxx lustre    2306867200    16000 2306850000   1% /fsx
/dev/nvme0n1p1         xfs         46856196 24000000   22600000  52% /
# /fsx — Type: lustre. This is the parallel filesystem.
# /home/$USER — the ROOT filesystem row (xfs). On the head node, /home lives
#               on local disk — the head node is the NFS *server*, not a client.
Command — from a compute node (via srun)
srun -N1 --pty df -T /fsx/scratch/$USER /home/$USER
What you will see on the compute node
Filesystem            Type       1K-blocks     Used  Available Use% Mounted on
10.x.x.x@tcp:/xxxxxxxx lustre    2306867200    16000 2306850000   1% /fsx
10.x.x.x:/home         nfs         46856196    32000   46824196   1% /home
# From here /home appears as its own row — Type: nfs — because compute nodes
# are NFS *clients* of the head node. This is what a learner-facing node sees.

Record the filesystem type for each zone. Lustre and NFS have different performance characteristics, different backup policies, and different quota models. Where you run df -T from matters — the head node hides the NFS-ness of /home because it's the server.

Health Check

Before you touch anything on a shared filesystem, read its state. This is the habit. Two commands, run in order, every time. You are looking at target states and per-OST fill — two different windows into the same filesystem.

Slide anchor: Slide 10 — Two commands. One habit. · Slide 9 — LNet.

Item 24 — Health commands Item 5 — LNet Item 20 — OST fill monitoring
2.1

Check target states with lctl dl

Lists all Lustre client devices and their current state. On FSx the MGS and MDS are managed by AWS — you will not see them listed. What you do see are the OSC (Object Storage Client) connections to each OST.

Command
sudo lctl dl
What to look for
  0 UP mgc MGC10.x.x.x@tcp ...    ← config client — UP is healthy
  1 UP lov ...
  2 UP lmv ...
  3 UP mdc ...-MDT0000-mdc-... UP       ← metadata client — UP is healthy
  4 UP osc ...-OST0000-osc-... UP       ← OST 0 client — UP is healthy
  5 UP osc ...-OST0001-osc-... UP       ← OST 1 client — UP is healthy
  # If you see INACTIVE or RECOVERING — note it and tell Rajesh immediately

RECOVERING looks like a temporary state. It is not always temporary. Note any non-UP state before proceeding.

2.2

Check per-OST fill with lfs df -h

Shows per-OST capacity and utilisation. The aggregate row at the bottom is the number monitoring dashboards typically show. The per-OST rows are what actually matters for job failures.

Command

xxxxxxxx-OST0000_UUID        1.1T        7.8M        1.1T   1% /fsx[OST:0]

Part 3 of 6 · ~15 minutes

Stripe Diagnosis

Read the configuration before you write anything. Your scratch directory has been provisioned with a deliberate stripe misconfiguration. Diagnose it using lfs getstripe, benchmark it using IOR, then read the Layout EA on the file IOR wrote. You are building the before half of the before/after evidence.

Slide anchor: Slides 7, 8 — Stripe count and stripe size. Slide 6 — Layout EA.

Item 22 — Stripe count Item 23 — Stripe size Item 33 — IOR benchmark

Note on stripe_count on this cluster: intent vs reality. This lab has 2 OSTs. When you run lfs setstripe -c 4 in Part 4, Lustre stores the requested stripe_count (4) on the directory's Layout EA as intent. The cap to the actually-available OST count happens at file-write time, on the file's Layout EA. So lfs getstripe on the directory will still show stripe_count: 4 after Part 4.1 — but the newfile you dd in Part 4.3 will show lmm_stripe_count: 2. Intent on the dir. Reality on the file. This split is fundamental to how Lustre applies stripe policy — and it's why you always confirm on the actual file, not just the directory. On a production cluster with 900 OSTs, -c 4 would stripe files across 4 distinct OSTs.

3.1

Read the directory stripe configuration

lfs getstripe on a directory shows the stripe configuration that will be inherited by all new files written into it. This is the Layout EA default for the directory.

Command
lfs getstripe /fsx/scratch/$USER/
What you will see
/fsx/scratch/yogi/
stripe_count:  1       stripe_size:   1048576   pattern:       raid0   stripe_offset: -1
# stripe_count: 1 — all data lands on a single OST
# stripe_size: 1048576 — 1MiB chunks
# stripe_offset: -1 — OST chosen automatically by Lustre

stripe_count=1 means no fan-out. All I/O serialises through one OST regardless of how many OSTs exist. This is the misconfiguration.

3.2

Run IOR — before fix

The IOR job script is already in your home directory. It writes and reads a test file in your scratch directory and reports aggregate bandwidth. Submit it now and wait for it to complete.

Commands
sbatch ~/ior_before.sh
watch squeue -u $USER
# Wait for the job to leave the queue (COMPLETED)
# Ctrl+C to exit watch
cat ~/results/ior_before.txt
What to look for in the output
access    bw(MiB/s)  IOPS   Latency(s)  block(KiB)  xfer(KiB)
------    ---------  ----   ----------  ----------  ---------
write     ~600       ...    ...         ...         ...
read      ~600       ...    ...         ...         ...
# Record the write bandwidth — this is your before number.
# On t3.medium the ceiling is closer to the NIC bandwidth than the
# single-OST ceiling — you'll see this in Part 4 when the "after" number
# only moves slightly. That's a real teaching moment: the bottleneck
# isn't always where you expect.
3.3

Inspect the Layout EA on the file IOR wrote

Run lfs getstripe on the specific file IOR created. IOR was invoked with -F (file-per-process), so the actual file on disk is ior_testfile.NNNNNNNN — with --ntasks=1, that's ior_testfile.00000000. This shows the actual stripe layout — which OST indices received data, how many objects were created. This is reading the Layout EA directly off the MDT.

Commands
ls /fsx/scratch/$USER/
# You will see: ior_testfile.00000000  (per-rank naming from IOR's -F flag)
lfs getstripe /fsx/scratch/$USER/ior_testfile.00000000
What you will see
/fsx/scratch/yogi/ior_testfile.00000000
lmm_stripe_count:  1
lmm_stripe_size:   1048576
lmm_pattern:       raid0
lmm_layout_gen:    0
lmm_stripe_offset: 0
	obdidx		 objid		 objid		 group
	     0	      12345	    0x3039	             0
# obdidx 0 only — all data on OST 0000
# One object. One OST. The misconfiguration is visible at the file level.

This is what the MDS held in the Layout EA. The MDS knew where every byte of this file lives — on OST 0000 only. This is why lfs getstripe is the diagnostic tool, not ls or stat.

Part 4 of 6 · ~20 minutes

Stripe Fix and Verification

Fix the stripe configuration, verify the split — intent lands on the directory, reality lands on new files, existing files are not restriped — and benchmark again. The delta between your before and after IOR numbers is your evidence. Not intuition. Numbers.

Slide anchor: Slide 13 — Same filesystem. Same hardware. Different stripe. Different bandwidth. · Slide 22 — The delta is your evidence.

Item 22 — Stripe count Item 23 — Stripe size Item 33 — IOR benchmark

On the size of the delta. On a production HPC cluster with fat NICs and many OSTs, changing stripe_count from 1 to N routinely produces multi-x bandwidth improvements. On this teaching cluster the head node is a t3.medium with a modest network path — striping across 2 OSTs still helps, but the NIC is the ceiling, so you'll typically see a small (few percent) improvement rather than a dramatic multi-x. The lesson is the same: numbers, not intuition. The direction of the delta matters even when the magnitude is bottlenecked elsewhere.

4.1

Fix the stripe configuration on your scratch directory

lfs setstripe at directory level changes the default stripe config for all new files written into it. Existing files are not restriped — they keep the configuration they were written with.

Command
lfs setstripe -c 4 /fsx/scratch/$USER/
# -c 4 requests stripe across 4 OSTs
# FSx has 2 OSTs — Lustre will cap PER-FILE at 2 at write time
# The directory Layout EA still records the requested value (4)
4.2

Verify the directory config changed

Command
lfs getstripe /fsx/scratch/$USER/
What you should see now
/fsx/scratch/yogi/
stripe_count:  4       stripe_size:   1048576   pattern:       raid0   stripe_offset: -1
# stripe_count: 4 — this is the requested INTENT stored on the directory.
# Lustre does NOT cap the directory-level value; only file-level (at write).
# Confirm by writing a file in the next step and inspecting IT.
4.3

Write a new file and verify it gets the actual cap

This step is critical. It proves three things: (1) new files inherit the directory's intent, (2) Lustre caps to the actually-available OST count at write time, and (3) the old IOR file is NOT retroactively restriped. All three matter operationally.

Commands
dd if=/dev/urandom of=/fsx/scratch/$USER/newfile bs=1M count=100 conv=fsync
lfs getstripe /fsx/scratch/$USER/newfile
What you will see on the new file
/fsx/scratch/yogi/newfile
lmm_stripe_count:  2
lmm_stripe_size:   1048576
	obdidx		 objid
	     0	      ...
	     1	      ...
# lmm_stripe_count: 2 — the CAP applied at file-write time (only 2 OSTs exist).
# Two OST indices — 0 AND 1. Data distributed across both OSTs.
# The directory says 4 (intent), the file says 2 (reality). Both are correct.
Now check the OLD IOR file
lfs getstripe /fsx/scratch/$USER/ior_testfile.00000000
What you will see on the old file
/fsx/scratch/yogi/ior_testfile.00000000
lmm_stripe_count:  1
	obdidx		 objid
	     0	      ...
# Still stripe_count: 1. The old file was NOT restriped.
# Fixing the directory changes future files only.
# Data already written must be copied to benefit from the new config.

This is the operationally important point. If a researcher fixes their stripe config mid-project, their existing output files are unaffected. Only new writes get the new layout. They need to re-run the job — not just change the config.

4.4

Run IOR — after fix

The ior_after.sh script writes to a new target path. Because the directory now has stripe_count=4 (intent), the new test file will be capped at 2 OSTs at write time. Compare the bandwidth to Part 3.

Commands

Part 5 of 6 · ~10 minutes

Space Awareness

You have written data. Now find it the Lustre way. lfs find knows about Lustre block allocation in a way that standard find does not. This is the tool you reach for when scratch fills up and you need to identify the offending files fast.

Slide anchor: Slide 12 — Not df. Not du. · Slide 11 — The aggregate number lies.

Item 21 — lfs find Item 20 — OST fill monitoring
5.1

Find your files by block usage with lfs find

The --blocks filter uses Lustre's own block accounting — it knows how many 512-byte blocks a file actually occupies on the OSTs, including sparse files. Standard find has no equivalent filter.

Command
lfs find /fsx/scratch/$USER --blocks +1 --type f
# --blocks +1 means: files using more than 1 block (i.e. any non-empty file)
# Adjust the threshold: --blocks +102400 means files larger than 100MB
Compare with standard find
find /fsx/scratch/$USER -type f
# Returns the same files but cannot filter by Lustre block usage
# find -size uses apparent file size, not allocated Lustre blocks
# On a parallel filesystem these can differ significantly for sparse files

When scratch fills: lfs find with --blocks and --uid filters is how you identify which user owns the space. Not df. Not du. lfs find.

5.2

Re-read per-OST fill after your writes

Run lfs df -h again now that you have written data (IOR test files + newfile) across both OSTs. Compare with your Part 2.2 baseline. The per-OST rows should show a small bump — and, importantly, the bump should be visible on BOTH OSTs if striping is working.

Command
lfs df -h /fsx/scratch/
What to compare
# Before Part 3/4 (from Part 2.2 baseline):
xxxxxxxx-OST0000_UUID   1.1T   7.8M   1.1T   1% /fsx[OST:0]
xxxxxxxx-OST0001_UUID   1.1T   7.8M   1.1T   1% /fsx[OST:1]

# After your writes — both OSTs should show growth:
xxxxxxxx-OST0000_UUID   1.1T   ~2G    1.1T   1% /fsx[OST:0]
xxxxxxxx-OST0001_UUID   1.1T   ~1G    1.1T   1% /fsx[OST:1]
# OST 0 grew more (holds ior_testfile from Part 3 + half of newfile from Part 4).
# OST 1 grew less (only its half of newfile + half of ior_testfile_after).
# That imbalance is what "the aggregate number lies" from Slide 11 looks like
# in miniature — visible per-OST, invisible in the aggregate summary.

This closes the loop from Part 2.2. You read per-OST fill before you touched anything. You are reading it again after. The delta on each OST is your proof of where your writes actually landed.

Part 6 of 6 · ~15 minutes

Quotas: user, group, project

Three quota dimensions on the same filesystem. Learn to read all three, understand which one bites first, and see what happens when a group quota is contended by two users.

Slide anchor: Slide 18 — Three quota dimensions. Slide 19 — First one to fire wins.

Item 26 — User quota Item 27 — Group quota Item 28 — Project quota
6.1

Read your user quota

Command
lfs quota -u $USER /fsx
What you will see (as yogi)
Disk quotas for usr yogi (uid 2018):
     Filesystem  kbytes   quota   limit   grace   files   quota   limit   grace
           /fsx     ...    7168000  8388608       -    ...       -       -       -
# Soft limit ~7 GiB, hard limit ~8 GiB (values in KiB).
# Chandra has 6 GiB hard / 5 GiB soft. Sujith matches yogi.
6.2

Read your group quota

Command
sudo lfs quota -g eng_dept /fsx    # yogi, sujith
sudo lfs quota -g life_dept /fsx   # chandra

Yogi and Sujith SHARE the eng_dept group quota (15 GiB hard). If Yogi writes 10 GiB, Sujith only has ~5 GiB of group budget left, even though her personal user quota still shows 8 GiB. Contention. This is where "why did my job die" often turns out to be "someone else in your group filled the group quota".

6.3

Read your project quota

Command
sudo lfs quota -p 1001 /fsx   # eng_dept project (yogi + sujith)
sudo lfs quota -p 1002 /fsx   # life_dept project (chandra)

Project quotas are yet another axis. Same user, same group, but constrained by the project a file is associated with. The tightest of the three (user, group, project) is what bites first.

instructor interventions

Specific traps a learner will hit on this cluster with this runbook. Each intervention names the moment to step in and the exact correction to give.

Rajesh → learner Trap · "lfs getstripe: cannot open '.../ior_testfile'"
Where Part 3.3 / Part 4.3 — learner types ior_testfile literally
Fix IOR was launched with -F (file-per-process). The file on disk is ior_testfile.00000000 — add the .00000000 suffix, or use a glob: lfs getstripe /fsx/scratch/$USER/ior_testfile*
Teach IOR's per-rank naming is a real-world gotcha — always ls the target dir first when the command line doesn't match the file on disk.
Rajesh → learner Trap · "the directory still says stripe_count: 4 — didn't the runbook say 2?"
Where Part 4.2 — learner expects the cap to appear on the directory
Fix Both values are correct. The directory Layout EA stores intent (what you requested); the cap is applied at file-write time and shown on the file's Layout EA. Have them run lfs getstripe on the newfile from Part 4.3 — it shows lmm_stripe_count: 2. Intent on the dir. Reality on the file.
Teach This is fundamental to how Lustre applies stripe policy — and why you always confirm on the actual file, not just the directory.
Rajesh → learner Trap · "the delta is only a few percent, not 4×"
Where Part 4.5 — learner records ~600 → ~615 MiB/s and worries the fix didn't work
Fix The fix DID work — verify via the newfile's lmm_stripe_count: 2 and both obdidx rows. Data is going to both OSTs. The bandwidth ceiling isn't the parallel filesystem here — it's the t3.medium NIC (~5 Gbps). On a production node with a fatter NIC you would see the multi-x delta.
Teach The lesson is direction + verification, not magnitude. The delta went the right way, and the file layout is provably fanned out. On a real cluster you would move the bottleneck; here you're seeing it.
Rajesh → learner Trap · "df -T on the head node doesn't show /home as NFS"
Where Part 1.1 — learner runs df -T directly on the head node and doesn't see the NFS row
Fix On the head node /home lives on the root filesystem (xfs). The head node IS the NFS server; it doesn't NFS-mount /home from itself. To see NFS, run from a compute node: srun -N1 --pty df -T /fsx/scratch/$USER /home/$USER
Teach The map you see depends on where you're standing. Learners will be on compute nodes at the real workload — that view is the one that matters.
Rajesh → learner Trap · "lfs find --blocks +1 doesn't return my dd'd file"
Where Part 5.1 — learner's newfile was written with dd if=/dev/zero and doesn't appear in lfs find output
Fix FSx SCRATCH_2 does zero-detection — an all-zero file reports 0 allocated blocks, so --blocks +1 filters it out. If Part 4.3 was followed with conv=fsync and /dev/urandom per this runbook, the file will appear. If not, have the learner redo the dd with conv=fsync from /dev/urandom.
Teach Block accounting on Lustre reflects what's actually on OSTs. Zero-detection, sparse files, and unflushed cache all make st_blocks lie about apparent size.
