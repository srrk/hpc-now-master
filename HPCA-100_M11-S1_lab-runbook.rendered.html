What makes a script operational

A personal script is one you run, at your desk, when you are paying attention. An operational script is one somebody else runs at 2 a.m. with a queue stopped and a principal investigator on the phone, or one a timer runs while nobody is watching at all. The difference is six habits, and every one of them exists because somebody's script once did damage that the habit would have stopped.

Most HPC sites run on one or two administrators. At that staffing level automation is not an efficiency gain. It is the only way the week's work fits into the week.

The six safety patterns — these are graded

PatternWhat it protects against
Fail fast on any error and on any unset variablea script that carries on after step 3 failed and does steps 4 to 8 against a half-built user
Dry run by default, explicit flag to actrunning it to see what it does, and finding out by it doing it
Idempotent: running it again is safethe second run after a partial failure creating duplicates, or worse, changing a number that is already in use
Log every action"something changed last night" with no way to say what
Confirm anything destructiveoverwriting the thing a user already depends on because it looked like a re-run
Lock, so two copies cannot run at oncetwo colleagues, or a colleague and a timer, both picking UID 2007

What to automate, and what not to

Frequency × duration × error rate. A task done twice a week, taking ten minutes, that goes wrong one time in five, is worth automating. A task done once a year whose failure is expensive and hard to check is not: you will not trust the script, and you will be right not to. Nor is a task where the thinking is the work. A script can create an account; it cannot decide whether somebody should have one.

Where a user lives on this cluster

Onboarding one person touches four systems, and they all have to agree.

  • Local identity on three nodes. The same username, the same UID and the same GID, on head, c1 and c2. There is no directory service here; each node keeps its own /etc/passwd and /etc/group.
  • A home directory on /home, which head exports and both compute nodes mount.
  • An SSH key in ~/.ssh/authorized_keys.
  • A scheduler association, without which the user exists everywhere and can run nothing.

Get one of the four wrong and the user does not find out at login. They find out when their first job fails on c2 and not on c1.

So that you, your neighbour and the instructor can run each other's scripts the same way, every script in this lab takes the same arguments. Everything inside it is yours to design.

2.4 Shell or Python

Pick the tool for the shape of the work

Most of onboarding is running commands on three hosts, which is what shell does well. Reading a CSV, deciding what to do when a field is missing, and keeping a list of what changed is structured data and real logic, which is where shell gets fragile and Python does not. Either is acceptable. Mixed is often best: a shell script that calls short commands, or a Python script that calls subprocess.run([...], check=True) for each one. Python's standard library is all that is installed; there is no package index from here.

2.5 The six patterns, as fragments

These are the building blocks the demo used, shown in isolation and not as an onboarding script. Assembling them around the eight steps is the task.

These go in your script file, not at your promptPasted at the root@head prompt, two of them change the shell you are typing in. After set -Eeuo pipefail, the next command that fails logs you out of head. After the lock lines, your shell holds /run/onboard.lock until you log out, so your own script will refuse to run. If either happens, type exit and choose 1.
Fail fast, and say where
set -Eeuo pipefail
trap 'echo "failed at line $LINENO: $BASH_COMMAND" >&2' ERR
What set -e does not catchA command whose result is tested (if, ||, &&, while) does not stop the script when it fails, because you asked to handle the failure yourself. And without pipefail, a pipeline's status is its last command's, so getent passwd x | cut -d: -f3 succeeds even when getent found nothing.
Dry run by default: one function decides whether anything happens
APPLY=0
run() {
  if (( APPLY )); then "$@"; else echo "would run: $*"; fi
}
Idempotent: ask before acting, every time
[ -d /srv/example ] || run mkdir /srv/example       # the check, then the act
mkdir -p /srv/example                               # or a command that is idempotent itself
Log every action, not the start and the end
LOG=~/course-repo/m11s1/logs/onboard-$(date +%Y%m%d).log
log() { printf '%s %s %s\n' "$(date -Is)" "$(hostname -s)" "$*" | tee -a "$LOG"; }
Confirm anything destructive
if [ -e "$target" ] && ! cmp -s "$new" "$target" && (( ! FORCE )); then
  log "REFUSED replace $target: differs; re-run with --force to replace"
  exit 4
fi
Lock: one copy at a time
exec 9>/run/onboard.lock
flock -n 9 || { echo "another onboard is running" >&2; exit 3; }

3Test the dry-run path, then the acting path10 min

Proof that the dry run changed nothing; proof that the acting run onboarded all three new starters across all four systems; and proof that a bad request stops before touching anything.

Test against a known state, before it runs anywhere else

A test is a comparison. Record the state, run the thing, record the state again, compare. "It looked fine" is not a test, because you only looked at what you expected to change.

3.1 Record the state before

./onboard.sh /opt/lab/reference/new-starters.csv; echo "exit $?"
for u in awilliams snair tokafor; do user-check $u; done > /tmp/after-dry.txt; diff /tmp/before.txt /tmp/after-dry.txt && echo "NO CHANGE"

4Prove it is safe to run again8 min

A second run that changes nothing, and the two patterns that only show themselves under pressure: the lock and the refusal.

Idempotency is tested, never assumed

The second run is the one that happens at a real site after the first one died halfway, at the moment you most need it to be harmless. "It checks first" is a claim. Two identical states either side of a second run is the proof.

4.1 Run it twice, compare

for u in awilliams snair tokafor; do user-check $u; done > /tmp/after-1.txt
./onboard.sh --apply /opt/lab/reference/new-starters.csv; echo "exit $?"
for u in awilliams snair tokafor; do user-check $u; done > /tmp/after-2.txt
diff /tmp/after-1.txt /tmp/after-2.txt && echo "NO CHANGE"
You should see, after the script's own output
exit 0
NO CHANGE
And exactly one association each, not two
sacctmgr -n -P show assoc format=account,user | grep -E 'awilliams|snair|tokafor'

4.2 The lock: start two at once

./onboard.sh --apply /opt/lab/reference/new-starters.csv & ./onboard.sh --apply /opt/lab/reference/new-starters.csv; echo "second exit $?"; wait

One of the two refuses with your lock-held exit code. If both report success, your second run is fast enough that the first had finished; add sleep 5 straight after taking the lock, run this again, then take the sleep out.

4.3 The refusal: a key that differs

A new key for awilliams, as if she had lost her laptop
ssh-keygen -q -t ed25519 -N '' -f /tmp/awilliams-new
grep awilliams /opt/lab/reference/new-starters.csv | sed 's#,[^,]*$#,/tmp/awilliams-new.pub#' | cat <(head -1 /opt/lab/reference/new-starters.csv) - > /tmp/rekey.csv
./onboard.sh --apply /tmp/rekey.csv; echo "exit $?"

Without --force it refuses and the old key is still there. Then run it again with --force and check that the key changed and that the log says so.

Stop · task 4read before going on
Check what you have
  • NO CHANGE on the second run, and one association per user. Copy both files into evidence/.
  • One of two concurrent runs refused.
  • The key replacement refused without --force and happened with it.
If the second run changed a UID, the step that asks "does this user already exist" is in the wrong place. It has to come before the step that chooses a number, and when the user exists, the number is theirs and is not chosen again.
Why the refusal is the right default

A re-run with different input is indistinguishable, from inside the script, from a mistake. The script cannot know whether you meant to replace the key a user logs in with. The person running it can, so the script asks them to say so.

Evidence that your log alone, with no other information, tells someone exactly what changed, where and when.

The log is for a reader who was not there

A log that says "onboard started" and "onboard finished" records that something happened and nothing about what. Each line needs the time, the host it changed, the object it changed, and what it did to it. The reader is you, three weeks from now, asked why snair has UID 2008 on two nodes and 2009 on the third.

The writing time is part of the answer. A script that saves ten minutes per onboarding and took fifty minutes to write has paid for itself on the fifth new starter, which at most sites is a matter of weeks. —Glossary
association
The scheduler's record that a user may run work under an account. A user without one exists on every node and can run nothing.
break-even
The number of runs after which the time spent writing a script is repaid by the time it saves. Writing time divided by the saving per run.
dry run
A run that reports what it would do and changes nothing. In an operational script, the default.
exit code
The number a program returns to whatever ran it. Zero for success; any other value is a failure the caller can act on, if the code means something specific.
fail fast
Stopping at the first error rather than continuing against a state the script no longer understands. In bash, set -Eeuo pipefail; the -E lets an ERR trap fire inside functions too.
idempotent
Safe to run again: a second run with the same input reaches the same state and changes nothing on the way.
lock
A mark one running copy holds so that a second copy refuses to start. flock on a file is the usual form.
operational script
A script written to be run by someone else, or by a timer, without the author present.
