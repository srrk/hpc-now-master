1.1

Install hwloc from tarball

arjun uses hwloc 2.7.2. chandra uses hwloc 2.9.3. The commands are identical — only the version number differs. The --prefix flag tells the build system where to install. Without it, the default is /usr/local — which is node-local and invisible to the compute node.

arjun — hwloc 2.7.2
arjun — install hwloc 2.7.2
cd ~
tar -xzf /tmp/tarballs/hwloc-2.7.2.tar.gz
cd hwloc-2.7.2
./configure --prefix=/apps/software/hwloc/2.7.2
make -j2
make install
# Verify the binary exists
/apps/software/hwloc/2.7.2/bin/lstopo --version
lstopo 2.7.2
chandra — hwloc 2.9.3
chandra — install hwloc 2.9.3
cd ~
tar -xzf /tmp/tarballs/hwloc-2.9.3.tar.gz
cd hwloc-2.9.3
./configure --prefix=/apps/software/hwloc/2.9.3
make -j2
make install
/apps/software/hwloc/2.9.3/bin/lstopo --version
lstopo 2.9.3

The software now exists at /apps. It does not exist in any user's environment. No PATH is set. No one can find it yet. That is the next step — and it is where the burden becomes visible.

1.2

Install likwid against your hwloc

likwid links against hwloc at compile time. The config.mk file must be edited to point at your specific hwloc install before building. If you skip this, likwid will find the system hwloc in /usr — a different version that may not exist on compute nodes.

arjun — likwid 5.3.0 against hwloc 2.7.2
arjun — install likwid linked to hwloc 2.7.2
cd ~
tar -xzf /tmp/tarballs/likwid-5.3.0.tar.gz
cd likwid-5.3.0
# Edit config.mk — six lines to change (note: uses ?= not = for PREFIX)
sed -i 's|^PREFIX ?= /usr/local|PREFIX = /apps/software/likwid/5.3.0|' config.mk
sed -i 's|^#HWLOC_INCLUDE_DIR = .*|HWLOC_INCLUDE_DIR = /apps/software/hwloc/2.7.2/include|' config.mk
sed -i 's|^#HWLOC_LIB_DIR = .*|HWLOC_LIB_DIR = /apps/software/hwloc/2.7.2/lib|' config.mk
sed -i 's|^#HWLOC_LIB_NAME = .*|HWLOC_LIB_NAME = hwloc|' config.mk
sed -i 's|^ACCESSMODE = accessdaemon|ACCESSMODE = perf_event|' config.mk
make -j2
make install
/apps/software/likwid/5.3.0/bin/likwid-topology --version 2>&1 | head -1
chandra — likwid 5.3.0 against hwloc 2.9.3
chandra — install likwid linked to hwloc 2.9.3 (different prefix!)
cd ~
tar -xzf /tmp/tarballs/likwid-5.3.0.tar.gz
cd likwid-5.3.0
# Same six edits — but different PREFIX and HWLOC paths
sed -i 's|^PREFIX ?= /usr/local|PREFIX = /apps/software/likwid/5.3.0-hwloc2.9|' config.mk
sed -i 's|^#HWLOC_INCLUDE_DIR = .*|HWLOC_INCLUDE_DIR = /apps/software/hwloc/2.9.3/include|' config.mk
sed -i 's|^#HWLOC_LIB_DIR = .*|HWLOC_LIB_DIR = /apps/software/hwloc/2.9.3/lib|' config.mk
sed -i 's|^#HWLOC_LIB_NAME = .*|HWLOC_LIB_NAME = hwloc|' config.mk
sed -i 's|^ACCESSMODE = accessdaemon|ACCESSMODE = perf_event|' config.mk
make -j2
make install
/apps/software/likwid/5.3.0-hwloc2.9/bin/likwid-topology --version 2>&1 | head -1

arjun and chandra install likwid to different prefixes — 5.3.0 and 5.3.0-hwloc2.9. This is intentional. Two copies of the same software compiled against different dependency versions. The modulefiles in Stage 2 point to their respective prefix.

1.3

Submit a SLURM job — with manual PATH exports

The software is installed. The only way to use it in a SLURM job is to manually export PATH and LD_LIBRARY_PATH in the job script. This is the pain Stage 2 eliminates. Write the job script exactly as shown — including the export lines.

arjun — write and submit job script
cat > ~/stage1_arjun.sh << 'EOF'
#!/bin/bash
#SBATCH --job-name=stage1-arjun
#SBATCH --ntasks=1
#SBATCH --output=/home/arjun/stage1_arjun_%j.out

# Manual environment wiring — this is what Stage 2 replaces
export PATH=/apps/software/likwid/5.3.0/bin:/apps/software/hwloc/2.7.2/bin:$PATH
export LD_LIBRARY_PATH=/apps/software/hwloc/2.7.2/lib:/apps/software/likwid/5.3.0/lib:$LD_LIBRARY_PATH

likwid-topology -s
EOF
sbatch ~/stage1_arjun.sh
watch squeue -u $USER
# Wait for COMPLETED — Ctrl+C to exit
cat ~/stage1_arjun_*.out
chandra — same pattern with hwloc 2.9.3 paths
cat > ~/stage1_chandra.sh << 'EOF'
#!/bin/bash
#SBATCH --job-name=stage1-chandra
#SBATCH --ntasks=1
#SBATCH --output=/home/chandra/stage1_chandra_%j.out

export PATH=/apps/software/likwid/5.3.0-hwloc2.9/bin:/apps/software/hwloc/2.9.3/bin:$PATH
export LD_LIBRARY_PATH=/apps/software/hwloc/2.9.3/lib:/apps/software/likwid/5.3.0-hwloc2.9/lib:$LD_LIBRARY_PATH

likwid-topology -s
EOF
sbatch ~/stage1_chandra.sh
cat ~/stage1_chandra_*.out

The job output file is the Stage 1 deliverable. It proves likwid-topology ran on the compute node. Record the output in your lab report.

2.1

Write the hwloc modulefile

arjun writes hwloc/2.7.2.lua. chandra writes hwloc/2.9.3.lua. Both files follow the same structure — only the version and path differ. Note prepend_path not setenv for PATH-type variables.

arjun — hwloc/2.7.2.lua
arjun — write /apps/modulefiles/hwloc/2.7.2.lua
mkdir -p /apps/modulefiles/hwloc
cat > /apps/modulefiles/hwloc/2.7.2.lua << 'EOF'
whatis("Name:        hwloc")
whatis("Version:     2.7.2")
whatis("Description: Hardware locality — topology detection and binding")

local root = "/apps/software/hwloc/2.7.2"

prepend_path("PATH",            root .. "/bin")
prepend_path("LD_LIBRARY_PATH", root .. "/lib")
prepend_path("MANPATH",         root .. "/share/man")
EOF
chandra — hwloc/2.9.3.lua
chandra — write /apps/modulefiles/hwloc/2.9.3.lua
mkdir -p /apps/modulefiles/hwloc
cat > /apps/modulefiles/hwloc/2.9.3.lua << 'EOF'
whatis("Name:        hwloc")
whatis("Version:     2.9.3")
whatis("Description: Hardware locality — topology detection and binding")

local root = "/apps/software/hwloc/2.9.3"

prepend_path("PATH",            root .. "/bin")
prepend_path("LD_LIBRARY_PATH", root .. "/lib")
prepend_path("MANPATH",         root .. "/share/man")
EOF

prepend_path adds to the front of PATH — it does not replace it. Using setenv on PATH would wipe the entire variable and the shell would stop finding system binaries. This is the single most common modulefile authoring mistake.

2.2

Write the likwid modulefile with depends_on

arjun's likwid modulefile declares it depends on hwloc/2.7.2. chandra's declares hwloc/2.9.3. The depends_on directive means Lmod loads hwloc automatically — the researcher never types it. The variant name in the file path (5.3.0-hwloc2.7 vs 5.3.0-hwloc2.9) makes the dependency visible in module avail.

arjun — write /apps/modulefiles/likwid/5.3.0-hwloc2.7.lua
mkdir -p /apps/modulefiles/likwid
cat > /apps/modulefiles/likwid/5.3.0-hwloc2.7.lua << 'EOF'
whatis("Name:        likwid")
whatis("Version:     5.3.0-hwloc2.7")
whatis("Description: Performance tools for x86 multicore — requires hwloc 2.7")

depends_on("hwloc/2.7.2")

local root = "/apps/software/likwid/5.3.0"

prepend_path("PATH",            root .. "/bin")
prepend_path("LD_LIBRARY_PATH", root .. "/lib")
EOF
chandra — write /apps/modulefiles/likwid/5.3.0-hwloc2.9.lua
cat > /apps/modulefiles/likwid/5.3.0-hwloc2.9.lua << 'EOF'
whatis("Name:        likwid")
whatis("Version:     5.3.0-hwloc2.9")
whatis("Description: Performance tools for x86 multicore — requires hwloc 2.9")

depends_on("hwloc/2.9.3")

local root = "/apps/software/likwid/5.3.0-hwloc2.9"

prepend_path("PATH",            root .. "/bin")
prepend_path("LD_LIBRARY_PATH", root .. "/lib")
EOF

Stage 3 of 5 · ~25 minutes

Spack

hwloc + likwid had one dependency each. OpenMPI has five. Doing that by hand would be Stage 1 repeated five times with interdependencies. Spack resolves the entire graph from a single command. Run spack spec first — before any compilation — and read the DAG. Then install. Then verify the Lmod integration picked up the generated modulefile automatically.

Slide anchor: Slides 12, 13, 14, 15 — How Spack builds · Read the DAG · Two hashes · The reproducibility artifact.

Item 44 — spack install with compiler variant

One Spack instance, shared. arjun installs OpenMPI first. When chandra runs the same spack install command, Spack will report the package is already installed — this is correct behaviour. Both arjun and chandra load the same binary via the same module. The hash ensures they get an identical build.

3.1

Read the dependency DAG — before installing anything

spack spec resolves the full dependency graph and prints it without building anything. Run this first. Read the output. Identify how many packages will be built and what compiler they all use.

arjun (or chandra) — inspect the DAG
source /apps/spack/share/spack/setup-env.sh
spack spec openmpi@4.1.5
openmpi@4.1.5%gcc@...
    ^hwloc@...%gcc@...        ← Spack resolves this version — you did not ask for it
    ^libfabric@...%gcc@...
    ^pmix@...%gcc@...
        ^libevent@...%gcc@...
    ^ucx@...%gcc@...
# Count the dependencies. Note that hwloc appears here too —
# Spack manages its own copy, separate from what you installed manually.

If you see something unexpected in the spec output — a wrong version, a missing variant — fix the spec before running spack install. spack spec takes seconds. A bad install takes 15 minutes before it fails.

arjun — install OpenMPI via Spack

This takes 6–15 minutes on t3.medium. Each dependency is built in order, progress is visible. The -j2 flag limits to 2 parallel compile jobs — t3.medium has 2 vCPU.

instructor interventions

Common wrong paths and redirect language — for Rajesh only. Do not share with learners.

Any learner Installs to /usr/local instead of /apps/software
When Stage 1 — learner omits --prefix from ./configure and the build installs to /usr/local/bin
Spring "Where did that install go? Run 'which lstopo'. Now SSH to the compute node and run which lstopo there. Do you see it?"
After /usr/local/bin is node-local. The compute node has no visibility into the head node's /usr/local. The entire point of /apps is NFS — every node sees it automatically. Re-run with --prefix=/apps/software/hwloc/VERSION/.
Any learner Uses setenv instead of prepend_path for PATH in modulefile
When Stage 2 — after module load, learner cannot run ls, cd, or other system commands
Spring "Run 'echo $PATH' after loading your module. What do you see? Now look at your modulefile — did you use setenv or prepend_path for PATH?"
After setenv replaces PATH entirely — the shell loses access to all system binaries. prepend_path adds to the front and preserves everything already there. Fix the modulefile, reload.
chandra Treats Spack cache hit as an error
When Stage 3 — chandra sees "already installed" message and thinks the install failed
Spring "Spack said it's already installed. Is that a problem? Run spack find openmpi — is it there? Run module avail openmpi — can you load it?"
After On a real facility, 50 research groups share one Spack OpenMPI — Spack builds it once. The hash guarantees arjun and chandra get identical binaries. This is the feature, not a bug.

Common wrong paths across all learners — redirect language:

Wrong path: Stage 2 module load works interactively but SLURM job shows "command not found"
Redirect: "Echo $MODULEPATH in the job script and check the output file. Is MODULEPATH set in the job environment? Add 'export MODULEPATH=/apps/modulefiles:$MODULEPATH' at the top of the job script."

Wrong path: module spider shows nothing after adding a new modulefile
Redirect: "module avail — does it show the module? module spider reads a cache. Run: /apps/lmod/lmod/lmod/libexec/update_lmod_system_cache_files -d /apps/lmod/cache -t /apps/lmod/cache/timestamp /apps/modulefiles"

Wrong path: learner checks Stage 1 SLURM output from the interactive terminal rather than the .out file
Redirect: "The deliverable is the SLURM output file — ~/stage1_USERNAME_JOBID.out. Show me that file. Running the command interactively proves nothing about the compute node environment."

Wrong path: Spack install hangs or OOM-kills on t3.medium
Redirect: "Check if you used -j4 instead of -j2. t3.medium has 2 vCPU — -j4 will saturate RAM. Run: spack install -j 2 openmpi@4.1.5"
