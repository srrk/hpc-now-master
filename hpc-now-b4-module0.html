section 0

Connect to the cluster

Enterprise IT analogy

You are SSH-ing into a jump host. The login node is the managed front door to the whole facility — functionally identical to a bastion in a corporate datacenter. Everything you do today passes through it. The controller and the compute node sit behind it, and you have no route to either.

Open a terminal and connect with your assigned username.

ssh <your-username>@mylab.hpc.now

Enter the password when prompted: hpcnow2026

You should see a password prompt, and that is correct here. On the production facilities you will operate later in this course, a password prompt means something is wrong — those use key-based authentication, and a prompt tells you your key was not accepted. This teaching cluster uses passwords deliberately, so nobody spends the first thirty minutes of week one debugging key registration. Note the difference now; you will need to read a password prompt as a fault soon enough.

If SSH refuses with "host key verification failed" — this cluster is rebuilt for each session, so the host key behind mylab.hpc.now changes even though the name does not. Your laptop remembers the old one and objects.

Clear the stale entry and reconnect:

# Run this on your laptop, not on the cluster
ssh-keygen -R mylab.hpc.now

# Then connect as normal
ssh <your-username>@mylab.hpc.now

A successful login looks like this:

[<your-username>@tb-login ~]$

You are on the login node. Everything from here runs in that shell.

If it does not work, read what you got. The password prompt returning again means the password or username is wrong. A connection refused or timed out means the address or the route, not your account. A hang with no prompt at all points at the network path. Three different failures, three different owners — telling them apart from the message alone is the skill this whole module is building.

section 1

Establish who you are here

Identity is a facility-wide fact, not a per-host one.

Enterprise IT analogy

A domain account. The same user object, the same SID, the same group memberships, on every server that trusts the directory. If it differs between two machines, you do not have an account problem — you have an integration problem, and that is a different team and a different fix.

1.1Read your own identity

whoami          # your username
id              # numeric identity and every group you belong to
groups          # the same group list, more readably
hostname        # which machine you are on

The output of id is the important one. It looks like this:

uid=3007(spendyal) gid=6003(chem) groups=6003(chem),6000(hpcusers)

1.2What each part means

uid=3007Your numeric user ID. The filesystem knows you by this number, not by your name.
gid=6003(chem)Your primary project group. Files you create belong to it by default.
groups=…Every group you are in. hpcusers is what grants you access to this facility at all.

Note your own numbers down. In section 4 you will run id again on a machine you have never logged into, and the numbers must be identical. If they were not, files your job wrote would come back unreadable to you — and the fault would be in the facility's identity configuration, not in your account.

section 2

Two filesystems, and what protects them

Discover the protection model. Do not assume it.

Enterprise IT analogy

A user's home share versus a working volume on a filer. Same protocol, same look in the shell, entirely different retention and backup policy. The mistake that costs people work is assuming the second is protected like the first — and on a real facility, nobody tells them otherwise until it is gone.

2.1Locate home, and see how much of it there is

pwd                 # you start in your home directory
ls -la ~
df -h ~             # which filesystem home lives on, and how big it is
du -sh ~            # how much of it you are using

Home is served over NFS from the headnode. It is small relative to the machine, it is shared by everyone, and — read this carefully — nothing on this cluster is backed up. Not home, not scratch. The facility's position on protection is published in the storage note:

cat /shared/facility/docs/storage-note.md

2.2Locate scratch, and prove it is a different thing

You have a working area at /scratch/$USER. Write to it, read it back, and then establish by inspection that it is not simply another directory on the same disk.

cd /scratch/$USER
echo "written by $USER at $(date)" > hello.txt
cat hello.txt

Now compare the two filesystems directly:

df -h ~ /scratch          # two rows — look at the device column
stat -f -c "%i  %n" ~ /scratch   # two different filesystem IDs
mount | grep -E "home|scratch"

Different devices, different filesystem IDs. They are separately served volumes that happen to appear next to each other in your shell. That is the point: on a real facility the difference between where you keep things and where you work is a difference in policy, and you can only see it by looking.

The trap here is assuming home is the working area, because on every system most people have administered, it was. Ask yourself what happens when four hundred compute nodes read from one NFS export at the same moment. You do not need the answer today — week seven is about exactly that — but notice the question exists.

section 3

Compose a software environment

Software here is assembled at need, not installed once.

Enterprise IT analogy

Not a package manager. Closer to loading a profile or activating a virtual environment — except several mutually incompatible versions of the same product are installed side by side, permanently, and each user composes the combination they need for the next hour. Nobody uninstalls anything, ever.

3.1See what is published

module avail

You will see the facility's own tree alongside what the platform ships. Two versions of CMake are published for this lab.

3.2Load one, and confirm where it came from

which cmake                    # before loading — probably nothing, or a system copy
module load cmake/3.26.5
module list                    # what is loaded now
which cmake                    # after loading
cmake --version

The path which reports should be under /shared/facility/software/ — the facility's tree, not /usr/bin. If it resolves to a system path, the module did not load or something else shadowed it. Loading a module changes nothing on disk; it edits your PATH and a handful of other variables in this shell only.

3.3Now load the second version, while the first is still loaded

module load cmake/3.29.8

Read what comes back, then look at the state you are actually in:

module list
which cmake
cmake --version

Say out loud what just happened. Either the system refused the second load because it conflicts with the first, or it swapped one for the other underneath you. Both are the same lesson from opposite sides: two versions of one application cannot be active at once, and the module system is what enforces that. A user whose job mysteriously ran against the wrong version has almost always hit this, and week nine takes it apart properly.

# Clear everything and start clean — a habit worth having
module purge
module list

section 4

Can your scheduler client see a controller?

The first fork in every scheduling incident you will ever handle.

Enterprise IT analogy

"The service is down" versus "my client cannot reach the service." You have made this distinction a thousand times with a monitoring agent or a backup client. It is the same distinction here, and it is the first thing to establish when someone tells you the queue is broken.

4.1Ask the scheduler what the facility looks like

sinfo

You should get the four partitions from the table at the top of this page, each with a node count and a state. You are not expected to interpret the states yet — only to establish that your client got an answer from a controller. An error naming a connection means client-to-controller. An empty but successful response means configuration. command not found means the client is not on your path.

sinfo -N -l                        # one line per node, with detail
scontrol show partition debug      # the full configuration of one partition

In that last output, find MaxTime. Note the value. It is the whole of section 9.

4.2Prove your identity reaches the compute node

You cannot log in to the compute node — try it and you will be refused, which is correct. But you can ask the scheduler to run a command there on your behalf.

srun -p standard --time=00:01:00 id
srun -p standard --time=00:01:00 hostname

Compare that id output against what you wrote down in section 1. Same UID, same GID, same groups — on a machine you have never logged into and cannot log into. That is what "your identity is a facility-wide fact" means, and it is why your job can write a file on the compute node that you can read afterwards from here.

If the queue is busy, srun will wait for its turn before printing anything. That is not a hang. Section 7 is about exactly that.

section 5

Self-check, and log what you did

Close the first lab on the two habits that carry the rest of the course.

5.1Run the facility self-check

tb-selfcheck

Seven checks, one line each, PASS or FAIL with a reason. Every item should pass. If one does not, the message names what is wrong — work back through the section of this runbook that covers it rather than working around it. In ten weeks the person seeing that message will be a real user, and you will be the one who has to know what it means.

Keep the output. Your instructor will ask for it.

5.2Write your first change-log entry

This facility keeps a shared change log. From week five onward, every privileged action you take is preceded by a line in it. Today you log something that could not possibly have harmed anything — which is exactly the point. The discipline has to be automatic before it is needed.

tb-changelog "connected to cluster, verified account, ran selfcheck"

# Read the log — everyone's entries are visible to everyone
cat /shared/facility/changelog/m0-changelog.tsv

Four things belong in every entry, forever: who, what, when, why. The wrapper handles the first three.

Before the break, write down your account in prose. Your identity and groups, where home is and what protects it, where scratch is and what does not, how software is composed, and what the scheduler told you. Half a page. You will be asked to reproduce it from memory next week, and the gap between the two is the actual measurement.

section 6

Write and submit your first job

From here you are a user, not an operator. Behave accordingly.

Change of role. For the rest of this runbook you are a new researcher at this facility — week one, a small piece of work to run, no particular interest in how the machine works. Do not read scheduler documentation beyond this page. Do not tune anything. When something is slow, do not intervene. The friction is the content.

Enterprise IT analogy

A batch job submitted to a scheduler, with a resource request attached. You have written the equivalent — a scheduled task with a service account and a timeout. The difference is that here the request is a declaration the scheduler plans around, and asking for more than you need does not make your work faster. It makes it wait longer.

6.1Write the script

Work in your scratch area. Create a file called first-job.sh with any editor — nano, vi, or the block below pasted straight into your shell.

cd /scratch/$USER

cat > first-job.sh << 'EOF'
#!/bin/bash
#SBATCH --job-name=first-job
#SBATCH --partition=standard
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --time=00:02:00
#SBATCH --output=first-job-%j.out

echo "Job $SLURM_JOB_ID running as $(whoami) on $(hostname)"
echo "Started at $(date)"

module load cmake/3.26.5
cmake --version

sleep 30
echo "Finished at $(date)"
EOF

chmod +x first-job.sh
cat first-job.sh

Read the #SBATCH lines. They are not comments to the shell — they are your resource request, read by the scheduler before anything runs. One node, one task, two minutes, output named after the job ID. That is the whole declaration.

Note that the job loads its own module. The compute node does not inherit your shell.

6.2Submit it

sbatch first-job.sh
Submitted batch job 42

Write that number down. The job ID is the only handle a user has on their work. Every question you ask about this job from now on uses it.

If submission is rejected outright, that is either syntax or policy, and the two read differently. If it hangs, that points at the controller, not at your script.

section 7

Watch it pend, run and disappear

Pending is a normal state. The reason field is the scheduler explaining itself.

7.1Look at the queue

squeue -u $USER

Run it repeatedly. Watch the ST column change. With twelve people and two cores, most of you will see PD — pending — before you see anything else.

# The reason field, spelled out
squeue -u $USER -o "%.8i %.10P %.12j %.3t %.10M %R"

# Or watch it live — Ctrl-C to stop
watch -n 5 "squeue -u $USER"

7.2The states, and the one people miss

PD · pendingAccepted, waiting. The last column tells you what it is waiting for.
R · runningAllocated and executing on a compute node.
CG · completingFinished, being cleaned up. Usually too brief to catch.
goneA finished job leaves the active queue entirely. It has not vanished.

That last one catches nearly everyone. You will run squeue, see nothing, and wonder what happened to your job. Nothing happened to it — it finished. The active queue shows active work. Section 8 is how you ask about work that is already done.

Do not intervene. If your job sits pending, leave it. Experienced operators find this genuinely difficult — the instinct is to cancel, resubmit, adjust something. Notice the instinct. Intervening in a scheduler that is working correctly is one of the more expensive habits you can bring into this job, and it starts here.

section 8

Find your output, and what the job consumed

The facility records what happened. The record is evidence.

8.1Retrieve the output

cd /scratch/$USER
ls -la first-job-*.out
cat first-job-<JOBID>.out

The file is named against the job ID and written to the directory you submitted from. Confirm it holds what you expected — the hostname of the compute node, your username, and the CMake version the job loaded for itself.

Look at the hostname in that output. Your job ran somewhere you have never logged in, as you, and left a file you can read. Section 4 told you that would happen; this is the evidence.

8.2Ask what it actually used

scontrol show job <JOBID>

In that output, find and compare:

TimeLimitWhat you asked for
RunTimeWhat you actually used
NumCPUsWhat was allocated to you
JobState / ExitCodeHow it ended — 0:0 is success

You asked for two minutes and used well under one. That gap is not free: the scheduler planned around the number you gave it. Do not correct it today — just notice that the request and the reality are different things, and that the facility knows both.

# A persistent record of every finished job on this facility
grep $USER /shared/facility/logs/jobcomp.log

The record is first of all evidence of what your job did. Later in the course it becomes an accounting question; today it is simply a fact the facility keeps.

section 9

Ask for something the facility cannot give you

Read the refusal as information, not as an error.

You are still a user. Submit a second job — the same trivial work, but sent to the debug partition asking for thirty minutes of wall clock.

9.1Submit it

cd /scratch/$USER

cat > second-job.sh << 'EOF'
#!/bin/bash
#SBATCH --job-name=second-job
#SBATCH --partition=debug
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --time=00:30:00
#SBATCH --output=second-job-%j.out

echo "If you are reading this, something is very wrong"
EOF

sbatch second-job.sh

9.2Watch what happens

squeue -u $USER
squeue -j <JOBID> -o "%.8i %.10P %.3t %R"

Wait. Check again. Check a third time. It will not start.

Before you read any further, write down — in the words you would use to a colleague, not in technical language — what the system told you and what you would do next if nobody were here to ask. Three or four sentences. Do this now, before you diagnose anything. Keep it; your instructor will ask for it, and the sentence you just wrote is the ticket text you will be receiving for the rest of your career.

9.3Now diagnose it

Three commands. In this order.

# 1 — What is the scheduler saying? Read the last column.
squeue -j <JOBID> -o "%.8i %.10P %.3t %R"

# 2 — What does that partition actually permit?
scontrol show partition debug | grep MaxTime

# 3 — What did you ask for?
grep time second-job.sh

Three links, one chain. The reason field names a partition limit — which rules out contention and rules in your request. The partition configuration confirms the ceiling. Your own script shows the request that exceeded it.

This is a working scheduler declining an impossible request. No operator intervention will start this job. Nothing is stuck, nothing is broken, nothing needs restarting. The request is simply not satisfiable in that partition, and the system said so immediately and precisely — you just had not read it yet.

Most of the "the queue is stuck" tickets you will handle from week five onward are exactly this. The ability to see it at a glance starts here.

9.4Clean up after yourself

scancel <JOBID>
squeue -u $USER        # confirm nothing of yours is left queued

Try cancelling somebody else's job while you are here. It will fail, and it is supposed to. On a shared facility you can only touch your own work — the enforcement is the scheduler's, not etiquette.
