Lab 8 / 11 · 15 minutes · Processes

Process Observation — Reading What Is Running

Follows: what a process is, ps, process states, signals, top, htop, pstree.

Setup. Log into mylab.hpc.now and confirm your prompt. No special directory needed — start from your home directory.

Ex 1

Read the process table and identify states

Run ps aux and read the STAT column. Identify at least one process in S state (sleeping — most processes). Look for any D or Z state entries and note them.

ps aux | head -20
Find processes by state
ps aux | awk '{print $8}' | sort | uniq -c | sort -rn
Expected output
Count of each STAT value on this system.
S and Ss will dominate — most processes are sleeping.
R or R+ may appear briefly for active processes.

D state means waiting on kernel I/O — cannot be killed with any signal while in this state. If you see one, note its PID and COMMAND.

Ex 2

Trace the PPID chain from your shell back to PID 1

Find your current shell's PID, then trace its parent chain up to PID 1. Every step should show a recognisable process — sshd, systemd, or a session manager.

echo "My shell PID: $$"
ps -ef | awk -v pid=$$ 'BEGIN{p=pid} p!=0{for(i=1;i<=NF;i++) printf $i" "; print ""; if($2==p){p=$3}}'

Or trace it manually step by step — simpler and clearer:

ps -f -p $$                 # your shell — note PPID
ps -f -p <PPID from above>   # its parent — note PPID again
ps -f -p <PPID from above>   # repeat until PPID is 1

Replace <PPID from above> with the actual number from each step. The chain ends at PID 1 — systemd.

Ex 3

Find the top five memory consumers

ps --sort=-rss -ef | head -6
Expected output
Header row then five processes sorted by RSS descending.
On a small cloud instance systemd, sshd, and kernel threads
typically lead. RSS is physical memory in use.
Ex 4

Locate your own shell in the process tree

pstree -p | grep -A 2 -B 2 "$$"

Or view the full tree:

pstree -p $USER

Your shell appears under sshd, which appears under systemd. This is the tree rooted at PID 1 that the slides described.

Ex 5

Send SIGTERM to a test process — verify clean exit

Create a background sleep process, send it SIGTERM, confirm it exits.

sleep 300 &                    # start background process
TESTPID=$!                      # capture its PID
echo "Test PID: $TESTPID"
ps -f -p $TESTPID               # confirm it is running
kill $TESTPID                   # send SIGTERM (default)
sleep 1
ps -f -p $TESTPID 2>/dev/null || echo "Process is gone"
Expected output
Process is gone

SIGTERM gave the process the opportunity to clean up and exit. For sleep this is immediate. For a real daemon it might take a few seconds.

Ex 6

Send SIGHUP to sshd — confirm it reloads without dropping your session

SIGHUP is the conventional "reload configuration" signal for daemons. sshd interprets it as a reload — it re-reads sshd_config and closes no existing connections.

SSHD_PID=$(systemctl show sshd --property=MainPID --value)
echo "sshd main PID: $SSHD_PID"
sudo kill -HUP $SSHD_PID
journalctl -u sshd -n 5 --no-pager
Expected output
Recent sshd journal entries including a "Received SIGHUP;
restarting" or "Server listening" message.
Your current session remains active throughout.

Your session survived because SIGHUP reloads the listener — it does not terminate existing authenticated connections. This is why daemons repurpose SIGHUP for configuration reload rather than using it to exit.

Checkpoint — Section 8 Type done in chat when this passes
ps -ef | awk '{print $3}' | sort -n | head -5 && echo "Section 8 complete"
Expected: a list of PPIDs — PID 1 should appear multiple times as the parent of system processes. Followed by Section 8 complete.

Lab 9 / 11 · 20 minutes · Services

Services — systemctl and Unit Files

Follows: systemd, systemctl verbs, is-active vs is-enabled, unit file anatomy.

Ex 1

Read the full status output for sshd — every line

systemctl status sshd
Expected output — read each section
● sshd.service - OpenSSH server daemon
     Loaded: loaded (/usr/lib/systemd/system/sshd.service; enabled; ...)
     Active: active (running) since ...
   Main PID: <pid> (sshd)
      Tasks: ...
     Memory: ...
     CGroup: /system.slice/sshd.service
             └─<pid> sshd: /usr/sbin/sshd -D [listener]
Recent log lines follow...

Loaded tells you where the unit file is. Active tells you the current runtime state. The CGroup line shows what processes systemd is tracking under this unit.

Ex 2

Confirm sshd is both active AND enabled — understand the difference

systemctl is-active sshd
Expected output
active
systemctl is-enabled sshd
Expected output
enabled

is-active answers: running right now? is-enabled answers: will it start at the next boot? These are independent questions with independent answers.

Ex 3

Check for failed units

systemctl list-units --failed
Expected output
On a healthy system: "0 loaded units listed."
On a system with failures: one or more units listed with
LOAD=loaded, ACTIVE=failed, SUB=failed.

Run this as part of your morning routine on any production system. A failed unit that nobody noticed is a common source of slow-developing incidents.

Ex 4

Read the sshd unit file — identify Type, Restart, and WantedBy

systemctl cat sshd

Find and note the answers to these three questions in the output:

What to find: What is the Type= value? What does that mean for how systemd tracks this service? Does a Restart= directive exist? What is WantedBy= — what does this tell you about when sshd starts at boot?

Ex 5

Create a simple oneshot service unit file

Write a unit file that runs a single command and exits. This is the simplest possible service — it demonstrates the unit file structure without requiring a persistent daemon.

sudo tee /etc/systemd/system/hello-lab.service << 'EOF'
[Unit]
Description=Hello Lab — oneshot test service

[Service]
Type=oneshot
ExecStart=/bin/echo "Hello from systemd on mylab.hpc.now"
RemainAfterExit=yes

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload
systemctl status hello-lab
Expected output
● hello-lab.service - Hello Lab — oneshot test service
     Loaded: loaded (/etc/systemd/system/hello-lab.service; disabled; ...)
     Active: inactive (dead)

Loaded confirms systemd found and parsed the unit file. Active shows it has not been started yet. daemon-reload is required after creating any new unit file — without it, systemd does not see the file.

Ex 6

Start the service and verify with status

sudo systemctl start hello-lab
systemctl status hello-lab
Expected output
● hello-lab.service - Hello Lab — oneshot test service
     Loaded: loaded (/etc/systemd/system/hello-lab.service; disabled; ...)
     Active: active (exited)
    Process: <pid> ExecStart=/bin/echo Hello from systemd on mylab.hpc.now (code=exited, status=0/SUCCESS)

... echo[<pid>]: Hello from systemd on mylab.hpc.now

active (exited) is the correct state for a oneshot service with RemainAfterExit=yes — it ran to completion and systemd considers it still "up." The echo output appears in the status log lines.

Ex 7

Enable the service — confirm the symlink appears

sudo systemctl enable hello-lab
ls -la /etc/systemd/system/multi-user.target.wants/ | grep hello
Expected output
Created symlink /etc/systemd/system/multi-user.target.wants/hello-lab.service → /etc/systemd/system/hello-lab.service.

lrwxrwxrwx 1 root root ... hello-lab.service -> /etc/systemd/system/hello-lab.service

This symlink is how enable works. When multi-user.target activates at boot, systemd follows these symlinks and starts everything they point to.

Ex 8

Disable and stop — confirm both states change

sudo systemctl disable --now hello-lab
systemctl is-active hello-lab
systemctl is-enabled hello-lab
Expected output
inactive
disabled

disable --now stops the service AND removes the boot symlink in one command. Both is-active and is-enabled change independently — confirm both.

Checkpoint — Section 9 Type done in chat when this passes
systemctl is-active sshd && systemctl is-enabled sshd && echo "Section 9 complete"
Expected: active · enabled · Section 9 complete — three lines, each confirming a different fact about sshd.

Lab 10 / 11 · 15 minutes · Logs

Logs — journalctl, /var/log, and dmesg

Follows: journald, journalctl flags, /var/log files, dmesg and the kernel ring buffer.

Ex 1

Read the last twenty sshd entries — identify each field

journalctl -u sshd -n 20 --no-pager
Expected output — read each column
Apr 25 09:01:15 mylab sshd[847]: Accepted publickey for chandra from 10.0.0.5 port 52341 ssh2

Timestamp · hostname · unit[PID] · message content
Every line has the same structure. The PID in brackets
identifies which sshd worker handled this event.
Ex 2

Filter to errors only — since today

journalctl -p err --since today --no-pager
Expected output
On a healthy system: few or no entries.
Any entries here are worth reading — priority 3 (err)
and lower (crit, alert, emerg) are genuinely significant.

-p err matches priority 3 and lower numbers — more severe. Priority 4 (warning) and above are excluded. This is the filter to run when something seems wrong.

Ex 3

Check the previous boot for errors

journalctl --list-boots --no-pager
Expected output
-1  <boot-id>  Mon 2026-04-24 ... — Mon 2026-04-24 ...
 0  <boot-id>  Tue 2026-04-25 ... — Tue 2026-04-25 ...

-1 = previous boot · 0 = current boot
journalctl -b -1 -p err --no-pager

This is invaluable after a system crash or unexpected reboot. -b -1 targets the boot that ended — -p err filters to the significant entries only.

If something goes wrong

If --list-boots shows only one boot entry, the journal may be volatile — not persisted to disk. Run ls /var/log/journal/. If the directory is empty or absent, only the current boot is stored.

Ex 4

Read /var/log/secure — identify recent SSH logins

sudo tail -20 /var/log/secure
Expected output
Apr 25 09:01:15 mylab sshd[847]: Accepted publickey for chandra ...
Apr 25 09:03:22 mylab sshd[848]: Accepted publickey for sujith ...

Lines show: timestamp · host · service · event type · username · source IP

Identify the last three successful logins by timestamp and username. /var/log/secure is the traditional auth log — the same information is also in the journal via journalctl -u sshd.

If /var/log/secure does not exist

On some systems rsyslog is not configured to write text files. Use journalctl -u sshd -n 20 --no-pager instead — same information, journal source.

Ex 5

Scan dmesg for hardware or driver complaints

dmesg -T | grep -i error | head -10
dmesg -T | grep -i oom | head -10
Expected output
On a healthy cloud instance: few or no entries.
Any OOM killer entries are significant — they show
which process was killed and why.

dmesg -T shows human-readable timestamps instead of seconds-since-boot. The raw format requires mental arithmetic nobody wants to do.

Ex 6

Check journal disk usage

journalctl --disk-usage
Expected output
Archived and active journals take up <size> in the filesystem.

On a fresh lab instance this will be small. On production systems that have been running for months, journal storage can grow to several gigabytes. journalctl --vacuum-time=30d trims entries older than 30 days when needed.

Checkpoint — Section 10 Type done in chat when this passes
journalctl -u sshd --since "5 minutes ago" --no-pager | wc -l && echo "Section 10 complete"
Expected: a number (count of sshd entries in the last 5 minutes) followed by Section 10 complete. If the count is 0, open a second SSH session to generate entries, then re-run.

Lab 11 / 11 · 10 minutes · Packages

Packages — dnf, Repositories, and Verification

Follows: dnf verbs, repository configuration, GPG verification, versionlock awareness.

Ex 1

Count installed packages

dnf list installed | wc -l
Expected output
A number between 300 and 800 on a typical minimal cloud instance.
The first line is a header — actual package count is this number minus 1.
Ex 2

Find which package owns /usr/bin/ss

dnf provides /usr/bin/ss
Expected output
iproute-<version>.<arch> : IP routing utilities
Repo        : @System
Matched from:
Filename    : /usr/bin/ss

dnf provides is the search that answers "I need this file — which package do I install?" It works for files not yet on the system too — searching the repository metadata rather than only installed packages.

Ex 3

List active repositories

dnf repolist
Expected output
repo id                    repo name
baseos                     Rocky Linux 9 - BaseOS
appstream                  Rocky Linux 9 - AppStream
extras                     Rocky Linux 9 - Extras

Each enabled repository is listed with its ID and name.
The ID is what you use with --enablerepo= and --disablerepo=.
Ex 4

Read the transaction history

dnf history
Expected output
ID  | Command              | Date and time       | Action(s) | Altered
------------------------------------------------------------------
 5  | install vim-enhanced | 2026-04-25 09:14    | Install   |       1
 4  | update               | 2026-04-25 08:01    | I, U      |      47
...

Each row is one transaction — install, remove, or update.
dnf history info 1               # detail of transaction 1

dnf history undo <id> reverses any transaction in this list. This is how you roll back an update that broke something — without it you would reinstall from scratch.

Ex 5

Read the full info output for an installed package

dnf info openssh-server
Expected output — read every field
Name         : openssh-server
Epoch        : ...
Version      : ...
Release      : ...
Architecture : x86_64
Size         : ...
Source       : ...
Repository   : @System
Summary      : An open source SSH server daemon
URL          : ...
License      : ...
Description  : ...

Repository shows @System for installed packages — meaning it came from a repository but is currently installed. The URL and License fields tell you where the upstream source lives.

Ex 6

Read a .repo file — identify gpgcheck and enabled

ls /etc/yum.repos.d/
cat /etc/yum.repos.d/rocky.repo 2>/dev/null || \
cat /etc/yum.repos.d/*.repo | head -30

Find and confirm:

What to verify: Is gpgcheck=1 set? Is enabled=1 set? Where does the gpgkey= line point? These three settings control whether packages from this repository are trusted and whether dnf will use it.

Never set gpgcheck=0 to work around a signature error. Find out why the signature failed — either import the correct key or verify the source of the package.
