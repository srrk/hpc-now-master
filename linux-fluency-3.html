Lab 12 / 14 · 15 minutes · Users

Identity Files, User Management, and Resolution

Follows: /etc/passwd, /etc/shadow, /etc/group, UIDs as integers, useradd, usermod, userdel, su, sudo, id, getent, NSS awareness.

Setup. Log into mylab.hpc.now and confirm your prompt. You will need sudo for several exercises in this section — your account is in the wheel group and has full sudo access.

Ex 1

Read /etc/passwd — count lines, find your entry, identify system accounts

wc -l /etc/passwd                    # count all accounts
grep $(whoami) /etc/passwd            # find your own entry
grep '/sbin/nologin' /etc/passwd | head -5  # system accounts
Expected output — your entry
chandra:x:1001:1001::/home/chandra:/bin/bash

Seven colon-separated fields:
username : x : UID : GID : GECOS : home : shell

Find three system accounts with /sbin/nologin as their shell. Note that they have low UIDs — typically below 1000. These are service accounts that should never log in interactively.

The file is world-readable. ls and ps read it to translate UIDs to names. Every user on the system can see every account listed here.

Ex 2

Run id — read every field including all supplementary groups

id
id $(whoami)
Expected output — Chandra
uid=1001(chandra) gid=1001(chandra) groups=1001(chandra),10(wheel)

uid    — numeric UID and the name the system resolves it to
gid    — primary group
groups — all supplementary groups, numeric and named

The wheel group gives sudo access on RHEL-family systems. If your account did not have this, the sudo exercises below would fail.

Ex 3

Use getent — confirm it matches /etc/passwd

getent passwd $(whoami)
getent group wheel
getent hosts mylab.hpc.now
Expected output
chandra:x:1001:1001::/home/chandra:/bin/bash   ← matches /etc/passwd
wheel:x:10:chandra,sujith,yogaraj              ← group members
192.168.x.x     mylab.hpc.now                  ← hostname resolved

On this lab instance, getent and grep /etc/passwd give the same answer because identity is local. On an HPC cluster with LDAP or SSSD, grep would miss accounts that only exist in the central directory. getent is always the correct tool.

Ex 4

Create a test user with an explicit UID

sudo useradd -m -s /bin/bash -u 9001 testuser
grep testuser /etc/passwd
ls -la /home/testuser/
Expected output
testuser:x:9001:9001::/home/testuser:/bin/bash

/home/testuser/ exists with correct ownership
drwx------ 2 testuser testuser 62 Apr 25 10:01 /home/testuser/

The -m flag created the home directory. Without it the home path would be in /etc/passwd but would not physically exist — a common source of login failures.

If useradd fails

If UID 9001 is already in use, try 9002 or 9003. Check with getent passwd 9001 — if it returns output, that UID is taken.

Ex 5

Add testuser to a supplementary group using usermod -aG

sudo groupadd labgroup
sudo usermod -aG labgroup testuser
id testuser
grep testuser /etc/group
Expected output
uid=9001(testuser) gid=9001(testuser) groups=9001(testuser),<gid>(labgroup)

/etc/group shows testuser in the labgroup member list

The -a in -aG is not optional. Run sudo usermod -G labgroup testuser without -a on a user with multiple groups — it replaces the entire supplementary group list with just labgroup. Always use -aG to append.

Ex 6

Use sudo to run a command as root — confirm the log entry

sudo whoami
sudo -i whoami
Expected output
root
root
sudo journalctl -u sudo --since "5 minutes ago" --no-pager 2>/dev/null || \
  sudo grep $(whoami) /var/log/secure | tail -5
Expected output
Entry showing your username, the command run, and the TTY.
Every sudo invocation is logged. This is how audit trails work.

sudo authenticates with your own password and logs your identity. su - authenticates with root's password and leaves a less granular audit trail. This is why sudo is preferred in operational environments.

Expected: your passwd entry · your full id output with UID, GID, and groups · Section 12 complete. Both commands should return your account — same UID, same groups.

Clean up. Remove the test user created in Exercise 4 before moving on.

sudo userdel -r testuser
sudo groupdel labgroup
grep testuser /etc/passwd        # should return nothing

Lab 13 / 14 · 20 minutes · SSH

Keys, Config, and the Server Side

Follows: SSH client basics, known_hosts, key-based authentication, ssh-keygen, installing keys, server-side permissions, ssh-agent, ~/.ssh/config, sshd reading and validation.

Ex 1

Generate an Ed25519 key pair with a passphrase

Generate a new key pair specifically for this lab. Use a passphrase — you will use the agent in Exercise 5 so you only need to type it once.

ssh-keygen -t ed25519 -f ~/.ssh/id_lab -C "$(whoami)@lab-exercise"
Expected output
Generating public/private ed25519 key pair.
Enter passphrase (empty for no passphrase): <type a passphrase>
Enter same passphrase again:
Your identification has been saved in /home/chandra/.ssh/id_lab
Your public key has been saved in /home/chandra/.ssh/id_lab.pub
ls -la ~/.ssh/id_lab*
Expected output
-rw------- 1 chandra chandra  411 Apr 25 10:15 /home/chandra/.ssh/id_lab
-rw-r--r-- 1 chandra chandra   97 Apr 25 10:15 /home/chandra/.ssh/id_lab.pub

Private key is 0600 — only you can read it. Public key is 0644 — world-readable, safe to share. The private key never leaves this machine.

Ex 2

Install the public key to your own account — verify passwordless connection

Install the lab key into your own authorized_keys on mylab.hpc.now. Since you are already on the host, do it directly rather than over the network.

cat ~/.ssh/id_lab.pub >> ~/.ssh/authorized_keys
cat ~/.ssh/authorized_keys
Expected output
ssh-ed25519 AAAA...longstring... chandra@lab-exercise

One public key per line. Multiple keys are allowed — one per device or context.

Now test that key-based connection works from your current session:

ssh -i ~/.ssh/id_lab -o PasswordAuthentication=no $(whoami)@mylab.hpc.now whoami
Expected output
chandra

Connection succeeded using the key — no password prompt.
If the connection asks for a password instead of using the key

Check permissions first: ls -la ~/.ssh/. The ~/.ssh/ directory must be 0700 and authorized_keys must be 0600. If either is group- or world-writable, sshd refuses to use the keys silently.

Fix: chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys

Ex 3

Verify ~/.ssh/ and ~/.ssh/authorized_keys permissions

ls -la ~/.ssh/
stat ~/.ssh/ | grep Access
stat ~/.ssh/authorized_keys | grep Access
Expected output
drwx------ 2 chandra chandra  ...  .ssh/         ← 0700
-rw------- 1 chandra chandra  ...  authorized_keys ← 0600
-rw------- 1 chandra chandra  ...  id_lab          ← 0600
-rw-r--r-- 1 chandra chandra  ...  id_lab.pub      ← 0644

If any of these are wrong, fix them now before proceeding. A group-writable ~/.ssh/ makes sshd refuse all key authentication with no error message to the user.

Ex 4

Add an entry to ~/.ssh/config — connect using only the alias

cat >> ~/.ssh/config << 'EOF'

Host mylab
    HostName mylab.hpc.now
    User chandra
    IdentityFile ~/.ssh/id_lab
    ServerAliveInterval 60
EOF

Replace User chandra with your own username if you are Sujith or Yogaraj.

chmod 600 ~/.ssh/config
cat ~/.ssh/config
ssh mylab whoami
Expected output
chandra

ssh mylab expands to the full connection parameters.
The alias saves typing and enforces consistent connection options.
Ex 5

Start ssh-agent, add your lab key, confirm it is loaded

eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_lab       # prompts for passphrase once
ssh-add -l                   # list loaded keys
Expected output after ssh-add -l
256 SHA256:... chandra@lab-exercise (ED25519)

The key is in the agent. Subsequent connections use the agent —
no passphrase prompt until the agent is cleared or the session ends.
ssh mylab whoami             # no passphrase prompt this time
Ex 6

Read /etc/ssh/sshd_config — identify key directives

sudo grep -v '^#' /etc/ssh/sshd_config | grep -v '^$'

Find and note the values for these directives:

What to find: PermitRootLogin — can root SSH in directly? PasswordAuthentication — are passwords accepted? PubkeyAuthentication — are keys enabled? AuthorizedKeysFile — where does sshd look for authorised keys?

The effective configuration is what matters — directives can be set in the main file or in drop-in files under /etc/ssh/sshd_config.d/. Check both.

Ex 7

Validate the sshd config — confirm it is error-free

sudo sshd -t
echo "Exit code: $?"
Expected output
Exit code: 0

No output and exit code 0 means the config is valid.
Any output means a syntax error — do not restart sshd until fixed.

Always run sshd -t before restarting sshd. An invalid config means sshd will not start after the restart — the operator is locked out. This validation step prevents that outcome.

Ex 8

Check the last ten sshd journal entries — find your key-based login

journalctl -u sshd -n 20 --no-pager
Expected output — look for this pattern
Apr 25 10:15:xx mylab sshd[pid]: Accepted publickey for chandra from ... ssh2: ED25519 SHA256:...

"Accepted publickey" confirms key authentication succeeded.
Compare to "Accepted password" — that would mean password auth.
Your exercise 2 connection should appear in this log.
Checkpoint — Section 13 Type done in chat when this passes
ssh-add -l && cat ~/.ssh/authorized_keys | wc -l && echo "Section 13 complete"
Expected: at least one key listed in the agent · a non-zero count of installed public keys · Section 13 complete. Both must return non-zero output confirming the key infrastructure is in place.

Lab 14 / 14 · 20 minutes · Networking

ip, ss, DNS, curl, and Firewall

Follows: CIDR notation, ip link/addr/route, ss listening and established, ports, DNS resolution path (/etc/hosts, /etc/resolv.conf, getent, dig), curl, openssl s_client, firewall-cmd, ping, traceroute.

Ex 1

Read the instance's IP address and determine the network size

ip addr
ip addr show | grep 'inet ' | grep -v '127.0.0.1'
Expected output
inet 10.x.x.x/20 brd 10.x.x.255 scope global dynamic eth0

The /20 (or whatever mask appears) tells you the network size.
/20 = 4096 addresses · /24 = 256 addresses · /16 = 65536 addresses

Read the CIDR mask from the output. Determine how many addresses are in the network. Note whether the address is from a private range (10.x.x.x, 172.16-31.x.x, or 192.168.x.x).

Ex 2

Read the routing table — identify the default gateway and simulate a lookup

ip route
Expected output
default via 10.x.x.1 dev eth0 proto dhcp metric 100
10.x.x.0/20 dev eth0 proto kernel scope link src 10.x.x.x metric 100

"default via" is the gateway — all non-local traffic goes here.
The second line is the directly-attached network — no gateway needed.
ip route get 8.8.8.8
Expected output
8.8.8.8 via 10.x.x.1 dev eth0 src 10.x.x.x uid <uid>

The kernel answers: to reach 8.8.8.8 go via the default gateway,
using source address 10.x.x.x out of interface eth0.
Ex 3

List all listening services — identify which are reachable from outside

ss -tlnp
Expected output
State   Recv-Q  Send-Q  Local Address:Port  Peer Address:Port  Process
LISTEN  0       128           0.0.0.0:22          0.0.0.0:*   users:(("sshd",...))
LISTEN  0       128              [::]:22             [::]:*   users:(("sshd",...))

0.0.0.0:22 and [::]:22 — sshd listens on all interfaces (IPv4 and IPv6)
Reachable from outside. 127.0.0.1:port would be loopback only.

For each listening service: is it bound to 0.0.0.0 (all interfaces — reachable from outside) or 127.0.0.1 (loopback only — not reachable from outside)? This distinction is the first question when investigating connectivity.

Ex 4

Test the full DNS resolution path

cat /etc/hosts                      # static overrides — checked first
cat /etc/resolv.conf                 # DNS server configuration
getent hosts mylab.hpc.now           # full NSS chain lookup
Expected output — getent hosts
10.x.x.x     mylab.hpc.now

This matches the IP address from ip addr in Exercise 1.
getent uses the full resolution chain — /etc/hosts first, then DNS.
dig example.com                      # bypass NSS, query DNS directly
dig @8.8.8.8 example.com            # query a specific DNS server
Expected output — dig example.com
;; ANSWER SECTION:
example.com.    300    IN    A    93.184.216.34

;; Query time: x msec
;; SERVER: x.x.x.x#53

dig shows which DNS server answered and how long it took.
If getent works but dig fails — DNS is unreachable but /etc/hosts resolved it.
If dig is not installed

Install it: sudo dnf install -y bind-utils. The bind-utils package provides dig, host, and nslookup.

Ex 5

Use curl to test HTTP connectivity and inspect TLS

curl -s -o /dev/null -w "%{http_code}\n" https://example.com
Expected output
200

HTTP status code only. 200 = success. 000 = connection failed entirely.
curl -v https://example.com 2>&1 | head -30
Expected output — first 30 lines
* Trying 93.184.216.34:443...
* Connected to example.com
* TLSv1.3 (OUT), TLS handshake ...
* SSL certificate verify ok.
* Server certificate:
*   subject: CN=www.example.org
...
> GET / HTTP/2

-v shows DNS resolution, TCP connection, TLS handshake, and headers.
This is the output to read when something is not working.
Check certificate expiry — the operational one-liner
openssl s_client -connect example.com:443 \
  </dev/null 2>/dev/null \
  | openssl x509 -noout -dates
Expected output
notBefore=Jan 13 00:00:00 2024 GMT
notAfter=Mar 13 23:59:59 2025 GMT

notAfter is when the certificate expires.
Certificates expire on weekends and during holidays — check early.
Ex 6

Read the firewall policy — confirm SSH is permitted

sudo firewall-cmd --state
sudo firewall-cmd --get-active-zones
sudo firewall-cmd --list-all
Expected output — list-all
public (active)
  target: default
  interfaces: eth0
  services: cockpit dhcpv6-client ssh
  ports:
  ...

"ssh" in the services list means TCP/22 is permitted inbound.
This is why you can connect — the firewall allows it.

Identify: which interface is in the active zone, which services are permitted, and whether any explicit ports are open. This is the read-level firewall verification that Associates are expected to perform.

The operator's job at this level is to read and verify — not to write rules. Confirming that expected ports are open and unexpected ports are closed is a security verification task that appears in every maintenance checklist.

Ex 7

Test basic connectivity with ping and traceroute

ping -c 4 8.8.8.8
Expected output
64 bytes from 8.8.8.8: icmp_seq=1 ttl=118 time=x ms
...
4 packets transmitted, 4 received, 0% packet loss

A response confirms the host is reachable at the IP layer.
No response does not confirm it is down — firewalls drop ICMP silently.
traceroute -n 8.8.8.8 2>/dev/null || tracepath -n 8.8.8.8
Expected output
 1  10.x.x.1       x ms
 2  x.x.x.x        x ms
 3  * * *           (hop did not respond — firewall dropping probes)
...
 n  8.8.8.8        x ms

Each line is a hop. Asterisks mean the hop is silent.
traceroute shows where the path breaks when a destination is unreachable.
If traceroute is not installed

Install it: sudo dnf install -y traceroute. Alternatively, tracepath is usually available and needs no installation.

Checkpoint — Section 14 Type done in chat when this passes

Expected: a line confirming sshd is listening on port 22 · a line confirming a default route exists · Section 14 complete. Both must return output — the network substrate that makes SSH possible is in place and readable.
