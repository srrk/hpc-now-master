how to use this runbook

This is the lab runbook for the SLURM Workload Management module. The lecture portion of this module has already been delivered. You are now executing the lab as a single uninterrupted bootcamp stretch — all eight sections in sequence, on a shared AWS ParallelCluster cluster.

Every command block is copy-pasteable. Do not type commands from memory or from slides — use the copy button. After each command, compare your terminal output to the Expected Output block. Discrepancies are diagnostic signals, not failures — read them and figure out what they mean before moving on.

Each section ends with a Checkpoint. Run the checkpoint command when you believe you have completed the section. When the checkpoint passes, type done in the session chat so Rajesh can confirm the cohort is ready to move on.

Lab structure. Each exercise is one of three types. Guided exercises provide complete commands — run them and read the output. Prompted exercises describe what you need to achieve and hint at the approach — you compose the command. Checkpoints give you a validation command and the expected output — you must produce that exact state on the cluster.

Trainer note. Sections 1–7 are independent — a cohort member who gets stuck on one section should not hold others back. Section 8 (Troubleshooting) uses pre-deployed scenarios; do not run setup-scenarios.sh during the session — it was run before lab start. The drain on compute node 2 is intentional — do not resume it until Lab 8 calls for it.

Lab 1 / 8 · 30 minutes · Guided

Cluster Orientation — Reading Before Touching

Follows: SLURM architecture, node states, sinfo, scontrol. No jobs are submitted in this section.

Setup. Log in to cluster.hpc.now. All exercises in this section run on the head node. You are observing a cluster with 4 compute nodes in partition compute and 2 nodes in partition debug.

Ex 1

Read the cluster state with sinfo

Run sinfo and read every column. Identify: which partitions exist, how many nodes are in each state, and what the time limits are.

sinfo
Expected output
PARTITION  AVAIL  TIMELIMIT  NODES  STATE  NODELIST
compute*      up    4:00:00      4   idle  compute-st-t3small-[1-4]
debug         up      30:00      2   idle  compute-st-t3small-[1-2]

The asterisk on compute* means it is the default partition — jobs submitted without --partition go here. TIMELIMIT is the maximum wall time a job in this partition can request.

Ex 2

Inspect a compute node in full detail

Use scontrol show node to see everything SLURM knows about one compute node. Read: CPUTot, CPUAlloc, RealMemory, FreeMem, and State.

scontrol show node compute-st-t3small-1
Expected output — key fields
NodeName=compute-st-t3small-1 Arch=x86_64 CoresPerSocket=1
   CPUTot=2 CPULoad=N/A
   AvailableFeatures=t3small
   ActiveFeatures=t3small
   Gres=(null)
   NodeAddr=10.0.1.10 NodeHostName=compute-st-t3small-1
   OS=Linux 5.10.x
   RealMemory=1920 AllocMem=0 FreeMem=N/A
   State=IDLE+CLOUD+POWER Reason=None
   CfgTRES=cpu=2,mem=1920M
   AllocTRES=

RealMemory is in MB. This node has 1920 MB (~2 GB) available for jobs. AllocMem=0 confirms no jobs are running on it right now. IDLE+CLOUD+POWER means the node is available and managed by ParallelCluster's dynamic scaling.

Ex 3

Inspect the compute partition's configuration

Read the partition record to find: MaxTime, DefaultTime, MaxNodes per job, and whether the partition is up.

scontrol show partition compute
Expected output — key fields
PartitionName=compute
   AllowGroups=ALL AllowAccounts=ALL AllowQos=ALL
   AllocNodes=ALL Default=YES QoS=N/A
   DefaultTime=01:00:00 DisableRootJobs=NO ExclusiveUser=NO GraceTime=0
   Hidden=NO
   MaxNodes=4 MaxTime=04:00:00 MinNodes=0
   Nodes=compute-st-t3small-[1-4]
   State=UP

DefaultTime=01:00:00 means a job submitted without --time gets 1 hour. MaxTime=04:00:00 means no job in this partition can request more than 4 hours. A request exceeding this results in a PENDING job with reason PartitionTimeLimit.

Ex 4

Use sinfo with a format string — node-centric view

The default sinfo output is partition-centric. Switch to node-centric view and use a custom format to show one row per node with state and memory.

sinfo -N -o "%-30N %8T %8m %8c %P"   # node, state, memory(MB), CPUs, partition
Expected output
NODELIST                       STATE    MEMORY   CPUS   PARTITION
compute-st-t3small-1           idle     1920     2      compute*
compute-st-t3small-2           drained  1920     2      compute*
compute-st-t3small-3           idle     1920     2      compute*
compute-st-t3small-4           idle     1920     2      compute*

Notice node 2 shows drained. This is intentional — it is one of the Lab 8 troubleshooting scenarios. Do not attempt to resume it now.

Lab 2 / 8 · 30 minutes · Guided

First Job — Write, Submit, Monitor, Review

Follows: job submission modes, job script anatomy, sbatch directives, SLURM environment variables, job output files.

Ex 1

Write the hello job script

A pre-written version is in ~/jobs/hello.sh. Read it in full before submitting — understand each directive and each command in the body.

cat ~/jobs/hello.sh
Expected file content
#!/bin/bash
#SBATCH --job-name=hello
#SBATCH --output=~/jobs/hello-%j.out
#SBATCH --error=~/jobs/hello-%j.err
#SBATCH --partition=compute
#SBATCH --time=00:05:00
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=1

echo "=== Job started ==="
echo "Job ID:       $SLURM_JOB_ID"
echo "Job name:     $SLURM_JOB_NAME"
echo "Running on:   $(hostname)"
echo "Node list:    $SLURM_JOB_NODELIST"
echo "Allocated CPUs: $SLURM_CPUS_PER_TASK"
echo "Date:         $(date)"
echo ""
echo "Counting to 5:"
for i in 1 2 3 4 5; do echo "  Step $i"; sleep 1; done
echo "=== Job complete ==="

The %j in the --output path is replaced by the actual job ID when the job runs. This ensures each job writes to its own file and older files are not overwritten.

Ex 2

Submit the job and capture the job ID

JOBID=$(sbatch --parsable ~/jobs/hello.sh)
echo "Submitted job ID: $JOBID"
Expected output
Submitted job ID: 1

--parsable makes sbatch output only the job ID number, with no surrounding text. This is essential when capturing job IDs in scripts for later use (dependencies, sacct queries).

Ex 3

Monitor the job with squeue

Watch your job transition from PENDING → RUNNING → disappear (COMPLETED). Run squeue every few seconds until the job is gone.

watch -n 2 "squeue -u $USER"         # refresh every 2 seconds; Ctrl+C to exit
Expected sequence
First appearance (PENDING on ParallelCluster — node may be powering on):
  JOBID PARTITION  NAME  USER  ST  TIME  NODES  NODELIST(REASON)
      1   compute hello chandra PD  0:00      1  (Resources)

Then RUNNING:
      1   compute hello chandra  R  0:05      1  compute-st-t3small-1

Then gone (job completed — press Ctrl+C after confirming it disappears)
If the job stays in PD for more than 3 minutes

On AWS ParallelCluster, compute nodes power on dynamically. The first job of the lab will wait 1–2 minutes for a node to boot. This is expected. If still waiting after 4 minutes, run squeue -j $JOBID -o %R to read the pending reason. Not Running means nodes are starting up. ReqNodeNotAvail means nodes have a problem — tell Rajesh.

Ex 4

Read the job output file

When the job disappears from squeue, the output file is written. Read it and verify every echo from the job script appears.

cat ~/jobs/hello-${JOBID}.out
Expected output
=== Job started ===
Job ID:       1
Job name:     hello
Running on:   compute-st-t3small-1
Node list:    compute-st-t3small-1
Allocated CPUs: 1
Date:         Thu Jun 13 10:15:42 UTC 2026

Counting to 5:
  Step 1
  Step 2
  Step 3
  Step 4
  Step 5
=== Job complete ===

The hostname shown is a compute node name, not the head node. This confirms the job executed on the allocated compute resource, not where you submitted it from.

Ex 5 (Prompted)

Query the completed job with sacct

Use sacct to retrieve accounting data for the completed job. Show: JobID, State, ExitCode, Elapsed time, and the node it ran on.

Build the command yourself. Hint: sacct -j $JOBID --format=JobID,State,ExitCode,Elapsed,NodeList — confirm State=COMPLETED and ExitCode=0:0.

Reference — reveal after trying
sacct -j $JOBID --format=JobID,State,ExitCode,Elapsed,NodeList -n
Expected output
1      COMPLETED      0:0   00:00:07   compute-st-t3small-1
1.batch COMPLETED     0:0   00:00:07   compute-st-t3small-1

The 1.batch row is the implicit batch step that wraps the job script. Both the job (1) and the step (1.batch) record COMPLETED with ExitCode 0:0 (signal 0, exit code 0 = clean exit).

Ex 1

Allocate resources interactively with salloc

Request a 10-minute allocation on the debug partition. salloc will block until resources are granted, then return you to your shell — with SLURM variables set in your environment.

salloc --ntasks=1 --cpus-per-task=1 --time=00:10:00 --partition=debug
Expected output
salloc: Granted job allocation 5
salloc: Waiting for resource configuration
salloc: Nodes compute-st-t3small-1 are ready for job

After salloc returns, you are still on the head node — but you hold an active allocation. Verify this by running echo $SLURM_JOB_ID — it should show your allocation's job ID. Running squeue -u $USER shows the job in RUNNING state.

Land on the compute node with srun --pty

srun within an active allocation launches a job step. --pty bash gives you an interactive shell on the allocated compute node.

srun --pty bash
Expected output
Your shell prompt changes — you are now on the compute node:
[chandra@compute-st-t3small-1 ~]$

You are now running a shell on a compute node. This is not an SSH session — it is a SLURM job step. Your resources are governed by the allocation you obtained with salloc. If you run resource-heavy commands here, they are within your allocation's limits.

Lab 4 / 8 · 25 minutes · Guided + Prompted

Resource Requests — CPUs, Memory, and Time Limits

Follows: --ntasks, --cpus-per-task, --mem, --time, consequences of over/under-requesting.

Ex 1

Submit a 2-CPU job and verify the allocation

The multi-cpu.sh script requests 2 CPUs and prints nproc inside the job to confirm the OS sees the allocated CPUs.

cat ~/jobs/multi-cpu.sh              # read first — note --cpus-per-task=2
JOBID=$(sbatch --parsable ~/jobs/multi-cpu.sh)
echo "Submitted: $JOBID"

Wait for completion, then read the output:

cat ~/jobs/multi-cpu-${JOBID}.out
Expected in output file
Allocated CPUs (SLURM): 2
CPUs visible to nproc:  2

Environment for a 2-thread application:
  OMP_NUM_THREADS would be: 2

nproc sees exactly 2 CPUs because SLURM creates a cgroup that limits the job to its allocated CPUs. If you request 1 CPU but run 4 threads, the OS will still run them — but SLURM's accounting will flag this as a resource abuse in a production environment.

Ex 2

Submit a job with a memory request

sbatch --job-name=mem-test \
       --output=~/jobs/mem-test-%j.out \
       --partition=compute \
       --time=00:02:00 \
       --ntasks=1 \
       --mem=256M \
       ~/jobs/mem-test.sh

The mem-test script shows available memory inside the job:

Expected in output file
Requested memory: 256M (from SLURM directive)
Free memory on node: ~1600 MB (the node's total, not your limit)
Your job's limit is enforced by cgroups — not visible in free -m.

Memory limits are enforced by cgroups, not by the values in free. The job sees the node's full memory in free output, but will be killed if it allocates more than 256 MB. Memory enforcement is per-job, not per-process-visibility.

Ex 3 (Prompted)

Submit an impossible resource request — observe pending reason

Submit a job requesting 999 GB of memory. Since no node has this much memory, it will wait in PENDING indefinitely. Read the reason and then cancel it.

Build this yourself. Use sbatch --wrap to submit an inline command without a script file. The --wrap flag takes a quoted command string as the job body. Request --mem=999G.

Reference — reveal after trying
BIGJOB=$(sbatch --parsable \
  --job-name=impossible \
  --partition=compute \
  --time=00:01:00 \
  --mem=999G \
  --wrap="echo this will never run")
echo "Big job ID: $BIGJOB"
squeue -j $BIGJOB -o "%.10i %.20j %.8T %R"
Expected squeue output
JOBID                 NAME     STATE REASON
 8            impossible   PENDING Resources
scancel $BIGJOB                       # cancel the impossible job
squeue -j $BIGJOB 2>/dev/null || echo "Job cancelled successfully"
Ex 4

Submit a job that will timeout — observe the TIMEOUT state

Submit a job that sleeps for 90 seconds but only requests a 1-minute time limit. Watch it hit the TIMEOUT wall.

TJOB=$(sbatch --parsable \
  --job-name=timeout-demo \
  --output=~/jobs/timeout-%j.out \
  --partition=debug \
  --time=00:01:00 \
  --ntasks=1 \
  --wrap="echo start; sleep 90; echo this will not print")
echo "Timeout job: $TJOB"

Watch the job. After ~1 minute it will transition to TIMEOUT:

watch -n 5 "squeue -j $TJOB -o '%.8i %.12j %.8T %.10M %.10l'"
Expected sequence
While running:
  JOBID       NAME    STATE       TIME  TIME_LIMIT
     10 timeout-dem RUNNING     0:30     1:00

After timeout (check sacct after squeue shows job gone):
  10     TIMEOUT    0:1:05   00:01:00

Lab 5 / 8 · 30 minutes · Guided + Prompted

Job Arrays — Parallel Tasks from a Single Submission

Follows: --array syntax, SLURM_ARRAY_TASK_ID, concurrency limits, cancelling individual array tasks.

Ex 1

Submit a 4-task array job

Read the array job script first. Note how $SLURM_ARRAY_TASK_ID makes each task unique despite using the same script.

cat ~/jobs/array.sh
Script content
#!/bin/bash
#SBATCH --job-name=array-lab
#SBATCH --output=~/jobs/array-%A_%a.out
#SBATCH --partition=compute
#SBATCH --time=00:05:00
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=1

echo "Array job:  $SLURM_ARRAY_JOB_ID"
echo "Task ID:    $SLURM_ARRAY_TASK_ID"
echo "Running on: $(hostname)"
echo "Date:       $(date)"
sleep 15
echo "Task $SLURM_ARRAY_TASK_ID complete"

The output path %A_%a uses two special tokens: %A = the array job's master ID, %a = the individual task ID. This produces separate output files per task: array-15_1.out, array-15_2.out, etc.

ARRAYJOB=$(sbatch --parsable --array=1-4 ~/jobs/array.sh)
echo "Array job ID: $ARRAYJOB"
Ex 2

Monitor array tasks in squeue

While the array is running, observe how each task appears in squeue with its own JOBID_TASKID identifier.

squeue -u $USER -o "%.10i %.12j %.4T %.8M %.12R"
Expected output while running
JOBID         NAME   ST     TIME         REASON
15_1     array-lab    R     0:05
15_2     array-lab    R     0:05
15_3     array-lab    R     0:05
15_4     array-lab    R     0:05

All 4 tasks start simultaneously because we have 3 idle nodes and no concurrency limit. In a production cluster with limited nodes, some tasks would show PD while others run.

Ex 3

Submit an array with a concurrency limit

The %N suffix on --array limits how many tasks run simultaneously. Submit 8 tasks with a maximum of 2 concurrent.

LIMITJOB=$(sbatch --parsable --array=1-8%2 ~/jobs/array.sh)
echo "Limited array: $LIMITJOB"
squeue -u $USER -o "%.10i %.8T %.12R"
Expected output — only 2 tasks in RUNNING
JOBID       ST         REASON
16_1         R
16_2         R
16_[3-8]    PD  JobArrayTaskLimit

The pending reason JobArrayTaskLimit is not a problem — it is the concurrency limit working as designed. Tasks 3–8 will start automatically as tasks 1 and 2 complete.

Cancel a single array task without affecting others

While the limited array is running, cancel only task 3. Verify task 3 disappears while tasks 1, 2, and 4+ continue.

Build this yourself. The syntax is scancel JOBID_TASKID. Replace JOBID with your array job's master ID and TASKID with 3.

Lab 6 / 8 · 20 minutes · Guided + Prompted

Job Dependencies — Building Sequential Workflows

Follows: --dependency flags, afterok/afternotok/afterany, DependencyNeverSatisfied, workflow chains.

Ex 1

Submit step 1 of the dependency chain

step1.sh runs for 30 seconds and exits cleanly. Submit it and capture its job ID — you will use this ID for the dependency in step 2.

JOB1=$(sbatch --parsable ~/jobs/step1.sh)
echo "Step 1 job ID: $JOB1"
squeue -j $JOB1 -o "%.8i %.12j %.8T"
Expected
Step 1 job ID: 20
 JOBID         NAME    STATE
    20        step1  RUNNING
Ex 2

Submit step 2 with an afterok dependency

step2.sh will only start if step1.sh exits with code 0. Submit it while step1 is still running — step2 will enter PENDING with reason Dependency.

JOB2=$(sbatch --parsable \
  --dependency=afterok:${JOB1} \
  ~/jobs/step2.sh)
echo "Step 2 job ID: $JOB2"
squeue -u $USER -o "%.8i %.12j %.8T %.20R"
Expected — step 2 is waiting on step 1
JOBID         NAME    STATE                   REASON
   20        step1  RUNNING
   21        step2  PENDING           Dependency

The REASON Dependency confirms step2 is held by its dependency, not by resource availability. Step2 will automatically transition to RUNNING the moment step1 reaches COMPLETED state.

Ex 3

Watch the dependency resolve

Use watch to observe both jobs simultaneously. After step1 completes (~30 seconds), step2 should immediately transition from PD to R.

watch -n 3 "squeue -u $USER -o '%.8i %.12j %.8T %.8M'"
Expected transition sequence
T=0:   JOB1 RUNNING,   JOB2 PENDING
T=30:  JOB1 gone,      JOB2 RUNNING
T=60:  JOB2 gone       (both complete)
Ex 4 (Prompted)

Demonstrate DependencyNeverSatisfied

Submit a job that depends on JOB1 completing with afterok — but JOB1 has already completed successfully. Then submit another job with afternotok on JOB1 (which succeeded). The afternotok job will immediately reach DependencyNeverSatisfied.

Build this yourself. Submit ~/jobs/step3-notok.sh with --dependency=afternotok:JOB1_ID. Since JOB1 already succeeded, this dependency can never be satisfied. Read the squeue REASON, then cancel the stuck job.

Reference — reveal after trying
JOB3=$(sbatch --parsable \
  --dependency=afternotok:${JOB1} \
  ~/jobs/step3-notok.sh)
squeue -j $JOB3 -o "%.8i %.8T %.30R"
Expected squeue output
JOBID    STATE                           REASON
   22  PENDING        DependencyNeverSatisfied
scancel $JOB3                         # clean it up

This is the most common dependency problem you will encounter in production — a user's pipeline got stuck at step 1, and steps 2 through 10 are all in DependencyNeverSatisfied. The fix: identify the failed upstream job, decide whether to resubmit from the failure point, and cancel the stuck dependent jobs.

Lab 7 / 8 · 25 minutes · Guided + Prompted

Monitoring & Accounting — Reading What Happened and What Is Happening

Follows: sacct, sstat, squeue format strings, sprio, sdiag, job efficiency analysis.

Ex 1

Run a comprehensive sacct query for today's jobs

Query all your jobs from today with a format that covers: ID, name, state, exit code, elapsed time, allocated CPUs, and max RSS (peak memory use).

sacct -u $USER \
  --format=JobID,JobName%15,State%12,ExitCode,Elapsed,AllocCPUS,MaxRSS \
  --starttime=today \
  -n
Expected output — all your jobs from the session
1         hello    COMPLETED      0:0   00:00:07   1
1.batch   hello    COMPLETED      0:0   00:00:07   1        1500K
3    multi-cpu    COMPLETED      0:0   00:00:03   2
3.batch  multi-cpu COMPLETED     0:0   00:00:03   2         780K
...and so on for all labs

MaxRSS (Maximum Resident Set Size) is the peak physical memory used by the job step. It is blank for the job-level row and populated for the .batch step row. This is the value used to right-size --mem for future submissions.

Ex 2

Capture live statistics from a running job with sstat

First submit a long-running job for observation, then query it with sstat while it runs.

MONITORJOB=$(sbatch --parsable ~/jobs/monitor-job.sh)
echo "Monitor job: $MONITORJOB"

Wait 10 seconds for the job to start, then query it live:
