before you start

Two labs, both hands-on, both yours. You have a private three-machine cluster that nobody else can see, reach or affect, and you have full sudo on all of it. You are the owner. Everything you break is yours to break and yours to put back, and there are reset commands for exactly that.

Expected Output blocks show the structure of correct output. Build identifiers, timestamps, byte counts and hardware addresses will differ from what is printed here, because they differ per pod. The interpretation matters, not the strings.

Your change set in Lab 2 is not the same as your neighbour's. Each pod is assigned a different package, mount, key and kernel parameter. Comparing screens will tell you how somebody solved a problem; it will not complete your lab.

If a command is not recognised. This build pins Warewulf 4.5.8. If any wwctl subcommand or flag is rejected, check wwctl version first and say so — flag names changed between point releases and the runbook is written against one exact version, not a family.

how to connect

Two machines, one command. You land on the shared host and jump straight to your own pod's head node; the second hop is configured for you.

ssh <username>@mylab.hpc.now
# password: hpcnow2026

# then, from that shell:
ssh head
# no password — you are the owner of this machine

Your prompt on the head node tells you which pod you are on. Check it before you run anything destructive, because every pod's head answers to the same hostname alias and the only thing distinguishing yours is which shell you are sitting in.

You have full sudo on your head node and on both of your compute nodes. You have no access to anyone else's pod and no access to the physical host beyond your own login shell.

your pod

Three machines, all yours. head is the provisioning server: it hands out addresses, serves the boot files, holds the fleet image, exports the shared filesystem, and runs the scheduler that decides which nodes are eligible for work. cn01 and cn02 are compute nodes on an internal network with no route to the outside.

The compute nodes are not simulated. They power on with nothing, acquire an address by DHCP, fetch a bootloader, pull a kernel and a root image over the network, have host-specific files written over that image, and register with the scheduler. That chain is the subject of the session, and this time it runs at full hardware speed — the whole thing takes well under a minute, which is its own lesson about what you can and cannot watch.

your three machines
head
provisioning server, boot server, NFS, scheduler controller — your shell lives here
cn01
diskless — IN SERVICE. Lab 2 checks you left it alone
cn02
diskless — your sandbox and reprovision target
internal net
DHCP and network boot live here — no route out, nothing else on it
image
rocky-9-lab — one image, both nodes, held on your head

Neither compute node has a disk. Run lsblk on either one and there is nothing to mount. Everything about them — the kernel, the files, the accounts — arrives over the network at boot and nowhere else. Power one off and everything outside /home ceases to exist. That is not a simplification for the lab; it is the entire subject.

Your server is not fresh out of the box. It has accumulated the sediment a real one does: more than one profile, a node record for hardware that no longer exists, an overlay entry someone commented out and never removed, and boot logs going back several days.

That is deliberate. A system with exactly one of everything makes attribute tracing trivial, because there is only one candidate answer.

There is no service processor here. On a real floor you power a node with ipmitool against its BMC — out of band, independent of whether the node's own operating system is alive. This pod has hpcops-power, doing the same job through the layer underneath these machines. The first node you meet that has stopped answering entirely is the one that teaches you why out-of-band power exists.

when you break it

You will, and that is fine — it is your pod. Two things worth knowing before you start rather than after.

If you break DHCP or the boot service on the internal network, you lose contact with your compute nodes and keep your shell on head. Nothing is lost that a reset will not restore.

reset paths
hpcops-reset 12
restores a blank trace template. Under a second. Costs you only what you typed into it
hpcops-reset 13 --profile-only
restores profiles, overlays and your change set. Keeps your rebuilt image and running nodes. Reach for this first — the common failure is a malformed overlay file
hpcops-reset 13
the full one. Rebuilds the image and both nodes, discards everything you did in Lab 2. Requires --confirm. Check the clock first
hpcops-power cycle cn02
out-of-band power, for a node that has stopped answering
Lab 1 — hands on, your own pod
Provisioning Server Tour
Establish, for certain rather than by assumption, where each property of a running node actually comes from.

You have been handed a provisioning server you did not build and told nothing about its history. Before anyone can safely change a fleet like this, they need to know which file or object is the real source of truth for each attribute of a running node — and whether changing it needs a reboot or a full image rebuild.

Eight exercises, then a trace file to complete and a self-check to run. Nothing here changes anything, so there is no way to get into trouble. Run every command with sudo; you own the machine.

Ex 1

List the node objects — then count what is actually running

wwctl node list reads a database. It tells you what this server believes exists. It does not check whether any of it is powered on.

sudo wwctl node list
sinfo -N
Expected output — note the row count
NODE NAME  PROFILES  NETWORK
cn01       compute   default:10.31.x.11
cn02       compute   default:10.31.x.12
cn07       compute   default:10.31.x.17

NODELIST  NODES PARTITION STATE
cn01          1  compute* idle
cn02          1  compute* idle

Three node objects. Two running machines. cn07 is a record for hardware that left the rack and took its reservation with it. Nothing here will tell you that unprompted — you have to notice.

Ex 2

Resolve one node fully — the difference between --long and --all

A node's own record holds very little. Most of what it is comes from the profiles it inherits, and only one of these two flags shows you the resolved result.

sudo wwctl node list cn01 --long
sudo wwctl node list cn01 --all
Expected output — the --all view, abridged
NODE  FIELD              PROFILE   VALUE
cn01  Profiles           --        compute
cn01  Kernel.Args        default   quiet crashkernel=no
cn01  ContainerName      compute   rocky-9-lab
cn01  SystemOverlay      default   site-system
cn01  RuntimeOverlay     default   site-runtime
cn01  NetDevs[default]   --        10.31.x.11

The PROFILE column is the answer to "where did this come from".
A value marked "--" was set on the node itself.

--long widens the table. --all resolves inheritance and shows which profile each value arrived from. Only the second one answers today's question.

Ex 3

Walk the profile chain, and find the one assigned to nothing

Profiles inherit. The effective configuration of a node is the resolved chain, not any single file. There is more than one profile here and they are not all in use.

sudo wwctl profile list
sudo wwctl profile list compute --all
sudo wwctl profile list compute-legacy --all
Expected output — compare the two compute profiles
PROFILE NAME
default
compute
compute-legacy

compute         ContainerName   rocky-9-lab
compute         Kernel.Args     quiet crashkernel=no

compute-legacy  ContainerName   rocky-8-lab
compute-legacy  Kernel.Args     quiet crashkernel=no console=ttyS0

Two settings differ. No node references compute-legacy.

A profile that is defined but assigned to nothing is the residue of a hardware refresh nobody cleaned up. Decide whether you would delete it or leave it, and be able to say why.

Ex 4

Inspect the image — and note its build identifier

One image serves both nodes. It carries the kernel and the entire package set, including the scheduler client that lets a node register at all. Nothing host-specific is in it, and that distinction is the whole basis of the model.

sudo wwctl container list
sudo wwctl container exec rocky-9-lab -- /bin/sh -c "rpm -q slurm-slurmd-ohpc munge"
Expected output
CONTAINER NAME  NODES  KERNEL VERSION      SIZE
rocky-9-lab     2      5.14.0-503.el9      xxx MiB

slurm-slurmd-ohpc-...
munge-...

Write down the kernel version and the size. The stock upstream image contains none of this — no scheduler client, no authentication daemon — and a node built from it boots perfectly and never joins the cluster. Somebody put these here on purpose.

Ex 5

The two overlays — written once, versus written at every boot

Anything that differs per node cannot live in a shared image. It is written over the image after the image is fetched, by one of two overlays with different lifetimes.

sudo wwctl overlay list
# the overlay sources live on disk — read them directly
sudo ls -R /var/lib/warewulf/overlays/site-system/rootfs/
sudo cat /var/lib/warewulf/overlays/site-runtime/rootfs/etc/fstab.ww
Expected output — note the third line
10.31.x.1:/home   /home   nfs   defaults  0 0
tmpfs             /tmp    tmpfs defaults  0 0
# 10.31.x.1:/exports/proj-xxxx  /proj  nfs defaults 0 0   # commented 11 Aug, reinstate?

The user accounts on a running node come from the SYSTEM overlay.
They are not in the image, and there is no directory service here.

A commented-out mount with a date and a question mark is somebody's unfinished change. It is also the exact line Lab 2 asks you to reinstate — and the export named in yours is not the same as your neighbour's.

Ex 6

Ask the node itself — and confirm it has no disk

Everything so far has been the server's view. Now get the node's own view and reconcile the two. Where they disagree, the node is right and the database is stale.

ssh cn01 lsblk
ssh cn01 uname -r
ssh cn01 findmnt -t nfs4,tmpfs,rootfs
ssh cn01 "getent passwd asamuel rmirza"
Expected output — lsblk returns nothing at all
(no output from lsblk)

5.14.0-503.el9.x86_64

TARGET  SOURCE            FSTYPE  OPTIONS
/       rootfs            rootfs  rw
/home   10.31.x.1:/home   nfs4    rw,relatime
/tmp    tmpfs             tmpfs   rw

asamuel:x:4001:6100::/home/asamuel:/bin/bash
rmirza:x:4002:6100::/home/rmirza:/bin/bash

The root filesystem is rootfs — it is in memory. Those two accounts are not in the image and there is no directory service on this network, so something else put them there. Find out what.

Ex 7

Find where the address came from, and read the evidence of past boots

A stateless node has no address until something gives it one. That transaction is logged, and the log is the first place any provisioning fault is diagnosed — before you change a single line of configuration.

sudo grep -A3 'host cn01' /etc/dnsmasq.d/warewulf.conf
sudo journalctl -u dnsmasq -u warewulfd --since '5 days ago' | grep -Ei 'DHCPACK|tftp|no address'
Expected output — five days of boots, one of them failed
DHCPACK(virbr-p03) 10.31.3.11 52:54:00:07:03:01 cn01
sent /var/lib/tftpboot/undionly.kpxe to 10.31.3.11
DHCPACK(virbr-p03) 10.31.3.12 52:54:00:07:03:02 cn02
no address available for 52:54:00:07:03:07

The last line is a machine asking for an address it will never get.
Match that hardware address against the node objects from Ex 1.

The failed request belongs to cn07. A record that outlived its hardware still holds a reservation, and something on the network is still asking for it. Both halves of that are worth explaining out loud.

Ex 8

Find the terminus — a node that boots but never registers runs nothing

The boot chain does not end when the operating system is up. It ends when the scheduler will accept work on that node, and that is a separate handshake with its own failure mode.

sinfo
scontrol show node cn01 | grep -E 'State|BootTime|Reason'
ssh cn01 systemctl is-active slurmd munge
Expected output
PARTITION AVAIL TIMELIMIT NODES STATE NODELIST
compute*     up  infinite     2  idle cn01,cn02

   State=IDLE
   BootTime=...
   Reason=(null)

active
active

Two layers had to be correct for this one line: the client arrived in the image, its configuration arrived through an overlay. Be able to name both, because when a freshly provisioned node sits in DOWN it is almost always one of them — and if the clocks disagree it is the authentication daemon, not the scheduler.

complete the trace

A template is waiting at ~/lab12-trace.yaml on your head node. It lists eleven attributes of a running compute node against blank answers. For each, record which object or file is the actual source of truth.

vi ~/lab12-trace.yaml
# most answers are layer names:
#   dhcp | image | profile | system-overlay | runtime-overlay | node-object

Three of the eleven are not layer names. They are values you have to read off your own pod: the image build identifier, cn02's hardware address, and the number of node objects in the database. All three differ from your neighbour's, and you collected all three during the exercises above.

Lab 1 Checkpoint run this when your trace is complete
hpcops-check 12
hpcops-check 12 --hint

The check names which attributes are correctly attributed and which are not. --hint gives you the next unmet one at three levels — the question, then the mechanism, then the object to inspect. Never the value. If you break the file's structure rather than its content, hpcops-reset 12 restores a blank template.

Before Lab 2 begins. Run the trace once more against cn02 instead of cn01. Every attribute that comes out identical tells you what a shared image and a shared profile actually guarantee. Every one that differs was assigned per node rather than per fleet, and those are the ones that bite at scale.

Lab 2 — hands on, your own pod
Modify and Reprovision
Land four specific changes on one node and prove they reached that node and nothing else.

This is the request an operator gets dozens of times over a node's life, and the one most likely to go wrong in a way nobody notices until the wrong machine reboots. You have full sudo, your own image and your own two nodes. Nothing you do here can reach anyone else.

Three things this lab is actually testing.

Each change has to be made twice — once so it is true on the running node, once so it is declared somewhere that survives the next boot. The check tests those separately. Confusing them is the single most common provisioning error there is.

cn01 is in service throughout. Nothing here is allowed to touch it, and the check will notice. There is an obvious shortcut that satisfies eleven of the twelve criteria and takes a production node down doing it.

The boot in step 6 takes well under a minute on this hardware. Start the log tailing before you trigger it, or you will miss the whole thing.

1

Read your change set before touching anything

Four changes, assigned to you and different from everyone else's: one package, one filesystem to mount at /proj, one SSH key principal to authorise, one kernel parameter to set.

cat /etc/hpcops/lab13-changeset
Expected output — this is pod03's; yours differs
PACKAGE   strace
MOUNT     10.31.3.1:/exports/proj-cfd  ->  /proj
KEY       svc-monitor-03
SYSCTL    kernel.numa_balancing = 0

Every kernel parameter in the set is one an HPC site actually sets, not a placeholder. Whatever yours turns out to be, be ready to say why a site would want it.

2

Put the package inside the image, then rebuild it

On a diskless node the image is the only thing carrying packages. Installing on the running node works until the next boot and then silently vanishes, which is worse than not working at all.

sudo wwctl container exec rocky-9-lab -- /bin/sh -c "dnf install -y <your package>"
sudo wwctl container build rocky-9-lab
sudo wwctl container list
Expected output
Building container: rocky-9-lab
Created image for VNFS container rocky-9-lab: xxx MiB

CONTAINER NAME  NODES  KERNEL VERSION      SIZE
rocky-9-lab     2      5.14.0-503.el9      xxx MiB

That one command has changed the image that both your nodes are configured to use. Nothing has moved yet — but your fleet's source of truth is now different from what cn01 is running. Hold that thought until step 7.

3

Declare the mount and the kernel parameter in the every-boot overlay

Both are host behaviour rather than host identity, so they belong in the overlay rewritten at every boot. The mount line is the one that was commented out with a date — reinstate it, with the export named in your change set.

sudo wwctl overlay edit site-runtime /etc/fstab.ww
# uncomment the /proj line and set it to your assigned export
sudo wwctl overlay edit site-runtime /etc/sysctl.d/90-hpc.conf.ww
# add your assigned parameter

Running sysctl -w on the node would satisfy anyone watching the output and would not survive the reboot two steps from now. Declared and set are different states, and criteria 9 and 10 test them separately.

4

Authorise the key in the first-boot overlay

Identity material belongs in the overlay applied once at provisioning rather than rewritten every boot — a node that regenerates its trust on every reboot is a node whose fingerprint nobody can pin.

sudo wwctl overlay edit site-system /root/.ssh/authorized_keys.ww
# append the public key for your assigned principal
sudo ls -l /var/lib/warewulf/overlays/site-system/rootfs/root/.ssh/

Ask yourself where this key would have to live if there were five hundred nodes and it had to be rotated on a Friday afternoon. The answer is the same file. That is the point of the model.

5

Render the overlays — editing is not building

Overlay source files are templates. Until they are rendered, your change exists in the editor's output and nowhere a booting node can reach.

sudo wwctl overlay build
Expected output
Building overlay for cn01: site-system, site-runtime
Building overlay for cn02: site-system, site-runtime

Note that it built for both nodes. Your overlays are now staged for cn01 too — and cn01 will not receive them, because it is not going to boot. Staged and delivered are yet another pair of different states.

6

Reboot cn02 and watch every stage of the chain

The node has no disk, so any reboot re-runs the entire chain from nothing. On this hardware it completes in well under a minute, so open the log first and trigger second — there is no second chance to watch it without another reboot.

# terminal 1 FIRST — the evidence trail, live
sudo journalctl -u dnsmasq -u warewulfd -f

# terminal 2 — then trigger it
ssh cn02 systemctl reboot

# if cn02 has stopped answering, the out-of-band path instead:
hpcops-power cycle cn02
Expected output — the chain, in order
DHCPDISCOVER(virbr-pNN) 52:54:00:07:NN:02
DHCPACK(virbr-pNN) 10.31.N.12 ... cn02          <- address
sent /var/lib/tftpboot/undionly.kpxe to cn02    <- bootloader
warewulfd: cn02 requested kernel                 <- kernel
warewulfd: cn02 requested container rocky-9-lab  <- root image
warewulfd: cn02 requested overlay site-system    <- identity
warewulfd: cn02 requested overlay site-runtime   <- behaviour
slurmctld: node cn02 returned to service         <- terminus

Seven stages, seven things that fail independently. If a node ever stops halfway, capture packets on the boot service port before you change any configuration — that check answers the question in seconds and guessing at the DHCP layer can burn an hour.

7

Prove the blast radius — four changes on cn02, nothing on cn01

Verifying that a change landed is the easy half. Verifying that it landed nowhere else is the half that keeps a partition in service.

ssh cn02 "rpm -q <pkg>; findmnt /proj; sysctl <param>"
ssh cn01 "rpm -q <pkg>; uptime -s"
Expected output — the second block is the important one
strace-...
TARGET SOURCE                         FSTYPE OPTIONS
/proj  10.31.3.1:/exports/proj-cfd    nfs4   rw,relatime
kernel.numa_balancing = 0

package strace is not installed
<boot time from before the lab started>

cn01 has not rebooted. It is running the old image.
That is the correct outcome, not a missed step.

Your fleet is now deliberately inconsistent, and somebody has to decide when cn01 catches up. That decision — not the rebuild — is the actual job.

Lab 2 Checkpoint twelve criteria
hpcops-check 13
hpcops-check 13 --hint

Each of your four changes is checked twice — true on the running node, and declared where it survives a boot. Then cn02's re-registration, and finally that cn01 has not moved: same boot, same packages, same mounts as at the start. On a clean pass it prints the measured time from image rebuild to cn02 returning to service.

The closing question. Break your measured round trip into its parts — the image rebuild, the network fetch, the boot itself, the scheduler handshake. Decide which one you would attack first if this were five hundred nodes instead of one, and say what you would actually change to attack it. Compare your number with someone else's: your images are not the same size.

the physical gap

Assigned alongside this session: a recorded walkthrough of an actual bare-metal deployment — racking, cabling, BMC configuration and first boot.

Your pod keeps its networks apart in software. A real provisioning network is kept apart by separate cabling, separate switches and separate colour conventions, and that discipline does not show up on a screen. The same goes for the service processor you stood in for with hpcops-power: on a real floor that is a separate embedded computer with its own address, its own credentials and its own failure modes, reachable when the node it is attached to is entirely dead.

Watch for both, and bring back one concrete example of something you did today that would not be acceptable on a real floor.
