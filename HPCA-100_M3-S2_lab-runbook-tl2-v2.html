02The node that disagrees8 min
Goalc2 is back in service, with a declaration that matches its hardware and leaves deliberate headroom.

2.1 Read what the scheduler was told about c2

Do
scontrol show node c2 | grep -E "NodeName=|CPUAlloc|RealMemory|State=|Reason="
You should see
NodeName=c2 Arch=x86_64 CoresPerSocket=1
   CPUAlloc=0 CPUEfctv=2 CPUTot=2 CPULoad=0.05
   RealMemory=3000 AllocMem=0 FreeMem=1234 Sockets=2 Boards=1
   State=IDLE+DRAIN+INVALID_REG ThreadsPerCore=1 TmpDisk=0 Weight=1 Owner=N/A MCS_label=N/A
   Reason=Low RealMemory (reported:1719 < 100.00% of configured:3000) [slurm@2026-09-19T13:07:25]

RealMemory=3000 is the declaration repeated back. FreeMem=1234 is measured. A node with 3000 MB declared and nothing allocated cannot have only 1234 free. The reason string names both sides of the disagreement, so you have the diagnosis before you run anything else. INVALID_REG means the node registered and was rejected, which is not the same as an operator draining it.

2.2 Ask the node what it actually has

Do
ssh c2 slurmd -C
You should see
NodeName=c2 CPUs=2 Boards=1 SocketsPerBoard=1 CoresPerSocket=1 ThreadsPerCore=2 RealMemory=1719
UpTime=0-00:03:10

1719 against a declared 3000. The CPU total matches — 2 either way — so the disagreement that matters is memory. The socket and thread split differs, because the hypervisor presents two threads of one core and the file describes them as two single-thread sockets; Slurm accepts either so long as the total agrees, and only a shortfall drains a node. The fault is in a file you can edit; the symptom appeared on a node.

2.3 Correct the declaration, with headroom

Do
cd /etc/slurm && git diff                # should be clean before you start
vi /etc/slurm/slurm.conf                 # find NodeName=c2, set RealMemory=1600
git diff -u slurm.conf | grep -E "^[+-]NodeName"
You should see
-NodeName=c2 CPUs=2 Boards=1 Sockets=2 CoresPerSocket=1 ThreadsPerCore=1 RealMemory=3000 State=UNKNOWN
+NodeName=c2 CPUs=2 Boards=1 Sockets=2 CoresPerSocket=1 ThreadsPerCore=1 RealMemory=1600 State=UNKNOWN

Declare below what slurmd -C reports, not at it. The kernel, the page cache and the node's own daemons need memory that jobs cannot have. 119 MB of headroom on a node this small.

2.4 Take the node out properly, then apply and return it

Do
scontrol update NodeName=c2 State=DRAIN Reason="memory redeclared, $(date +%F) <you>"
scontrol reconfigure
sleep 45
scontrol update NodeName=c2 State=RESUME
sinfo -N -l
You should see
Sat Sep 19 15:28:29 2026
NODELIST   NODES PARTITION       STATE CPUS    S:C:T MEMORY TMP_DISK WEIGHT AVAIL_FE REASON
c1             1   normal*       mixed 2       2:1:1   1600        0      1   (null) none
c2             1   normal*        idle 2       2:1:1   1600        0      1   (null) none

Changing what a node is declared to be changes the terms under which running jobs were allocated, so you drain first even when the node is already idle. The reason text is read by whoever is on shift next — say what, when and who.

Both nodes now read 1600, and c2's REASON is empty. The sleep 20 matters: the reconfigure restarts the controller and c2 has to register again, and if you resume too early the state prints as idle* — the trailing star means the node is not answering yet, not that anything is wrong. Measured: 20 seconds is not enough and 45 is. If you still see the star, wait and re-run sinfo -N -l; nothing needs fixing.

03Write the three new queues8 min
GoalThe configuration file describes four queues and the diff shows exactly what you changed. Nothing is live yet.

3.1 Move the default off the old queue

Do — edit the existing normal line
PartitionName=normal Nodes=c1,c2 Default=NO State=UP \
  MaxTime=04:00:00 DefaultTime=01:00:00 PriorityTier=1 AllowAccounts=ALL

Exactly one partition may carry Default=YES. standard is about to take it. Job 101 keeps running in normal — a partition losing the default flag does not disturb work inside it.

3.2 Add the three new partitions

Do — add below the marker line
PartitionName=standard Nodes=c1,c2 Default=YES State=UP \
  MaxTime=04:00:00 DefaultTime=01:00:00 PriorityTier=1 AllowAccounts=ALL

PartitionName=debug Nodes=c1,c2 Default=NO State=UP \
  MaxTime=00:30:00 DefaultTime=00:10:00 PriorityTier=100 AllowAccounts=ALL

PartitionName=restricted Nodes=c2 Default=NO State=UP \
  MaxTime=04:00:00 DefaultTime=01:00:00 PriorityTier=1 AllowAccounts=chem

Six decisions are encoded there: node set, default flag, default time, maximum time, access control and priority tier. DefaultTime matters most — leave it out and a five-minute test job reserves four hours of the node's future, and the cluster looks full while it is idle.

AllowAccounts takes an account name. The accounting database already knows who is in chem, so there is one membership list rather than two.

04Apply the change and read it back7 min
GoalThe four queues are loaded, the controller log is clean, and job 101 is untouched.
CarefulUse scontrol reconfigure, not systemctl restart. Reconfigure makes the running daemons re-read the file and leaves running jobs alone. A restart takes the service down, depends on the state directory and the parse succeeding, and needs a change window even though it is recoverable.

4.1 Apply, then read the log immediately

Do
scontrol reconfigure
journalctl -u slurmctld --since "2 min ago" --no-pager | tail -15
You should see
slurmctld[3941]: Recovered state of 2 nodes
slurmctld[3941]: Recovered JobId=101 StepId=batch
slurmctld[3941]: Recovered information about 1 jobs
slurmctld[3941]: select/cons_tres: part_data_create_array: preparing for 4 partitions
slurmctld[3941]: read_slurm_conf: backup_controller not specified
slurmctld[3941]: Running as primary controller
slurmctld[3941]: child started successfully
slurmctld[3594]: Relinquishing control to new slurmctld process

Silence from scontrol reconfigure is not success. A parse error appears here within seconds and names the line, and the controller keeps running on the old configuration while you fix it. On this release a reconfigure does not edit the running daemon in place — it starts a fresh one, hands over and recovers state, which is why you see Relinquishing control and a job being recovered. Running work is untouched either way. The timestamps and process ids will be yours, and preparing for 4 partitions is the line that says your edit landed.

05Two QOS, with limits, attached10 min
GoalTwo named limit sets exist, each refuses at submission rather than holding jobs pending, and every user can still submit ordinary work.

These do not go in the configuration file. They live in the accounting database, so the commands are different and no reload is needed — they take effect for new submissions at once.

5.1 Create both, then set their limits

Do
sacctmgr -i add qos debugcap
sacctmgr -i add qos pilotcap

sacctmgr -i modify qos debugcap set Priority=1000 \
  MaxJobsPerUser=2 MaxSubmitJobsPerUser=4 Flags=DenyOnLimit
sacctmgr -i modify qos pilotcap set Priority=0 \
  MaxWall=02:00:00 Flags=DenyOnLimit
You should see
 Adding QOS(s)
  debugcap
 Settings
  Description    = debugcap
 Adding QOS(s)
  pilotcap
 Settings
  Description    = pilotcap
 Modified qos...
  debugcap
 Modified qos...
  pilotcap

A new QOS is unlimited until you set limits, not restrictive. MaxJobsPerUser is how many run at once; MaxSubmitJobsPerUser is how many exist at all, running plus pending.

DenyOnLimit is why this is the kinder configuration. Without it a job over its limit pends against something it can never satisfy, and the user gets silence until Thursday. With it they get an error at 09:15 they can act on.

5.2 Confirm the limits landed

Do
sacctmgr show qos format=Name,Priority,MaxWall,MaxJobsPU,MaxSubmitPU,Flags
You should see
      Name   Priority     MaxWall MaxJobsPU MaxSubmitPU                Flags
---------- ---------- ----------- --------- ----------- --------------------
    normal          0
  debugcap       1000                     2           4          DenyOnLimit
  pilotcap          0    02:00:00                                DenyOnLimit

The names used to set a limit and the names used to display it are not always the same string. You set MaxJobsPerUser; it displays as MaxJobsPU. Blank means unlimited.

5.3 Attach them to the three users

Do
sacctmgr -i modify user lmarchetti set QOS=normal,debugcap,pilotcap DefaultQOS=normal
sacctmgr -i modify user dpatel     set QOS=normal,debugcap,pilotcap DefaultQOS=normal
sacctmgr -i modify user rkoenig    set QOS=normal,debugcap          DefaultQOS=normal

sacctmgr show assoc format=Account%-12,User%-12,QOS%-40
You should see
 Modified user associations...
  C = hpca100    A = chem                 U = lmarchetti
 Modified user associations...
  C = hpca100    A = chem                 U = dpatel
 Modified user associations...
  C = hpca100    A = bio                  U = rkoenig
Account      User         QOS
------------ ------------ ----------------------------------------
root                      normal
root         root         normal
bio                       normal
bio          rkoenig      debugcap,normal
chem                      normal
chem         dpatel       debugcap,normal,pilotcap
chem         lmarchetti   debugcap,normal,pilotcap
Carefulset QOS= replaces the whole list, it does not add to it. That is why normal is typed out again each time. Leave it out and the user can no longer submit ordinary work, and the only way back is a reset.

DefaultQOS matters because most users never pass --qos. Setting it to normal means the caps apply only when somebody asks for them.

Seven rows, not three. Every account has a row of its own as well as a row per user, and root has two. Rows sort alphabetically, so bio comes before chem. The %-12 and %-40 widths are not decoration: at its default width the QOS column is 20 characters and cuts debugcap,normal,pilotcap down to debugcap,normal,pil+, so you cannot see whether the list you set is the list that landed.

Check
sacctmgr -n -P show qos format=Name,Flags | grep -c DenyOnLimit && test $(sacctmgr -n -P show assoc format=User,QOS | grep -cE "^(lmarchetti|dpatel|rkoenig)\|.*\bnormal\b") -eq 3 && echo "TASK 5 PASS"
Pass: 2 then TASK 5 PASS — both flagged, all three users keep normal.

06Prove each rule in pairs12 min
GoalThree rules each demonstrated by one submission accepted and one refused, with the refusal wording recorded.

A rule is not proven by a submission that succeeds. A limit that never refuses anything has not been shown to exist, and the limit nobody exercised is the one that is wrong.

6.1 Ask before you submit

Do
su - rkoenig -c 'sbatch --test-only -A bio -p restricted -t 00:10:00 --wrap="sleep 20"'
You should see
allocation failure: Invalid account or account/partition combination specified

--test-only validates a submission against the limits without queueing it. Note the wording: a rejected --test-only says allocation failure:, while the same gate reached by a real submission in 6.3 says sbatch: error: Batch job submission failed:. Same gate, two different strings, and Task 8 has to translate both. The refusal message names the gate that refused — read it as the name of a gate, not as an explanation.

Two limits are visible at once. Four submissions were allowed to exist and two of them run, which is MaxJobsPerUser=2 holding the third and fourth pending. The fifth was refused outright, which is MaxSubmitJobsPerUser=4 with DenyOnLimit. The second user experience is much better than the first.

Pending rows sort above running ones, and your job numbers will differ from these — what matters is two running, two pending, one refused.
