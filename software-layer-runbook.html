01What is actually installed12 min
GoalA map of the site stack — every application, and every build of it that exists.

1.1 Ask what you can load

Do
module purge
module avail
Look for
  • How many entries, under how many directories.
  • Which are applications, and which are compilers or build tools.
  • Any application you would expect on a research cluster and cannot see.
This site runs far more than you are seeing. A hierarchical module system lists only what is loadable from where you stand. The rest is behind something.

1.2 Find the rest

There is a second way to question the module system. It reports everything it knows about, loadable or not, and tells you what must be loaded first in each case. Find it and use it — module --help, and your M1-S3 notes.
Look for
  • How many versions of each application exist.
  • What you are told to load first, and whether that differs between versions of the same application.
  • Which applications appear once, and which appear several times.

1.3 Ask the package manager the same thing

Do
spack find
spack find -l --show-full-compiler
Look for
  • Whether this agrees with the module system, or shows more.
  • What the compiler column tells you that module names did not.
  • Anything installed with no module at all.
Write it like thisexample from another site — two toolchains, three applications
## 1. Stack map

| Application   | intel-2023 + IMPI | aocc-4.1 + OpenMPI |
| ------------- | ----------------- | ------------------ |
| GROMACS 2023  | yes               | yes                |
| LAMMPS 2Aug23 | yes               | —                  |

Two toolchains. GROMACS is built for both; the other two for one

02Where an application's libraries come from13 min
GoalEvery shared library one binary uses, sorted by where it came from, on the login node and on a compute node.

2.1 Load a toolchain, find a binary

Do
module purge
module load gcc/12.3.0 openmpi/4.1.6 netcdf-c/4.9.2
which ncdump
module list
Look for
  • How many modules ended up loaded, against the three you asked for.
  • What the binary's path says about how this stack is laid out.

2.2 Resolve here, then on a compute node

Do
ldd $(which ncdump) | tee $HOME/course-repo/m7-s1/login.txt

srun -p standard -n 1 -t 00:02:00 \
  bash -lc 'module load gcc/12.3.0 openmpi/4.1.6 netcdf-c/4.9.2; ldd $(which ncdump)' \
  | tee $HOME/course-repo/m7-s1/compute.txt

diff $HOME/course-repo/m7-s1/login.txt $HOME/course-repo/m7-s1/compute.txt
awk '{print $3}' $HOME/course-repo/m7-s1/login.txt | grep '^/' | sort -u
Look for
  • How many libraries one program depends on.
  • How many distinct places they are being found in. Group the paths by their leading directories.
  • Any line with no path, and what that would mean.
  • Whether login and compute agree — and if so, what makes that true rather than lucky.
Write it like thisexample from another site — name your own groups
## 2. Library trace — binary: 

### 
/usr/lib64/libm.so.6
/usr/lib64/libpthread.so.0

### 
/opt/apps/intel-2023/impi/lib/libmpi.so.12

### 
/opt/apps/intel-2023/gromacs-2023/lib/libgromacs.so.8

12 libraries, 3 origins, nothing unresolved.
Login and compute resolved identically.
If the user switched toolchain, groups 2 and 3 would change
and group 1 would not.
A path is not an originTwo libraries under the same parent can come from different places. Decide each by what put it there. Name your groups for the origin, not the directory.
03A binary that will not run9 min
GoalThe class of failure, the evidence for it, and what you would tell the user.

3.1 Read the ticket, then try it in both places

Do
cat /projects/course/m7-s1/repro/ticket.txt
/projects/course/m7-s1/repro/wavesolve
srun -p standard -n 1 -t 00:02:00 /projects/course/m7-s1/repro/wavesolve
Look for
  • The error text, word by word. It names something specific — write down exactly what.
  • Whether it names a file that is absent, or something else.
  • Whether both runs failed the same way, and what that comparison rules out.

3.2 Look inside the binary

Do
file /projects/course/m7-s1/repro/wavesolve
ldd  /projects/course/m7-s1/repro/wavesolve
objdump -T /projects/course/m7-s1/repro/wavesolve | sort -u -k5
ldd --version | head -1
Look for
  • Whether ldd found everything it was looking for.
  • In the objdump output, what the binary demands of its libraries — not just which libraries.
  • What this machine reports about itself, and how that compares.
Four commands, four different questionsWhat kind of file it is; whether its libraries resolve; what it demands of them; what this machine provides. Three can look fine while the program still cannot start.
Write it like thisexample — a different failure class
## 3. Failure report — wavesolve

Class:     built for the wrong processor architecture
Evidence:  `file` reports aarch64; the nodes are x86-64
Both nodes: failed identically, so this is not a per-node
           configuration difference
Remedy:    the user obtained a build for the wrong platform.
           They need the x86-64 build, or to build here.
Whose:     theirs — nothing I change on the cluster fixes it
"It does not work" is not a className the mechanism.

05An application with no owner8 min
GoalWhere one application came from, who owns it, and whether it works where users need it.

5.1 Find out what it is

Do
module show kestrelfit/0.9.3
ls -la /opt/software/manual/kestrelfit/0.9.3/
stat -c '%U %G %y %n' /opt/software/manual/kestrelfit/0.9.3/bin/*
spack find kestrelfit
Look for
  • Where it sits on disk, against everything you found in task 1.
  • The owner column — what it says, and whether that name means anything here.
  • What you would expect beside an installed application and cannot find.
  • What the package manager says, including when it says nothing.

5.2 Run it where users would

Do
module load kestrelfit/0.9.3
kestrelfit --version
srun -p standard -n 1 -t 00:02:00 bash -lc 'module load kestrelfit/0.9.3; kestrelfit --version'

5.3 If they differ, find out why

Do
ldd $(which kestrelfit)
srun -p standard -n 1 -t 00:02:00 bash -lc 'module load kestrelfit/0.9.3; ldd $(which kestrelfit)'
ldconfig -p | wc -l
srun -p standard -n 1 -t 00:02:00 bash -c 'ldconfig -p | wc -l'
Look for
  • Which ldd line differs between the two, if any.
  • What the two counts say about how these machines were built.
  • Whether this is the same class of failure as task 3 or a different one — and how you can tell.
