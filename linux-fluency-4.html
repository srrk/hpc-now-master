Lab 15 / 17 · 20 minutes · Shell Scripting

set -euo pipefail, Loops, Functions, Git

Follows: the minimum serious script, variables, conditionals, loops, functions, exit codes, trap, SSH patterns, jq, Git discipline.

Working directory. Create a dedicated directory for this session's scripts before starting.

mkdir -p ~/lab-scripts && cd ~/lab-scripts
Ex 1

Write a script with set -euo pipefail that loops over hostnames

Create the script below. It loops over three hostnames and runs ssh hostname on each. One hostname is intentionally unreachable — observe what happens with and without ConnectTimeout and || echo FAILED.

Create the script
cat > ~/lab-scripts/check-hosts.sh << 'EOF'
#!/bin/bash
set -euo pipefail

HOSTS="mylab.hpc.now doesnotexist.hpc.now mylab.hpc.now"

for host in $HOSTS; do
    echo "=== ${host} ==="
    ssh -o ConnectTimeout=5 \
        -o StrictHostKeyChecking=no \
        "${host}" "hostname" 2>/dev/null \
        || echo "FAILED: ${host}"
done

echo "Loop complete"
EOF
chmod +x ~/lab-scripts/check-hosts.sh
bash ~/lab-scripts/check-hosts.sh
Expected output
=== mylab.hpc.now ===
mylab
=== doesnotexist.hpc.now ===
FAILED: doesnotexist.hpc.now
=== mylab.hpc.now ===
mylab
Loop complete

ConnectTimeout=5 prevents the loop hanging on the dead host.
|| echo FAILED keeps the loop running despite set -e being active.

Remove || echo FAILED and re-run. The script exits at the unreachable host and never reaches the third. This is what set -e does — and why the || is necessary when failure is expected and must be handled rather than propagated.

Ex 2

Add a function that checks whether a host responds

Append the function to the script
cat > ~/lab-scripts/check-hosts-v2.sh << 'EOF'
#!/bin/bash
set -euo pipefail

HOSTS="mylab.hpc.now doesnotexist.hpc.now mylab.hpc.now"

check_host() {
    local host="$1"
    if ssh -o ConnectTimeout=5 \
           -o StrictHostKeyChecking=no \
           "${host}" "hostname" >/dev/null 2>&1; then
        echo "OK: ${host}"
        return 0
    else
        echo "FAIL: ${host}" >&2
        return 1
    fi
}

for host in $HOSTS; do
    check_host "${host}" || true
done

echo "Check complete"
EOF
chmod +x ~/lab-scripts/check-hosts-v2.sh
bash ~/lab-scripts/check-hosts-v2.sh
Expected output
OK: mylab.hpc.now
FAIL: doesnotexist.hpc.now
OK: mylab.hpc.now
Check complete

OK lines go to stdout. FAIL lines go to stderr.
Both appear in the terminal but can be separated in pipelines.

Note local host="$1" inside the function. Without local, the variable host would be global — a name clash with the loop variable above it would produce silent, confusing bugs.

Ex 3

Add a trap EXIT handler

Add a trap that prints a completion message regardless of how the script exits — including on failure.

cat > ~/lab-scripts/check-hosts-v3.sh << 'EOF'
#!/bin/bash
set -euo pipefail

HOSTS="mylab.hpc.now doesnotexist.hpc.now mylab.hpc.now"

cleanup() {
    echo "--- Script exiting at $(date '+%H:%M:%S') ---" >&2
}
trap cleanup EXIT

check_host() {
    local host="$1"
    if ssh -o ConnectTimeout=5 \
           -o StrictHostKeyChecking=no \
           "${host}" "hostname" >/dev/null 2>&1; then
        echo "OK: ${host}"
        return 0
    else
        echo "FAIL: ${host}" >&2
        return 1
    fi
}

for host in $HOSTS; do
    check_host "${host}" || true
done

echo "Check complete"
EOF
chmod +x ~/lab-scripts/check-hosts-v3.sh
bash ~/lab-scripts/check-hosts-v3.sh
Expected output
OK: mylab.hpc.now
FAIL: doesnotexist.hpc.now
OK: mylab.hpc.now
Check complete
--- Script exiting at HH:MM:SS ---

The cleanup handler fires on normal exit.
It also fires if the script is killed or fails mid-run.
Ex 4

Pipe a response through jq to extract a single field

Use curl and jq to extract a field from a public JSON API. The example uses a simple public endpoint that requires no authentication.

curl -s https://httpbin.org/json | jq '.slideshow.title'
Expected output
"Sample Slide Show"
Filter a list — select matching elements
curl -s https://httpbin.org/json | jq '.slideshow.slides[] | .title'
Raw output for use in a pipeline
curl -s https://httpbin.org/json | jq -r '.slideshow.author'
Expected output — -r flag
Yours Truly

Without -r: "Yours Truly" — quoted JSON string.
With -r: Yours Truly — raw string, pipeable to other commands.
If jq is not installed

Install it: sudo dnf install -y jq. If httpbin.org is unreachable, use any local JSON file: echo '{"key":"value"}' | jq '.key'

cat > ~/lab-scripts/.gitignore << 'EOF'

Lab 16 / 17 · 10 minutes · Time Synchronization

chrony, chronyc, and Scheduled Work

Follows: why clock sync matters, the chrony service, chronyc sources and tracking output, cron and systemd timers at awareness level.

Ex 1

Read chronyc sources — identify the best source and its Reach

chronyc sources
Expected output — read every column
MS Name/IP address         Stratum Poll Reach LastRx Last sample
===============================================================================
^* time.example.com              2   6   377    42   -123us[ -145us] +/-  3ms
^+ time2.example.com             2   6   377    38   +201us[ +180us] +/-  5ms
^? time3.example.com             0  10     0   10y     +0ns[   +0ns] +/-    0s

^* = current best source (there must be exactly one)
377 in Reach = all 8 recent polls succeeded (octal all-ones)
^? with Reach 0 = unreachable — this source is not contributing

Find the line with ^*. Note its Reach value and its Last sample offset. If no ^* line exists, chrony is not synchronized — investigate with systemctl status chronyd.

Reach 377 means healthy. Any value below 377 means some recent polls failed. Reach 0 on every source means the host has no working time reference — a serious operational problem.

Ex 2

Read chronyc tracking — record System time offset and Stratum

chronyc tracking
Expected output — the key fields
Reference ID    : C0A80A01 (time.example.com)
Stratum         : 3
System time     : 0.000023514 seconds slow of NTP time
Last offset     : -0.000012ms
Leap status     : Normal

Stratum 3 = three hops from a GPS-disciplined clock — normal.
Stratum 16 = not synchronized — this is a problem.
Leap status Normal = correct. Anything else needs investigation.
System time offset in microseconds = the host is well synchronized.

Record the System time offset value. On a well-synchronized host this will be in the range of microseconds to a few milliseconds. An offset of seconds or minutes means the clock is drifting badly.

Ex 3

Check the chrony service — confirm active and enabled

systemctl status chronyd
systemctl is-active chronyd
systemctl is-enabled chronyd
Expected output
active
enabled

Both must be true. active = running now. enabled = will start at boot.
A host where chronyd is active but not enabled will lose time sync
after the next reboot.
Ex 4

List scheduled timers and decode three entries

systemctl list-timers --no-pager
Expected output — read each column
NEXT                        LEFT    LAST                  PASSED UNIT
Thu 2026-04-25 03:00:00 UTC 13h     Thu 2026-04-24 03:00  11h    logrotate.timer
Thu 2026-04-25 00:00:00 UTC 10h     Wed 2026-04-23 00:00  1day   fstrim.timer
Thu 2026-04-25 10:14:01 UTC 1min    Thu 2026-04-25 09:14  59min  systemd-tmpfiles-clean.timer

NEXT = when will this timer next fire
LAST/PASSED = when did it last fire and how long ago
UNIT = the timer — and the .service it activates has the same base name

Pick three timers from the output. For each one, answer: when does it next run? What service does it trigger? How often does it run based on NEXT and LAST?

Ex 5

Locate and decode a crontab entry

ls /etc/cron.d/
cat /etc/cron.d/* 2>/dev/null | grep -v '^#' | grep -v '^$' | head -10
Expected output — a crontab line
30 2 * * *  root  /usr/local/sbin/some-cleanup-script.sh

Decode left to right:
30  = minute 30
2   = hour 2 (2:30 AM)
*   = any day of month
*   = any month
*   = any day of week
root = run as root
/usr/local/sbin/... = the command

If /etc/cron.d/ is empty, check crontab -l for your user's own crontab. Decode whichever entry you find — minute, hour, day-of-month, month, day-of-week, user (if present), command.

Lab 17 / 17 · 20 minutes · Configuration Discipline

All Six Rules — Applied to a Real Config File

Follows: the six rules (backup, validate, diff, version-control, stage, rollback), YAML, INI, and env file formats.

This is the most important lab in the Linux Fluency series. Every subsequent module — A1 through A12 — assumes these six habits are already formed. Work through each exercise deliberately. The goal is not to complete the steps. The goal is to internalise the sequence so it runs automatically.

The working file for this lab is /etc/chrony.conf. You will make a real, valid change to it — raise the makestep threshold — applying all six rules in sequence.

Rule 1

Back up before editing — with a date-stamped filename

sudo cp /etc/chrony.conf \
  /etc/chrony.conf.bak-$(date +%Y%m%d-%H%M%S)
ls -la /etc/chrony.conf*
Expected output
-rw-r--r-- 1 root root  xxx Apr 25 10:00 /etc/chrony.conf
-rw-r--r-- 1 root root  xxx Apr 25 10:15 /etc/chrony.conf.bak-20260425-101512

The backup sits next to the live file with a precise timestamp.
It is findable by anyone running ls in /etc/.

The date-stamped suffix survives multiple edits in the same day. A suffix of .bak without a timestamp is overwritten on the second edit. Record the exact backup filename — you will use it in Rule 3 and Rule 6.

Rule 2

Validate syntax — first confirm the current config is clean, then test a bad one

Confirm the current config validates
sudo chronyd -Q 2>&1 | head -5
echo "Exit code: $?"
Expected output
2026-04-25T10:15:12Z chronyd version 4.x starting (+CMDMON +NTP ...)
2026-04-25T10:15:12Z Loaded 2 sources from file /etc/chrony.conf
Exit code: 0

Exit code 0 = config is valid. The validator reads the file without
starting the daemon. Safe to run without affecting the running service.
Demonstrate what a syntax error looks like — on a copy
sudo cp /etc/chrony.conf /tmp/chrony-bad.conf
echo "this is not valid chrony syntax" | sudo tee -a /tmp/chrony-bad.conf
sudo chronyd -Q -f /tmp/chrony-bad.conf 2>&1 | tail -3
echo "Exit code: $?"
Expected output
Error: unknown directive 'this'
Exit code: 1

Non-zero exit code = bad config. If you had restarted chronyd with
this file, the service would have failed to start.

The validator shows exactly what is wrong and where. This is the difference between finding the mistake before the restart and finding it after production is down.

Edit

Make the change — raise the makestep threshold

The current makestep line allows step corrections only in the first 3 clock updates. Raise the threshold to 60 seconds and allow it in the first 5 updates — useful for nodes that boot with badly drifted clocks.

grep makestep /etc/chrony.conf         # see the current value first
sudo sed -i 's/^makestep.*/makestep 60 5/' /etc/chrony.conf
grep makestep /etc/chrony.conf         # confirm the change
Expected output
makestep 60 5

The line has changed. Now validate before touching the service.
Rule 2

Validate the edited config before restarting anything

sudo chronyd -Q 2>&1 | tail -3
echo "Exit code: $?"
Expected output
... Loaded 2 sources from file /etc/chrony.conf
Exit code: 0

Valid. Safe to proceed. If the exit code were non-zero here,
the service must not be restarted until the error is fixed.
Rule 3

Diff to confirm exactly what changed — read every line

Replace TIMESTAMP with the actual timestamp from your backup filename.

diff -u /etc/chrony.conf.bak-TIMESTAMP /etc/chrony.conf
Expected output
--- /etc/chrony.conf.bak-20260425-101512  2026-04-25 10:15:12
+++ /etc/chrony.conf                      2026-04-25 10:18:34
@@ -5,7 +5,7 @@
 pool 2.rhel.pool.ntp.org iburst
 driftfile /var/lib/chrony/drift
 rtcsync
-makestep 1.0 3
+makestep 60 5
 leapsectz right/UTC
 logdir /var/log/chrony

Lines prefixed with - are what was removed.
Lines prefixed with + are what was added.
Only one line changed. This is what was intended.

If the diff shows more than the one expected line changed — stop. Find out why before proceeding. A diff that shows unexpected changes is a signal that the edit did something unintended. The time to catch it is now, before the restart.

Rule 4

Commit the change to the Git repository

cd ~/lab-scripts
cp /etc/chrony.conf chrony.conf
git add chrony.conf
git commit -m "raise makestep threshold to 60s, allow in first 5 updates

Previous setting (makestep 1.0 3) caused nodes with drifted hardware
clocks to reject small corrections on boot, leaving them out of sync
until the fourth NTP poll. Raised to 60s threshold, 5 update window
to allow step corrections on nodes that boot with significant drift."
git log --oneline
Expected output
def5678 raise makestep threshold to 60s, allow in first 5 updates
abc1234 add gitignore excluding swap files, keys, and secrets
789abcd add host check script with function, trap, and ConnectTimeout

In six months, when someone reads git log and asks why makestep is set to 60, the commit message body answers the question. "fix config" would not answer it. The body takes thirty seconds to write and saves an investigation.

Rule 5

Stage before fleet-wide deployment — the written plan

This is a written exercise. In a real cluster, you would apply this change to one node first. Write the staging plan below as a one-paragraph handover note.

Write the staging plan to a file
cat > ~/lab-scripts/staging-plan.txt << 'EOF'
Staging plan — chrony.conf makestep change

1. Apply to cn01 only: scp chrony.conf cn01:/etc/chrony.conf
2. Validate on cn01: ssh cn01 "chronyd -Q"
3. Restart on cn01: ssh cn01 "systemctl restart chronyd"
4. Verify on cn01: ssh cn01 "chronyc tracking | grep 'Leap status'"
5. Watch for 5 minutes — confirm Leap status remains Normal
   and System time offset does not grow.
6. If step 5 passes, roll out to cn02-cn05 (five nodes).
7. Verify all five. Wait 10 minutes.
8. Roll out to remaining compute nodes.
9. Document completion in the change ticket.

Rollback at any stage: restore from backup and restart chronyd.
EOF
cat ~/lab-scripts/staging-plan.txt

The staging plan exists before the change goes wider. If something goes wrong on cn01, the cluster keeps running because no other node was touched. This is the discipline that makes fleet-wide changes safe.

Rule 6

Know your rollback — execute it from memory

State the rollback procedure. Then execute it — restore the original config and verify the service is healthy. Replace TIMESTAMP with your actual backup timestamp.

Before running the rollback: write down the two commands from memory. Close the runbook if needed. The rollback must be executable under time pressure without reference material.

Execute the rollback
sudo cp /etc/chrony.conf.bak-TIMESTAMP /etc/chrony.conf
sudo systemctl restart chronyd
grep makestep /etc/chrony.conf        # confirm original value is restored
systemctl is-active chronyd           # confirm service is running
chronyc tracking | grep 'Leap status' # confirm Normal
Expected output
makestep 1.0 3      ← original value restored
active
Leap status     : Normal

Two commands. Executed in under ten seconds. This is what rollback looks like when it is prepared in advance. When production is down and every second matters, this is the difference between a two-minute recovery and a twenty-minute one.

the six rules — permanent reference

Every config file edit. Every service. Every time. Without exception.

Rule 1

Back up before editing

Every edit begins here. Date-stamped. Next to the file. cp file file.bak-$(date +%Y%m%d-%H%M%S)

Rule 2

Validate syntax before restarting

Use the service's own validator. Zero exit code = valid. Restart only after validation passes. sshd -t · nginx -t · visudo -c · chronyd -Q · systemctl daemon-reload

Rule 3

Diff to understand what changed

Read every line before restarting. The intended change should be there. Nothing else should be. diff -u file.bak-TIMESTAMP file

Rule 4

Version-control where possible

Commit with a message that says what changed and why. The commit message is the audit trail. git add · git commit -m 'what and why' · git push

Rule 5

Stage before fleet-wide deployment

One host first. Verify. Then a handful. Then the fleet. The discipline applies even when the change feels trivial.

Rule 6

Know your rollback

Know it before making the change — not during the incident. Two commands: restore the backup, restart the service. cp file.bak-TIMESTAMP file && systemctl restart svc
