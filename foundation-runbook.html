cluster topology

Two nodes. One entry point. One shared filesystem. This is the smallest valid HPC cluster — the structural pattern holds at any scale.

aws parallelcluster · this session's environment

         ↑
   Laptop SSHs here first
Head node Management and login plane. Same access model as an OOB management server in a DC rack.
Compute node Workload execution. No public IP — accessed through the head node only.
Shared /home Single NFS export from head node, mounted on both nodes. Same home directory on either node.
NFS mount mode hard — client retries indefinitely if server unreachable. Correct for a cluster. A soft mount would propagate I/O errors to running jobs.

BLOCK 02 Filesystem Hierarchy

The Linux filesystem is a floor plan. Every directory has a fixed purpose. Knowing the floor plan means always knowing where to look.

DirectoryPurposeDC equivalent
/bin /sbinEssential system commandsFirmware — always present
/etcAll configuration filesCMDB and config store
/homeUser home directoriesPersonal network share per user
/varLogs, spool, variable runtime dataLog aggregator landing zone
/tmpTemporary files — wiped on rebootVolatile scratch — never store here
/procLive kernel and process data — not real files on diskReal-time telemetry from the kernel
/sysHardware and kernel interfaceHardware management bus
/devDevice files — every disk, NIC, terminalPhysical device inventory
/mnt /mediaMount points for filesystemsExternal storage attachment points
2.1
$ ls -la /
2.2
$ cat /proc/cpuinfo | head -30

CPU model, core count, and feature flags. Every monitoring tool — top, htop, lscpu — reads from here. This is the source, not an abstraction.

2.3
$ cat /proc/meminfo | head -20

MemAvailable is the operationally relevant field — not MemFree. Available includes memory the kernel can reclaim from cache.

2.4
$ cat /proc/loadavg

Output: 0.00 0.01 0.05 1/98 1234 — three numbers are load average over 1, 5, and 15 minutes. Load average reflects scheduler queue depth, not CPU utilisation percentage. On a single-core instance, 1.0 means fully occupied. Values above core count mean processes are queuing.

2.5
$ ls /sys/class/net

Expected: eth0 and lo — every network interface the kernel has enumerated.

2.6
$ ls /sys/block

Expected: xvda — the root disk. Every block device visible to the OS has an entry here.

2.7
$ cat /etc/os-release
2.8
$ cat /etc/hosts

Both nodes are listed here. ParallelCluster wrote the compute node's IP into this file at cluster creation. Name resolution between nodes works without a DNS server because of this file. In Module 9, Ansible manages entries like this across all nodes.

2.9
$ ls /var/log
2.10
$ sudo tail -20 /var/log/messages
2.11
$ sudo tail -f /var/log/messages

Follow mode — output updates in real time. Ctrl+C to exit. In Module 8, Prometheus automates reading metrics equivalent to this feed and alerting when values cross thresholds.

Module 2 — navigating node roles on a live cluster. Module 8 — Prometheus reads /proc metrics automatically; this is the manual version.

BLOCK 03 Process and Load Visibility

/proc contains live process state. top, ps, and iostat are structured views of what is already there — they contact no external service.

3.1
$ top
FieldMeaningWhen to investigate
load averageQueue depth over 1/5/15 minsAny value above core count
id% CPU idleBelow 10%
wa% CPU waiting for I/OAbove 20% — storage bottleneck
buff/cacheRAM used as disk cacheNormal — kernel reclaims when needed
3.2
Inside top: M → sort by memory P → sort by CPU q → quit
3.3
$ ps aux

All processes, all users, full detail.

3.4
$ ps aux | grep slurmctld

SLURM controller process. Should be running on the head node. First step of any scheduler diagnostic — confirm the daemon is alive before investigating queue behaviour.

3.5
$ ps auxf | head -40

Process tree — shows parent-child relationships.

3.6
$ sudo yum install -y sysstat
3.7
$ iostat -x 2 5
FieldMeaningReference value
%utilDisk busy percentageAbove 80% — saturated
awaitAverage I/O latency in msSingle digits on SSD
r/s w/sRead and write ops per secondBaseline first, then alarm on spikes
3.8
$ sleep 300 & $ echo "Test process PID: $!"
3.9
$ ps aux | grep sleep
3.10
$ kill <PID>

SIGTERM — requests the process to stop cleanly. Always the correct first move.

3.11
$ kill -9 <PID>

SIGKILL — unconditional termination. Use when SIGTERM does not work. A process killed with SIGKILL exits with code 137 from the shell's perspective (128 + 9). This appears in job accounting records as a distinguishable failure mode.

3.12
$ echo "Exit code of last command: $?"

Every command returns an exit code. 0 means success. Any non-zero value means failure. Scripts that do not check $? silently continue through failures and produce incorrect results without any visible error.

3.13
$ ps aux | grep sleep

Confirm the process is gone.

BLOCK 04 Shell Environment Model

A job scheduler launches a non-interactive, non-login shell. This is a different environment from the terminal session used to write and test job scripts. This difference explains the majority of "works on the login node, fails in the job" failures.

Shell type
When it runs
Files sourced
Login shell
SSH into a node
/etc/profile → /etc/profile.d/* → ~/.bash_profile
Interactive non-login
Opening a new terminal
~/.bashrc
Non-interactive (batch job)
Scheduler-launched job
Nothing by default
4.1
$ echo $SHELL $ echo $0

Identifies the current shell type.

4.2
$ cat ~/.bash_profile

Sourced on login. Typically calls ~/.bashrc and sets environment variables that should persist across the session.

4.3
$ cat ~/.bashrc

Sourced for interactive shells. Environment variables set only here may not be visible to batch jobs.

4.4
$ env | sort | head -40
VariableHPC risk if wrong
PATHWrong version of MPI or compiler loaded for the job
LD_LIBRARY_PATH"Library not found" errors in jobs while working fine interactively
LD_PRELOADSilently replaces optimised libraries with generic ones
4.5
$ env | grep -i ld_
4.6
# Simulate what a batch job environment looks like $ env -i HOME=$HOME USER=$USER PATH=/usr/bin:/bin bash --norc --noprofile $ env | sort

Compare with step 4.4. Variables set in ~/.bashrc and ~/.bash_profile are absent. This is what a job sees by default. Job scripts must explicitly export any variables they depend on.

4.7
$ exit

Exit the clean environment and return to the normal shell.

BLOCK 05 Filesystem Concepts: Inodes, Mounts, and NFS

The mount command is the OS equivalent of presenting a LUN to a host. Above the mount point is the OS. Below it is the storage device.

5.1
$ df -hT

All mounted filesystems with types and usage. Look for the line with type nfs4 — that is the shared /home. Example line: 10.0.x.x:/home   nfs4   8.0G   /home

5.2
$ df -i

Inode usage per filesystem. A filesystem can exhaust inodes while disk space shows available — when this happens, no new files can be created. Running only df -h without df -i is a diagnostic error in HPC operations.

5.3
$ lsblk
5.4
$ lsblk -f

Adds filesystem type and UUID. First command to run when new storage appears on a node.

5.5
$ findmnt

Tree view of all mount points with sources, types, and options.

5.6
$ findmnt /home

Shows exact mount options in effect for /home. Look for hard in the options — this means the NFS client retries indefinitely rather than returning an error to the application if the server is unreachable.

5.7
$ echo "written on head node" > ~/nfs-test.txt $ cat ~/nfs-test.txt
5.8
$ cat /etc/hosts

Find the compute node hostname from this file before SSHing to it.

5.9
$ ssh <compute-node-hostname>
5.10
$ hostname

Confirm the compute node.

5.11
$ cat ~/nfs-test.txt

The file written in step 5.7 on the head node is visible here. /home is not local to this node — it is the same NFS export mounted on both nodes.

5.12
$ echo "written on compute node" >> ~/nfs-test.txt
5.13
$ exit
5.14
$ cat ~/nfs-test.txt

Both lines present — one written from each node into the same NFS-backed file.

5.15
$ echo "test file" > ~/stat-test.txt $ stat ~/stat-test.txt
FieldMeaning
InodeUnique file ID on this filesystem — independent of filename
Blocks512-byte blocks consumed on disk
LinksNumber of directory entries pointing to this inode (hard links)
AccessPermission bits — owner / group / others
5.16
$ ls -li ~/

Inode numbers alongside filenames. Two filenames pointing to the same inode number are hard links — same data, two names.

5.17
$ cat /etc/fstab

Persistent mount configuration. Every line is a filesystem mounted at boot. The NFS entry for /home was written here by ParallelCluster. In Module 9, Ansible manages these entries across all nodes.

5.18

lsof and fuser: why a filesystem won't unmount.

# Open a file and keep it open in the background $ tail -f ~/nfs-test.txt & $ TAIL_PID=$! # Try to unmount /home — this will fail $ sudo umount /home

Expected: umount: /home: target is busy

# Find which process is holding the filesystem open $ lsof /home # fuser returns PIDs using the path directly $ sudo fuser -m /home # Stop the process, then unmount $ kill $TAIL_PID $ sudo umount /home $ df -hT | grep home # Remount — both nodes need /home $ sudo mount /home $ df -hT | grep home

Never unmount a shared filesystem without running lsof and fuser first. On a cluster with running jobs, an unexpected unmount of /home or scratch storage is an incident, not a maintenance operation.

Module 2 — cluster navigation lab. Module 5 — NFS is replaced by Lustre; the mount command and df -i check stay the same. Module 9 — fstab entries managed by Ansible across all nodes.

BLOCK 06 SSH and Key Management

SSH is the management plane for every node in the cluster. The ~/.ssh/config file is what makes that management plane scalable — one alias per host, no IP addresses typed manually after initial setup.

6.1
$ ls -la ~/.ssh/
6.2
$ stat ~/.ssh/hpc-key.pem

Permissions must be 400 or 600. SSH refuses to use a key file readable by others. This is enforced by SSH itself, not by convention.

6.3
$ chmod 400 ~/.ssh/hpc-key.pem
6.4
$ ssh-keygen -t ed25519 -C "hpc-course"

Accept default path. Set a passphrase. Generates: ~/.ssh/id_ed25519 (private — never copied anywhere) and ~/.ssh/id_ed25519.pub (public — installed on servers).

6.5
$ cat ~/.ssh/id_ed25519.pub

The public key is the lock. The private key is the physical key. Locks go on servers. The key stays on the laptop.

6.6
$ vim ~/.ssh/config
Host hpc-head HostName <head-node-public-ip> User ec2-user IdentityFile ~/.ssh/hpc-key.pem StrictHostKeyChecking no Host hpc-compute HostName <compute-node-private-ip> User ec2-user IdentityFile ~/.ssh/hpc-key.pem ProxyJump hpc-head

Save: Esc → :wq

6.7
$ chmod 600 ~/.ssh/config
6.8
$ ssh hpc-head $ hostname $ exit
6.9
$ ssh hpc-compute $ hostname $ exit

ProxyJump routes through the head node transparently. The compute node has no public IP — this is the only path from outside the VPC. This pattern holds whether the cluster has 2 nodes or 2000.

6.10
$ eval $(ssh-agent) $ ssh-add ~/.ssh/hpc-key.pem

Agent holds the decrypted key in memory for the session. Subsequent SSH connections do not prompt for the passphrase.

BLOCK 07 Networking: OS Tools

Concepts — IP addressing, routing, VLANs, RDMA — are assumed known. These four commands confirm network state from inside the OS.

7.1
$ ip addr show

All interfaces and their assigned IP addresses. Replaces the deprecated ifconfig.

7.2
$ ip route show

Kernel routing table. In a cluster with multiple network interfaces — management Ethernet and high-speed fabric — this table determines which traffic goes where. A misconfigured routing table silently sends job traffic over the wrong interface.

7.3
$ ss -tulnp
FlagMeaning
tTCP
uUDP
lListening only
nNumeric — no DNS resolution
pShow owning process

Look for slurmctld on port 6817. Port open = scheduler accepting connections. A process can be running (visible in ps aux) but not listening if it failed to bind the port — these are two different diagnostic facts.

7.4
$ ping -c 4 <compute-node-hostname>
7.5
$ traceroute <compute-node-hostname>

Expected: single hop — both nodes are in the same VPC subnet.

BLOCK 08 Reading a Job Script

A Slurm job script is a Bash script with #SBATCH directives at the top. The directives are instructions to the scheduler. Everything below them is the script the scheduler executes.

8.1
cat << 'EOF' > ~/test-job.sh #!/bin/bash #SBATCH --job-name=hello-hpc #SBATCH --nodes=1 #SBATCH --ntasks=1 #SBATCH --time=00:02:00 #SBATCH --output=/home/ec2-user/job-%j.out echo "Job started on node: $(hostname)" echo "Job ID: $SLURM_JOB_ID" echo "Working directory: $(pwd)" date EOF
8.2
$ cat ~/test-job.sh
DirectiveMeaning
--job-nameLabel for the job in the queue
--nodesNumber of compute nodes requested
--ntasksNumber of parallel tasks (processes)
--timeMaximum wall time — scheduler kills the job at this limit
--outputWhere stdout is written — %j expands to the job ID
8.3
$ sbatch ~/test-job.sh

Expected: Submitted batch job <JOBID>

8.4
$ squeue
StateMeaning
PDPending — waiting for resources
RRunning
CGCompleting — cleaning up
FFailed — non-zero exit code
8.5
$ cat ~/job-<JOBID>.out
8.6
$ sacct -j <JOBID> --format=JobID,JobName,State,ExitCode,Elapsed

Job accounting record. ExitCode format is signal:exit_code. 0:0 is success. 0:1 means the script exited with code 1. 0:137 means the job was killed with SIGKILL — by the OOM killer, a timeout, or a forced cancel.
