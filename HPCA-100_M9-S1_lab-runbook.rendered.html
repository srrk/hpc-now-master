—Before you startread once · 8 min

Four places a user lives, and they must agree

Yesterday's sandbox kept users in each node's own /etc/passwd. This one keeps them in a directory on head, and that changes where the truth is, not how many places it has to be true. One person is four records, and any one of them can disagree with the others.

PlaceWhat it holdsHow to ask it
The directory, on headThe account, its numbers, its groups, whether it is enabledldapsearch -x -ZZ -y /root/.dirmgr "(uid=jchen)"
The node's view, on every nodeWhat this node currently believes, which may be a cached copygetent passwd jchen · id jchen · sssctl user-show jchen
The schedulerWho may run work under which account, and what they ransacctmgr -n -P show assoc user=jchen · sacct -u jchen
The filesystemOwnership as numbers; names are looked up afterwardsls -ln /home

The node's view is the one that surprises people. A node does not ask the directory every time; it keeps a copy, for speed and so that it keeps working when the directory is briefly unreachable. A cluster that stops working whenever its directory blinks is a design problem. A cluster that keeps working on an old copy has a different problem, and you need to know which one you have.

The account lifecycle

Request, approval, creation in all four places, first login, changes, suspension, de-provisioning, and what happens to the data afterwards. Creation is the step everyone practises. De-provisioning is where the problems come from, months later. Disabling access takes a minute. Deciding what happens to the person's data, their groups, their running jobs and their accounting history is the part that gets missed.

Accounting history is the record of what an account did and what it used. Allocation reports and audits depend on it after the person has gone, so it is kept.

Your access

You are root on your own three nodes. On head you can bind to the directory as its manager with the password file /root/.dirmgr; /root/.ldaprc already names the server, the base and the manager's DN. The requirement specification is the contract for this lab, and verify-spec checks tasks 1, 3, 4 and 5 against it.

Write your diagnoses and decisions there as you go.

1Finish the directory integration10 min

c1 and c2 resolving directory users exactly as head does, through the node client, surviving a reboot.

1.1 See the difference

for n in head c1 c2; do echo "== $n"; ssh $n getent passwd jchen; done

head answers. The compute nodes do not, which is the "user not found on one node" class of problem in its plainest form. Every job jchen submits would fail on a compute node right now.

1.2 What the previous administrator left on c1

ssh c1 'authselect current; grep -E "^(passwd|group):" /etc/nsswitch.conf; systemctl is-enabled sssd; ls -l /etc/sssd/sssd.conf'
And how head, which works, is set up
authselect current; grep -E "^(passwd|group):" /etc/nsswitch.conf; systemctl is-enabled sssd
Installed is not integrated
  • The client configuration says where the directory is and how to talk to it.
  • The profile decides whether the system's name service consults the client at all.
  • The service has to be running for the client to answer.

A node can have all the software and a configuration file and still resolve nobody. Compare the two nodes line by line before you change anything, and read the configuration file you are about to switch on. It was written by someone else.

diff <(cat /etc/sssd/sssd.conf) <(ssh c1 cat /etc/sssd/sssd.conf)

1.3 Complete it on c1

ssh c1 'authselect select sssd --force && systemctl enable --now sssd'
ssh c1 'getent passwd jchen; id jchen'

1.4 Then c2, and prove all three agree

ssh c2 'authselect select sssd --force && systemctl enable --now sssd'
U=$(ldapsearch -LLL -x -ZZ -y /root/.dirmgr "(objectClass=posixAccount)" uid | awk '/^uid:/ {printf "%s ", $2}')
for n in head c1 c2; do ssh $n "for u in $U; do getent passwd \$u; done" | md5sum; done

Three identical checksums. If one differs, compare that node's output with head's and find the line. A plain getent passwd with no name lists only local accounts here, because the node client does not enumerate the directory; that is why the loop asks for each user by name.

2Three tickets15 min

A written diagnosis for each ticket in ~/course-repo/m9s1/diagnoses.md, using the headings in section 2 of the specification, and a repair for each one that is yours to repair.

The method, for every identity ticket

  • Reproduce it as the user, where the user was. su - <user> on the node they named, the command they ran. A ticket you cannot reproduce is a ticket you have not understood.
  • Same user, same command, different host. If it works on one node and not another, the difference is on the node, not in the user.
  • Ask all four places, and find where they disagree. The disagreement is the diagnosis. Which place is right is a separate question, and the answer is not always the directory.
  • Ownership is a number. ls -l shows names that were looked up a moment ago; ls -ln shows what is actually stored.
  • Ask when and why the disagreement started, because the repair is not finished until it cannot happen again.

2.1 Read all three before touching anything

cat /opt/lab/tickets/ticket-*.txt

2.2 Start the diagnoses file

vi ~/course-repo/m9s1/diagnoses.md   # one section per ticket

Write as you go: what you ran, on which node, and what came back. The diagnosis is the record of the evidence, not a sentence at the end.

Two rules for every repairNever make a symptom go away by deleting an account or a user's data. And never fix a node by making it disagree with the source, for example by adding a user or a group locally to match what the user expects. Both stop the ticket and leave a worse problem behind.
Stop · task 2read before going on

This Stop does not give the answers. Here is how to know you have them.

Test each diagnosis against three questions
  • Did you reproduce it as the user, on the node they named, before you changed anything, and does the same action now behave correctly?
  • Can you name the two places that disagreed, and show the evidence from each?
  • Can you say why they came to disagree, and what you changed so they will not again?

If you can answer all three for a ticket, the diagnosis is complete. If you repaired something without being able to answer the third, the ticket will come back.

Own or escalate

For each ticket, decide whether anything in it belongs to someone else, a data owner or a security contact, and write who. Some of what you found today is a decision, not a repair.

3A new starter, in all four places8 min

lbianchi created as section 3 of the specification requires, agreeing in the directory, on every node, on disk and in the scheduler.

3.1 A UID nobody has, anywhere

Every number the directory holds
ldapsearch -LLL -x -ZZ -y /root/.dirmgr "(uidNumber=*)" uidNumber | awk '/^uidNumber:/ {print $2}' | sort -n | uniq -c
And every number a node holds locally
for n in head c1 c2; do ssh $n "awk -F: '\$3>=1000 && \$3<60000 {print \$3}' /etc/passwd"; done | sort -n | uniq

The uniq -c count beside each directory number should be 1. Choose a number that appears in neither list, and use the same number for the personal group.

3.2 Create the directory entries

cp /opt/lab/spec/templates/user.ldif ~/course-repo/m9s1/lbianchi.ldif && vi ~/course-repo/m9s1/lbianchi.ldif
ldapadd -x -ZZ -y /root/.dirmgr -f ~/course-repo/m9s1/lbianchi.ldif
Add her to the project group
printf 'dn: cn=p_shared,ou=Groups,dc=hpca100,dc=lab\nchangetype: modify\nadd: memberUid\nmemberUid: lbianchi\n' | ldapmodify -x -ZZ -y /root/.dirmgr

3.3 Home, key, scheduler

mkdir /home/lbianchi && cp -r /etc/skel/. /home/lbianchi/ && chown -R lbianchi:lbianchi /home/lbianchi && chmod 700 /home/lbianchi
install -d -m 700 -o lbianchi -g lbianchi /home/lbianchi/.ssh
install -m 600 -o lbianchi -g lbianchi /opt/lab/spec/keys/lbianchi.pub /home/lbianchi/.ssh/authorized_keys

3.4 Prove the four agree

for n in head c1 c2; do ssh $n id lbianchi; done; ls -lnd /home/lbianchi; sacctmgr -n -P show assoc user=lbianchi format=account,user

4A leaver, taken away properly18 min

mrossi de-provisioned on all five aspects, with every decision written down before it is carried out.

Disabling access is the easy fifth

The five aspects are access, data, group membership, running work and accounting history. Each is a decision with a reason and an owner, not a command. The commonest failure at real sites is stopping after the first. The second commonest is deleting the accounting history, which removes the record that allocation reports and audits depend on.

4.1 Everything mrossi has, in every place

ldapsearch -LLL -x -ZZ -y /root/.dirmgr "(|(uid=mrossi)(memberUid=mrossi))" dn
ls -la /home/mrossi /home/mrossi/results | head -20
squeue -u mrossi; sacct -u mrossi -S 2026-01-01 -X -o JobID,JobName,Account,State,Start,End; sacctmgr -n -P show assoc user=mrossi format=account,user

4.2 Decide, and write it down, before acting

vi ~/course-repo/m9s1/deprovision-mrossi.md   # five headings, section 4 of the specification
Questions each heading has to answer
  • Access. How is the account disabled at the source, and how will you prove every node now refuses it, not only head?
  • Data. Who needs results/, who may decide that, and what happens to the rest of the home directory? If the decision is not yours, what do you need and from whom?
  • Group membership. Which groups, and does removing them affect anyone else's access?
  • Running work. Cancel it, or let it finish? What does each cost the group, and who decides?
  • Accounting history. What is kept, and who will ask for it later?

4.3 Act on your decisions

Disable the account at the source
printf 'dn: uid=mrossi,ou=People,dc=hpca100,dc=lab\nchangetype: modify\nreplace: nsAccountLock\nnsAccountLock: TRUE\n' | ldapmodify -x -ZZ -y /root/.dirmgr

The group removals, the data and the running job follow your decisions file. Use the commands from task 3 and from the four-places table; this runbook does not choose for you.

4.4 Prove it on every node

for n in head c1 c2; do echo "== $n"; ssh $n "su - mrossi -c true" && echo "STILL ALLOWED"; ssh $n id mrossi; done

Every node refuses the session, and no node lists a project group. If any node still allows it, ask that node what it believes about mrossi, and compare that with the directory.

sacct -u mrossi -S 2026-01-01 -X -n | wc -l; verify-spec 4
Stop · task 4read before going on
Check what you have
  • Five headings, each with a decision, a reason, an owner, an action and a verification.

  • Past jobs still reported by sacct.
A de-provisioning that disables login and stops there is the failure this task exists to prevent. The four headings after the first are where the problems come from months later: a group still holding a former member, data nobody can read, a job billed to an account nobody watches, an audit question nobody can answer.
5The access review6 min

A script that generates the list of accounts idle for 90 days or more, from the directory, and its output for today.

A review is a recurring obligation, so it is a script

An access review compiled by hand is done once and never again, because nobody has the afternoon twice. Generated, it runs every quarter for the cost of reading its output. That is section 5's first requirement.

5.1 Where last login lives

A=$(cat /opt/lab/spec/last-login-attribute); ldapsearch -LLL -x -ZZ -y /root/.dirmgr "(uid=jchen)" uid "$A"
You should see a timestamp in this form
dn: uid=jchen,ou=People,dc=hpca100,dc=lab
uid: jchen
lastLoginTime: 20261113040122Z

Year, month, day, hours, minutes, seconds, then Z for UTC. Your script converts it, compares it with today, and keeps the accounts at 90 days or more.

5.2 Write it, run it

vi ~/course-repo/m9s1/access-review.sh && chmod +x ~/course-repo/m9s1/access-review.sh && ~/course-repo/m9s1/access-review.sh && cat ~/course-repo/m9s1/access-review-$(date +%F).txt

—Glossary
access review
A recurring check of who still holds access and whether they should. Generated from data, owned by the people who can say "still needed".
bind DN
The identity a client presents to the directory. Here, the directory manager.
de-provisioning
Removing a person from the cluster on all five aspects: access, data, group membership, running work and accounting history.
directory
The service that holds accounts and groups centrally. Here, on head, queried with ldapsearch.
node client
The service on each node that answers identity questions from the directory and keeps a local copy of the answers. Here, sssd.
profile
The setting that decides which sources the system's name service consults. Set with authselect.
StartTLS
Upgrading a directory connection to an encrypted one before anything is exchanged. -ZZ makes ldapsearch refuse to continue without it.
uidNumber, gidNumber
The numbers the filesystem actually stores. Names are looked up from them each time something is listed.
