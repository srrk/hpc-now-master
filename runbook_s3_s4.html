before you start

This runbook covers Sessions 3 and 4 on a single AWS EC2 instance. Session 3 runs entirely from the shell and requires no job scheduler — it uses only standard Linux tools already present on the instance. Session 4 requires the sysstat package for iostat; verify the pre-flight checklist before beginning any Session 4 exercise.

The t3.medium's EBS-backed storage behaves consistently enough to demonstrate all diagnostic patterns clearly. Throughput numbers will differ from the slide examples; the Cached delta and the oflag=direct comparison will be clearly visible, which is what the exercises teach.

Session 3 · /proc, Page Cache, and Direct I/O · ~40 minutes

Reading Kernel State, Proving the Cache, and Measuring Real Storage

Eight exercises progressing from /proc filesystem fundamentals through per-process diagnosis, to the page cache proof and the direct I/O benchmark discipline that all subsequent HPC storage work assumes.

Every number that comes out of a storage benchmark needs to be verified against /proc/meminfo before it can be trusted. The exercises in this session build that verification habit from first principles: what /proc is, what it exposes, how to read a process's actual memory footprint, and how to tell whether a dd result is measuring RAM or storage.

Ex 1

Verify that /proc is a virtual filesystem — no disk, no daemon

Run three commands that together prove /proc is generated entirely in kernel memory: check the mount type, observe a zero-byte file, then read data from that zero-byte file. These three facts together define what a virtual filesystem is.

Step 1 — confirm filesystem type
mount | grep /proc
Expected output — filesystem type proc
proc on /proc type proc (rw,nosuid,nodev,noexec,relatime)

"type proc" is the key field.
This is not ext4, xfs, or any on-disk filesystem.
No disk blocks are read when you access /proc.
Step 2 — observe the zero-byte paradox
ls -l /proc/meminfo
wc -c /proc/meminfo
Expected output — size 0, yet content exists
-r--r--r-- 1 root root 0 Jun  5 10:22 /proc/meminfo

1365 /proc/meminfo

ls reports 0 bytes. wc -c reports real content.
The file size metadata is meaningless — the kernel generates
content at read time, not at write time. There is nothing to stat.
Step 3 — read from the zero-byte file
cat /proc/meminfo | head -5
Expected output — live kernel data
MemTotal:        3886588 kB
MemFree:          312744 kB
MemAvailable:    3102456 kB
Buffers:           18932 kB
Cached:          2891204 kB

Content appears instantly. No stale cache. No daemon update.
The kernel computed these numbers at the moment read() was called.

Run cat /proc/meminfo twice in rapid succession. The numbers will differ slightly — because they are always current. A file on disk would return identical bytes both times.

Ex 2

Read /proc/meminfo — identify the fields that matter and the one to ignore

Not all fields in /proc/meminfo are equally useful. This exercise reads the six most important fields and establishes the rule: judge memory pressure from MemAvailable, not from MemFree. Low MemFree on a healthy, busy system is expected.

grep -E '^(MemTotal|MemFree|MemAvailable|Buffers|Cached:|Dirty|Writeback):' \
    /proc/meminfo
Expected output — t3.medium (4 GB RAM)
MemTotal:        3886588 kB    ← physical RAM Linux sees. Fixed.
MemFree:          312744 kB    ← RAM with NO assignment. LOW = NORMAL.
MemAvailable:    3102456 kB    ← what new allocations can actually use.
Buffers:           18932 kB    ← filesystem metadata cache. Usually small.
Cached:          2891204 kB    ← file data in page cache. Large = GOOD.
Dirty:             14208 kB    ← modified pages not yet written to storage.
Writeback:             0 kB    ← dirty pages being flushed right now.
Watch these fields live during the page cache exercises
watch -n1 "grep -E '^(MemFree|MemAvailable|Cached:|Dirty|Writeback):' \
    /proc/meminfo"

Run this in a second terminal and leave it open throughout Exercises 6, 7, and 8. You will observe Cached growing during Exercise 6, Dirty accumulating during the write, Writeback appearing during flush, and Cached collapsing during Exercise 8.

meminfo field interpretation — what each field is actually telling you
MemFreeCompletely unassigned RAM. Low is normal and healthy on a busy system. Do not use to judge pressure.
MemAvailableEstimated RAM available for new allocations, including reclaimable cache. Use this to judge pressure.
CachedFile data in page cache. Large values mean Linux is doing its job — filling unused RAM with useful cache.
DirtyPages modified but not yet written to storage. Growing Dirty = writes accumulating in RAM.
WritebackDirty pages currently being flushed to storage. Writeback > 0 means the kernel is writing right now.

MemFree is the most commonly misread field in /proc/meminfo. A node showing 300 MB MemFree and 3 GB MemAvailable is in excellent health. A node showing 3 GB MemFree may be underutilised. Always use MemAvailable for capacity decisions.

Ex 3

Read /proc/PID/status — distinguish actual RAM usage from virtual address space

Launch a background process, then read its status file. Compare the four memory fields: two describe virtual address space reservation (large but meaningless for pressure), two describe actual physical RAM consumption (small but meaningful).

Launch a test process and capture its PID
sleep 300 &
TEST_PID=$!
echo "Test PID: $TEST_PID"
Read the memory fields from status
grep -E '^(State|Threads|VmPeak|VmSize|VmHWM|VmRSS):' \
    /proc/${TEST_PID}/status
Expected output — sleep process
State:     S (sleeping)
Threads:   1
VmPeak:    2232 kB     ← largest virtual space ever reserved. NOT actual RAM.
VmSize:    2232 kB     ← current virtual address space. NOT actual RAM.
VmHWM:      636 kB     ← peak resident memory. Actual physical RAM high-water mark.
VmRSS:      636 kB     ← current resident memory. Actual physical RAM right now.
Clean up
kill $TEST_PID 2>/dev/null; wait $TEST_PID 2>/dev/null

The rule for memory diagnosis. Use VmRSS and VmHWM — resident set size and its high-water mark. These report actual physical RAM. Use VmSize and VmPeak only for understanding virtual address space layout, never for judging memory pressure. A process with VmSize of 40 GB and VmRSS of 800 MB is using 800 MB of RAM.

The State field is the first thing to read when a process appears hung. S is sleeping (interruptible), D is uninterruptible sleep (disk wait — cannot be killed), R is running. Exercise 5 covers the D-state investigation workflow.

Ex 4

Read fd/, environ, cmdline, and maps from /proc/PID

These four subdirectories answer the diagnostic questions that come up most frequently during job debugging: what files is the process reading, what environment variables did it inherit, what exact command launched it, and what libraries is it using.

Launch a process that opens a file, capture PID
# Create a test file and open it with tail -f to hold the fd open
echo "lab test data" > /tmp/lab_testfile.txt
tail -f /tmp/lab_testfile.txt &
TAIL_PID=$!
echo "PID: $TAIL_PID"
sleep 1
Read open file descriptors from fd/
ls -la /proc/${TAIL_PID}/fd
Expected output — open file descriptors
lrwxrwxrwx 1 yogi yogi 64 Jun  5 10:30 0 -> /dev/pts/0
lrwxrwxrwx 1 yogi yogi 64 Jun  5 10:30 1 -> /dev/pts/0
lrwxrwxrwx 1 yogi yogi 64 Jun  5 10:30 2 -> /dev/pts/0
lrwxrwxrwx 1 yogi yogi 64 Jun  5 10:30 3 -> /tmp/lab_testfile.txt

fd 0 = stdin, fd 1 = stdout, fd 2 = stderr (all terminal here).
fd 3 = the file we opened. The path is the actual filesystem path.
In HPC job debugging: fd/ reveals which filesystem a job is reading,
whether it is using /scratch or /home or /tmp, and whether it has
an unexpected file handle open (e.g. a stale NFS mount).
Read environment variables
tr '\0' '\n' < /proc/${TAIL_PID}/environ | grep -E 'HOME|PATH|USER|TERM'
Expected output — inherited environment
HOME=/home/yogi
PATH=/usr/local/bin:/usr/bin:/bin:/usr/local/sbin:/usr/sbin
TERM=xterm-256color
USER=yogi

environ is NUL-separated — tr '\0' '\n' converts it to readable lines.
In HPC: use this to verify SLURM_JOB_ID, CUDA_VISIBLE_DEVICES,
OMP_NUM_THREADS, and library paths are what the scheduler set them to.
Read the exact invocation from cmdline
tr '\0' ' ' < /proc/${TAIL_PID}/cmdline; echo
Expected output — full argument list
tail -f /tmp/lab_testfile.txt

cmdline is also NUL-separated between arguments.
tr '\0' ' ' and a trailing echo produce a clean readable line.
In HPC: use this to confirm the binary and flags a running job was
launched with — useful when the submission script has been modified
after the job started.
Inspect memory maps
cat /proc/${TAIL_PID}/maps | head -10
Expected output — virtual memory layout
55a3c2e00000-55a3c2e04000 r--p 00000000 103:01 1234567  /usr/bin/tail
55a3c2e04000-55a3c2e0a000 r-xp 00004000 103:01 1234567  /usr/bin/tail
7f8b2a000000-7f8b2a028000 r--p 00000000 103:01 9876543  /usr/lib64/libc.so.6
...

maps shows: address range, permissions, offset, device, inode, path.
In HPC: confirm a job is using the expected MPI library, not an older
system version pulled from a stale LD_LIBRARY_PATH entry.
Clean up
kill $TAIL_PID 2>/dev/null; wait $TAIL_PID 2>/dev/null
rm -f /tmp/lab_testfile.txt

These four files — fd/, environ, cmdline, maps — are readable by the process owner without sudo. For other users' processes, sudo is required. In a Slurm context, these are accessible while the job is running, before the process exits and the /proc/PID directory disappears.

Ex 5

Diagnose D-state processes using wchan and stack

A process in D state (uninterruptible sleep) cannot be killed. It is blocked inside the kernel waiting for something — usually I/O. The kernel stack tells you exactly where. This exercise simulates the workflow, then demonstrates how to read the evidence on a real blocked process if one appears during the lab.

Check for D-state processes on the instance
ps aux | awk '$8 ~ /^D/ {print $0}'
Expected output — healthy instance (no D-state)
(no output)

No output means no processes are in D-state right now.
On a healthy instance with local EBS, D-state processes are rare.
On a cluster node with NFS or Lustre issues, this command will return
lines — each one a process blocked waiting for filesystem response.
Full D-state investigation workflow (apply to any PID showing D state)
# Step 1 — confirm the state from status
cat /proc/<PID>/status | grep '^State'

# Step 2 — quick summary: what kernel function is it waiting in?
cat /proc/<PID>/wchan

# Step 3 — full kernel stack (requires root)
sudo cat /proc/<PID>/stack
What the stack output looks like and how to read it
State: D (disk sleep)

nfs_wait_bit_killable                ← wchan: currently waiting here

[<0>] rpc_wait_bit_killable+0x...   ← stack entry 0 (deepest wait)
[<0>] __rpc_wait_for_completion+...
[<0>] rpc_run_task+0x...
[<0>] nfs_read_rpc_prepare+0x...
[<0>] nfs_initiate_read+0x...
[<0>] nfs_readpage+0x...            ← NFS page fault triggered this
[<0>] filemap_fault+0x...

Read the stack top-down: the top frames are deepest in the kernel.
This stack says: process tried to read a page → NFS triggered →
RPC call sent to server → waiting for response.
The subsystem is [nfs]. Resolution: check NFS server health, not the node.

Other subsystem signatures:
[jbd2]    → journal commit on local ext4 — usually transient
[lustre]  → Lustre OST or MGS connectivity issue
[ib_core] → InfiniBand fabric issue
[xfs]     → local XFS journal or I/O issue

The kernel stack identifies the subsystem responsible for the D-state. That subsystem determines the investigation path — a Lustre stack means checking the OSS, an NFS stack means checking the NFS server, a local journal stack may resolve itself. This is the starting point for Task T58 and T61 in the associate curriculum.

Why D-state matters in HPC. Slurm will not release a node back to the pool while any process from the job's cgroup is still alive. A D-state process blocked on a hung NFS mount will hold the node in CG state indefinitely — the scheduler cannot drain it, other jobs cannot use it, and killing the process has no effect. The /proc/PID/stack workflow is the only way to determine whether the wait will eventually resolve (transient I/O) or requires operator intervention (dead NFS server, dropped Lustre connection).

Ex 6

Prove the page cache — buffered write fills RAM, not storage

Write a file with dd using default (buffered) I/O. Observe the Cached field in /proc/meminfo before and after. Then immediately re-read the file and observe that the throughput is impossible for any storage device — it is memory speed. This is the central demonstration of the session.

Run the watch command first. Open a second terminal, SSH in as the same user, and run watch -n1 "grep -E '^(MemFree|Cached:|Dirty|Writeback):' /proc/meminfo" before running any command below. The live view makes the cache fill visible in real time.

Step 1 — record the Cached baseline before writing
grep '^Cached:' /proc/meminfo
Expected — baseline before write
Cached:   1243648 kB     ← record this number (will be ~1.2 GB or similar)
Step 2 — write 2 GB with buffered I/O (default dd, no flags)
dd if=/dev/zero of=/labdata/${USER}/io_test bs=1M count=2048 2>&1
Expected output — suspiciously fast write
2048+0 records in
2048+0 records out
2147483648 bytes (2.1 GB, 2.0 GiB) copied, 0.83 s, 2.6 GB/s

This number (~2+ GB/s) is RAM speed — not EBS storage speed.
The data went into the page cache, not to disk.
dd returned before the storage write completed.
Step 3 — check how much Cached grew
grep '^Cached:' /proc/meminfo
Expected — Cached grew by ~2 GB
Cached:   3291136 kB     ← increased by ~2 GB since Step 1

The 2 GB we "wrote" is now sitting in RAM as page cache.
Storage barely started the actual write yet.
Step 4 — immediately read the file back (cache hot)
dd if=/labdata/${USER}/io_test of=/dev/null bs=1M 2>&1
Expected output — memory speed read
2048+0 records in
2048+0 records out
2147483648 bytes (2.1 GB, 2.0 GiB) copied, 0.41 s, 5.2 GB/s

5 GB/s from EBS? Impossible — EBS gp3 max throughput is 125–1000 MB/s.
This read came entirely from the page cache in RAM. Storage was not touched.
Any benchmark result that exceeds your storage hardware rating is measuring
page cache, not storage. The Cached field in /proc/meminfo is the proof.

The Cached field is the evidence that proves a benchmark number is measuring RAM. If Cached grew by roughly the size of the write, the benchmark is not measuring storage. Keep the test file — Exercise 7 uses it for the Direct I/O comparison.

Ex 7

Measure real storage with Direct I/O — oflag=direct and iflag=direct

Direct I/O bypasses the page cache entirely. The process waits for actual storage completion before dd returns. The Cached field does not move. The throughput number is real storage speed. This is the correct way to benchmark storage in any HPC environment.

Step 1 — write with Direct I/O (bypasses cache)
grep '^Cached:' /proc/meminfo   # record baseline
dd if=/dev/zero \
   of=/labdata/${USER}/io_test_direct \
   bs=1M count=512 \
   oflag=direct 2>&1
grep '^Cached:' /proc/meminfo   # compare to baseline
Expected output — real storage speed, Cached unchanged
Cached:   3291136 kB     ← baseline

512+0 records in
512+0 records out
536870912 bytes (537 MB, 512 MiB) copied, 4.21 s, 127 MB/s

Cached:   3291136 kB     ← UNCHANGED — cache was not used

127 MB/s is the actual EBS gp3 write throughput for this instance.
Cached did not grow. Storage did the work. The number is trustworthy.
Step 2 — read with Direct I/O (must read same file written directly)
dd if=/labdata/${USER}/io_test_direct \
   of=/dev/null \
   bs=1M \
   iflag=direct 2>&1
Expected output — real storage read speed
512+0 records in
512+0 records out
536870912 bytes (537 MB, 512 MiB) copied, 4.06 s, 132 MB/s

~132 MB/s — consistent with EBS gp3 baseline throughput.
Compare to Exercise 6's 5.2 GB/s: that was cache. This is storage.

The alignment requirement. Direct I/O requires that transfer sizes be aligned to the storage block size (typically 512 bytes to 4096 bytes). Using bs=1M satisfies this automatically — 1 MiB is divisible by any block size in common use. If you use a non-aligned block size (e.g. bs=513) with oflag=direct, dd will return an error: Invalid argument. This is not a kernel bug; it is the O_DIRECT contract.

Step 3 — side-by-side comparison summary
echo "=== Buffered write result (Exercise 6) ==="
echo "Write: ~2.6 GB/s  (RAM speed — cache filled)"
echo "Read:  ~5.2 GB/s  (RAM speed — cache served it)"
echo ""
echo "=== Direct I/O result (Exercise 7) ==="
echo "Write: ~127 MB/s  (storage speed — cache bypassed)"
echo "Read:  ~132 MB/s  (storage speed — cache bypassed)"
echo ""
echo "=== Which number is real? ==="
echo "The Direct I/O number. Every other benchmark needs this verification."
Clean up test files
rm -f /labdata/${USER}/io_test /labdata/${USER}/io_test_direct

The three valid ways to get a trustworthy storage benchmark are: (1) oflag=direct / iflag=direct; (2) drop caches between write and read; (3) use a file larger than physical RAM so it cannot fit in cache. Exercise 8 covers option 2.

Ex 8

Drop caches safely — the correct procedure and when to use it

Dropping caches forces subsequent reads to go to storage rather than RAM. This is a measurement tool — useful before running a read benchmark. It is not a fix for low memory, and it is not a routine operation on production nodes.

Step 1 — flush dirty pages to storage before dropping
sync
grep -E '^(Dirty|Writeback):' /proc/meminfo
Expected — Dirty near zero after sync
Dirty:          0 kB
Writeback:      0 kB

sync flushes all dirty pages to storage before we drop the cache.
Dropping cache without sync first could discard unflushed writes —
though in practice the kernel protects against this, sync is required
practice because it makes the sequence explicit and auditable.
Step 2 — record Cached baseline, then drop
echo "=== Before drop ==="
grep -E '^(MemFree|Cached:):' /proc/meminfo

echo 3 | sudo tee /proc/sys/vm/drop_caches

echo "=== After drop ==="
grep -E '^(MemFree|Cached:):' /proc/meminfo
Expected output — Cached collapses, MemFree rises
=== Before drop ===
MemFree:    312744 kB
Cached:    3291136 kB

3

=== After drop ===
MemFree:   3287056 kB    ← rose by ~3 GB
Cached:      24576 kB    ← collapsed from 3.2 GB to ~24 MB

The echo 3 value drops both page cache (1) and reclaimable slab (2).
echo 1 drops page cache only.
echo 2 drops reclaimable slab only.
echo 3 drops both — use this for benchmark preparation.
Step 3 — now run a read benchmark with cold cache
# Write a fresh test file (buffered write is fine here — we only care about the read)
dd if=/dev/zero of=/labdata/${USER}/cold_read_test bs=1M count=512 2>&1
sync

echo "=== Dropping cache before read benchmark ==="
echo 3 | sudo tee /proc/sys/vm/drop_caches

echo "=== Cold cache read ==="
dd if=/labdata/${USER}/cold_read_test of=/dev/null bs=1M 2>&1

rm -f /labdata/${USER}/cold_read_test
Expected output — cold cache read hits real storage
=== Cold cache read ===
512+0 records in
512+0 records out
536870912 bytes (537 MB, 512 MiB) copied, 4.10 s, 131 MB/s

~131 MB/s — consistent with the Direct I/O read result from Exercise 7.
This confirms both methods (direct I/O and drop-cache) measure the same thing.
drop_caches values — what each number actually does
echo 1Drop page cache only (file data). Slab cache (dentries, inodes) retained.
echo 2Drop reclaimable slab cache (dentries, inodes). Page cache retained.
echo 3Drop both. Use for benchmark preparation — clean slate for read tests.

When NOT to drop caches. Never drop caches on a production HPC node as a memory management technique. Dropping cache does not free memory for new allocations — MemAvailable already accounts for reclaimable cache. Dropping cache on a busy login node or active compute node evicts useful data that will immediately need to be re-read from storage, causing a transient I/O spike. Use drop_caches only before intentional benchmark runs, never as a routine maintenance action.

Session 3 Checkpoint Run this full sequence and verify all three results
echo "=== /proc virtual filesystem ==="
mount | grep "type proc" | awk '{print "OK: /proc is type", $5}'

echo ""

echo ""
echo "Session 3 checkpoint complete"
Expected: /proc confirmed as type proc · MemAvailable shows a large value (not MemFree) · Cached grew significantly during buffered write, grew by ~0 MiB during direct write. The cache delta contrast is the proof the session builds toward.

Session 4 · iostat and Storage Saturation Diagnosis · ~35 minutes

Reading iostat Correctly, Understanding %util, and Diagnosing Saturation from r_await

Seven exercises building from iostat invocation fundamentals through the first-block rule, workload shape identification from merge rate, and the central diagnostic skill: using r_await and aqu-sz to distinguish a busy device from a saturated one.

The central lesson of this session is that %util = 100% is the beginning of an investigation, not the end. A device can be at 100% utilisation and still have headroom. A device can be genuinely saturated while %util stays constant at 100%. Only r_await and aqu-sz reveal which state the device is in. Every exercise builds toward that diagnosis pattern.

Set your device name before starting. Run lsblk | grep -v loop and note the root block device name. Set it as a shell variable at the start of your session and all Exercise commands will work unchanged.

export DEVICE=$(lsblk -d -o NAME,TYPE | awk '$2=="disk"{print $1; exit}')
Then verify: echo $DEVICE — should print nvme0n1 or xvda.

Ex 1

Run iostat -xh and read the field layout

iostat -xh is the standard invocation for storage diagnosis. The -x flag adds extended statistics (r_await, aqu-sz, %util). The -h flag makes throughput human-readable. Run it and identify each column group before moving to interpretation.

# Set device variable first (from pre-flight)
export DEVICE=$(lsblk -d -o NAME,TYPE | awk '$2=="disk"{print $1; exit}')
echo "Using device: $DEVICE"

iostat -xh 2 3 $DEVICE
Expected output — three intervals (discard the first block)
Linux 6.1.x  (mylab.hpc.now)    06/05/2026  _x86_64_   (2 CPU)

avg-cpu:  %user   %nice %system %iowait  %steal   %idle
           0.25    0.00    0.20    0.05    0.00   99.50

Device     r/s     w/s     rkB/s    wkB/s   rrqm/s  wrqm/s %rrqm %wrqm r_await w_await aqu-sz rareq-sz wareq-sz  svctm  %util
nvme0n1   0.12    0.45     4.8k    82.4k     0.00    0.02   0.0%   4.6%    0.32    1.24   0.00     4.0k     4.0k   0.00   0.0%

← BLOCK 1 — since-boot average. Discard this block.

Device     r/s     w/s     rkB/s    wkB/s ...  r_await  aqu-sz  %util
nvme0n1   0.00    1.50     0.0k   192.0k  ...     0.00    0.02    0.2%

← BLOCK 2 — first useful interval. Start reading here.
iostat field groups — what each column is measuring
r/s · w/sRead / write IOPS. High = many small operations (random). Low = few large ops (sequential).
rkB/s · wkB/sRead / write throughput. High throughput + low IOPS = large sequential transfers.
rrqm/s · %rrqmRead requests merged per second / merge rate. High % = sequential. Low % = random.
r_awaitRead latency in ms = queue time + service time. PRIMARY saturation signal.
aqu-szAverage queue depth. Rising queue alongside rising r_await = saturation developing.
%utilFraction of time queue was non-empty. NOT a capacity metric. Misleading on NVMe.

The data source for all iostat output is /proc/diskstats. You can read that file directly with cat /proc/diskstats — iostat simply computes rates between samples from those raw counters. Understanding the source makes the first-block rule intuitive: block 1 divides the raw counter by total uptime, not by a 2-second interval.

Ex 2

Demonstrate the first-block rule — since-boot average vs interval rate

Generate a burst of I/O, then run iostat and compare block 1 (since-boot) to blocks 2 and 3 (interval rates). The contrast proves why block 1 must always be discarded.

Step 1 — generate a brief I/O burst, then immediately capture iostat
# Write 256 MB with direct I/O to generate real device activity
dd if=/dev/zero of=/labdata/${USER}/burst_test bs=1M count=256 \
   oflag=direct 2>/dev/null &
DD_PID=$!

iostat -xh 2 4 $DEVICE 2>/dev/null | \
    grep -E "(Device|$DEVICE|^$)" | head -20

wait $DD_PID
rm -f /labdata/${USER}/burst_test
Expected output — block 1 vs burst interval
Device    r/s    w/s   rkB/s    wkB/s  r_await  aqu-sz  %util
nvme0n1  0.11   0.42    4.6k    78.2k     0.28    0.00    0.0%
← BLOCK 1: since-boot averages. Low wkB/s because the burst is diluted
  across the entire uptime of the instance.

Device    r/s    w/s   rkB/s    wkB/s  r_await  aqu-sz  %util
nvme0n1  0.00  62.50    0.0k   125.0M     1.24    0.08   64.0%
← BLOCK 2: interval during the burst. wkB/s now shows real throughput.

Device    r/s    w/s   rkB/s    wkB/s  r_await  aqu-sz  %util
nvme0n1  0.00   0.00    0.0k     0.0k     0.00    0.00    0.0%
← BLOCK 3: burst finished. Back to idle.

If you had only read block 1, you would have concluded "nothing is happening".
The burst that caused an alert is invisible in block 1.
Always discard block 1. Start reading at block 2.

The recommended workflow for live troubleshooting: start iostat -xh 2 before the workload begins. Discard the first output block. Watch subsequent intervals. For capture: iostat -xh 2 60 > iostat_capture.txt captures 60 two-second intervals — two minutes of ground truth.

Ex 3

Read merge rate to identify workload shape — sequential vs random

The kernel I/O scheduler merges adjacent requests before sending them to the device. High merge rate indicates sequential access (adjacent requests can be merged). Low merge rate indicates random access (no adjacency, nothing to merge). The %rrqm and %wrqm columns reveal the pattern directly.

Sequential write — watch for high wrqm/s and %wrqm
# Sequential write: large block size, single stream
dd if=/dev/zero of=/labdata/${USER}/seq_test bs=1M count=512 \
   oflag=direct 2>/dev/null &
SEQ_PID=$!
sleep 1

iostat -xh 2 4 $DEVICE | grep -v "^$" | grep -E "(Device|$DEVICE)"

wait $SEQ_PID
rm -f /labdata/${USER}/seq_test
Expected — sequential: high throughput, significant merge rate
Device  r/s   w/s    rkB/s   wkB/s  rrqm/s  wrqm/s  %rrqm  %wrqm  r_await  aqu-sz  %util
nvme0n1 0.00  32.50   0.0k  128.0M    0.00   48.00   0.0%  59.6%    0.00    0.08   54.0%

High wkB/s (128 MB/s) + high %wrqm (~60%) = sequential write pattern.
Requests are adjacent — the scheduler is merging them before dispatch.
Low w/s (32) with high wkB/s means large requests after merging.
Install fio if needed, then random read — low merge rate
# Install fio for random I/O workload generation
sudo dnf install -y fio 2>/dev/null || sudo apt install -y fio 2>/dev/null

fio --name=randread_test \
    --filename=/labdata/${USER}/fio_random \
    --rw=randread \
    --bs=4k \
    --size=256M \
    --numjobs=4 \
    --runtime=20 \
    --time_based \
    --direct=1 \
    --output=/dev/null &
FIO_PID=$!
sleep 2

iostat -xh 2 4 $DEVICE | grep -v "^$" | grep -E "(Device|$DEVICE)"

wait $FIO_PID
rm -f /labdata/${USER}/fio_random*
Expected — random: high IOPS, low throughput, low merge rate
Device   r/s    w/s   rkB/s  wkB/s  rrqm/s  wrqm/s  %rrqm  %wrqm  r_await  aqu-sz  %util
nvme0n1 3420.00  0.00  13.4M  0.0k    1.00    0.00   0.0%   0.0%    1.12    3.82   98.0%

High r/s (3420) + low %rrqm (~0%) = random read pattern.
Requests target non-adjacent locations — nothing to merge.
Low rkB/s per IOPS (4 kB each) confirms small 4k random reads.

Note: on NVMe, low merge rate is also normal even for sequential I/O,
because NVMe schedulers perform less aggressive merging than SCSI schedulers.
Low %rrqm on NVMe alone is not proof of random access.

The merge rate is a signal, not a definitive classifier. Combine it with rareq-sz (average request size after merging): large request size + high merge rate = sequential. Small request size + low merge rate = random. On NVMe devices, use request size as the primary signal.

Ex 4

Read r_await and aqu-sz — understand what they measure and their baseline values

r_await is read completion latency: queue time plus service time. On a healthy, lightly loaded device, it reflects only service time because requests are not waiting. As load increases and the queue builds, queue time grows and r_await rises. The queue size (aqu-sz) rising alongside r_await is the saturation signature.

Capture baseline r_await and aqu-sz at idle
echo "=== Idle baseline (skip block 1, read block 2) ==="
iostat -xh 2 3 $DEVICE | grep -E "(r_await|aqu-sz|$DEVICE)" | tail -4
Expected — idle baseline values
Device  ... r_await  w_await  aqu-sz  %util
nvme0n1 ...    0.28     1.14    0.00   0.0%

r_await at idle: 0.28 ms — this is service time alone (no queue).
aqu-sz at idle:  0.00 — no requests in flight between samples.

Reference baselines by device type:
  EBS gp3 (NVMe):       0.1 – 0.5 ms healthy
  EBS io2 (provisioned): 0.05 – 0.3 ms healthy
  Local NVMe SSD:        0.05 – 0.3 ms healthy
  SATA/SAS SSD:          0.1 – 1.0 ms healthy
  Spinning HDD (seq):    1 – 5 ms healthy
  Spinning HDD (rand):   8 – 15 ms healthy
Generate moderate load and observe r_await and aqu-sz together
fio --name=moderate_load \
    --filename=/labdata/${USER}/fio_await \
    --rw=randread \
    --bs=4k \
    --size=256M \
    --numjobs=2 \
    --runtime=30 \
    --time_based \
    --direct=1 \
    --output=/dev/null &
FIO_PID=$!
sleep 2

echo "=== Under moderate load ==="
iostat -xh 2 5 $DEVICE | grep -E "($DEVICE)" | tail -4

wait $FIO_PID
rm -f /labdata/${USER}/fio_await*
Expected — moderate load, r_await rising but not alarming
nvme0n1  1820.00  0.00  7.1M  0.0k  ...  0.62  0.00  1.12  2.40  92.0%

r_await: 1.12 ms  — rose from 0.28 ms idle baseline. Queue time is adding ~0.8 ms.
aqu-sz:  2.40     — average of 2.4 requests in flight. Modest.
%util:   92%      — device is busy but r_await is still low. Busy, not saturated.

Saturation is when r_await climbs sharply, not when %util is high.
This device still has headroom — adding more load would increase throughput,
not just accumulate latency.

aqu-sz has no fixed "normal" value — it depends on the device's queue depth and the workload. What matters is the trend: a steadily rising aqu-sz alongside steadily rising r_await, while throughput stops growing, is the saturation signature. A stable aqu-sz alongside stable r_await, even at a high value, means the device has found equilibrium.

Ex 5

Prove the %util ceiling — why %util = 100% is not a saturation finding

%util measures the fraction of the interval during which at least one request was in flight. On a device with parallel queues (any NVMe, any EBS), this counter saturates at 100% long before the device's actual capacity is exhausted. This exercise demonstrates the ceiling: %util reaches 100%, then stops providing information, while r_await continues to reveal the actual device state.

Push load until %util reaches 100%, observe r_await while it does
fio --name=util_ceiling \
    --filename=/labdata/${USER}/fio_util \
    --rw=randread \
    --bs=4k \
    --size=256M \
    --numjobs=8 \
    --iodepth=32 \
    --runtime=30 \
    --time_based \
    --direct=1 \
    --output=/dev/null &
FIO_PID=$!
sleep 2

echo "=== %util pinned at 100% — watch r_await ==="
iostat -xh 2 8 $DEVICE | grep -E "($DEVICE)"

wait $FIO_PID
rm -f /labdata/${USER}/fio_util*
Expected output — %util ceiling demonstration
nvme0n1  3100.00  0.00  12.1M  ...  r_await  1.04  aqu-sz  3.22  %util 100.0%
nvme0n1  3250.00  0.00  12.7M  ...  r_await  1.18  aqu-sz  3.84  %util 100.0%
nvme0n1  3180.00  0.00  12.4M  ...  r_await  1.22  aqu-sz  3.91  %util 100.0%
nvme0n1  3220.00  0.00  12.6M  ...  r_await  1.19  aqu-sz  3.88  %util 100.0%

%util is pinned at 100% across all intervals.
r_await is stable at ~1.2 ms — close to the idle baseline, no queue blowup.
aqu-sz is stable at ~3.9 — the device is handling the concurrency comfortably.

This device is BUSY but NOT SATURATED.
If we added more load: r_await would start climbing sharply.
%util would remain at 100% — it is already at its ceiling and tells us nothing.

The transition from busy to saturated is invisible in %util.
Only r_await and aqu-sz reveal it.

Why %util misleads on NVMe. The %util metric was designed for spinning disks with a single actuator — at any moment, the disk is either busy (one request being served) or idle. On that model, %util ≈ capacity consumed. NVMe devices have many internal queues and flash channels that process multiple requests in parallel. "At least one request in flight" is true almost continuously under any meaningful load. The metric saturates early and tells you nothing about remaining capacity. Use r_await instead.

Ex 6

Apply the four-state diagnosis pattern to pre-baked scenarios

Given any combination of %util and r_await, the device state falls into one of four categories. This exercise reads a set of pre-staged iostat snapshots and classifies each one. The classification drives the operational response.

%utilr_awaitStateMeaningAction
Low Low Idle / Healthy Device underutilised. Storage is not the bottleneck. Look elsewhere for the bottleneck.
High Low Busy — not saturated Device working hard. Capacity still available. Headroom exists. Continue monitoring. No immediate action needed.
High High Saturated Queue building. Requests waiting. Application is slowing down. Investigate workload. Consider striping, queue depth, I/O scheduling.
Low High Anomalous Unusual. Bursty workload, very large requests, or device error. Investigate device health. Check dmesg for hardware errors.

Ex 7

Run the complete live monitoring workflow against a real workload

This exercise ties the session together: start monitoring before the workload, discard block 1, apply the reading checklist to every subsequent interval, capture to a file, and produce a diagnosis. This is the exact workflow used in production HPC storage troubleshooting.

Terminal 1 — start iostat capture before the workload
iostat -xh 2 30 $DEVICE > /labdata/${USER}/iostat_capture.txt &
IOSTAT_PID=$!
echo "iostat capture PID: $IOSTAT_PID"
echo "Capturing 30 intervals (60 seconds). Start workload in Terminal 2."
Terminal 2 — run a workload while the capture is running
# Sequential write phase (30 sec), then random read phase (30 sec)
echo "Phase 1: Sequential write..."
fio --name=seq_phase --filename=/labdata/${USER}/workload_file \
    --rw=write --bs=1M --size=512M --direct=1 \
    --runtime=25 --time_based --output=/dev/null

echo "Phase 2: Random read..."
fio --name=rand_phase --filename=/labdata/${USER}/workload_file \
    --rw=randread --bs=4k --size=512M --numjobs=4 --direct=1 \
    --runtime=25 --time_based --output=/dev/null

rm -f /labdata/${USER}/workload_file
Terminal 1 — wait for capture to complete, then analyse
wait $IOSTAT_PID
echo "Capture complete. Analysing..."

echo "=== Block count ==="
grep -c "$DEVICE" /labdata/${USER}/iostat_capture.txt

echo "=== r_await range across all intervals (skip block 1) ==="
grep "$DEVICE" /labdata/${USER}/iostat_capture.txt | tail -n +2 | \
    awk '{print $14}' | sort -n | \

Reading checklist — apply to every iostat interval
r_awaitStable and near baseline? Healthy. Rising sharply? Saturation developing. Primary signal.
aqu-szModest (<4) and stable? Healthy. Growing continuously alongside r_await? Saturation confirmed.
%utilUse only to detect idle (low) vs active (high). Never use to judge capacity consumed.
rareq-szLarge (>64 kB)? Sequential. Small (4–16 kB)? Random. Confirms workload shape.
%rrqm / %wrqmHigh? Sequential (merging happening). Low? Random. On NVMe, use rareq-sz as primary signal.
IOPS plateauIf r/s stops growing while r_await keeps rising: device hit its IOPS limit. Saturation.

The Lustre boundary. On a compute node, iostat sees only local block devices. Lustre and NFS storage behavior is on the server side — outside the compute node's /proc/diskstats entirely. However, the interpretation does not change: r_await and aqu-sz are still the saturation signals on the OSS side, visible via Prometheus/Grafana metrics collected from OSS nodes. The tool changes; the diagnostic reasoning does not.
