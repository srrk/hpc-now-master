how to use this runbook

This is the second lab runbook for Linux for HPC. Day 1 covered processes, signals, and resource limits (Labs 18–20). This runbook opens at Lab 21 and closes at Lab 22 — the two labs for Day 2.

The goal of these exercises is reading fluency with the memory subsystem. Every exercise produces a number or a set of fields. The interpretation matters as much as the command. When an exercise asks you to explain something, write one sentence. That sentence is the evidence of comprehension.

The key shift for this session. Stop reading used in free -h. Start reading available. The exercises build this reflex deliberately — by the end of Section 21 it should be automatic.

Lab 21 / 22 · 20 minutes · Memory

free, /proc/meminfo, OOM Scores, PSI

Follows: virtual memory, the page cache, free -h honestly, /proc/meminfo fields, swap, overcommit modes, OOM killer scoring, exit code 137, dmesg OOM anatomy, PSI pressure stall information.

Ex 1

Run free -h — read available, explain buff/cache

free -h
Expected output — read each column
              total        used        free      shared  buff/cache   available
Mem:          xxx Gi       xxx Gi      xxx Gi    xxx Mi      xxx Gi      xxx Gi
Swap:           0B          0B          0B

Read in this order:
1. available — how much can new allocations use?
2. buff/cache — the page cache — reclaimable, not permanently occupied
3. used — process allocations only, excluding page cache
4. free — genuinely unoccupied — small is correct on a loaded system

The number that matters is available.
If Swap shows 0B: swap is disabled on this node.

Write one sentence explaining why a large buff/cache value is not alarming. This is the key comprehension check for the page cache model.

Large buff/cache means the kernel has used idle RAM as a page cache — which is correct behaviour. The kernel will reclaim those pages immediately when a process needs memory. They are not occupied; they are useful.

Ex 2

Read /proc/meminfo — record the fields beyond what free shows

cat /proc/meminfo

Find and record these specific fields:

grep -E 'MemAvailable|^Cached:|Inactive\(file\)|Dirty:|Writeback:|SReclaimable:|AnonHugePages' /proc/meminfo
Expected output — interpret each field
MemAvailable:   xxx kB    ← the number free -h "available" is derived from
Cached:         xxx kB    ← page cache size — total
Inactive(file): xxx kB    ← page cache pages not recently accessed — reclaim candidates
Dirty:          xxx kB    ← modified in memory, not yet flushed to storage
Writeback:        0 kB    ← actively being flushed right now (0 = idle)
SReclaimable:   xxx kB    ← kernel slab that can be reclaimed under pressure
AnonHugePages:  xxx kB    ← anonymous memory currently backed by transparent hugepages

Large Inactive(file) means the page cache has cold pages that can be reclaimed at low cost — the kernel does not even need to write them to disk first, because the disk already has the data. This is the healthiest form of memory pressure absorption.

Ex 3

Read the overcommit policy and swap state

cat /proc/sys/vm/overcommit_memory
grep Swap /proc/meminfo
Expected output
0                        ← overcommit mode (0=heuristic, 1=always, 2=strict)

SwapTotal:        0 kB   ← swap disabled on this node
SwapFree:         0 kB

Mode 0 (heuristic): the kernel allows overcommit up to a heuristic
threshold. Most allocations are granted. The OOM killer fires when
the heuristics prove optimistic under real pressure.

With swap disabled (SwapTotal: 0), the Slurm cgroup memory controller is the primary enforcement mechanism. When a job exceeds its --mem allocation, the OOM killer fires within the job's cgroup — not at the node level.

Ex 4

Read oom_score for three processes — compare their kill priority

for name in sshd chronyd; do
    pid=$(pgrep -o $name 2>/dev/null) || continue
    score=$(cat /proc/${pid}/oom_score 2>/dev/null)
    adj=$(cat /proc/${pid}/oom_score_adj 2>/dev/null)
    echo "${name} (PID ${pid}): oom_score=${score}  oom_score_adj=${adj}"
done
echo "My shell: oom_score=$(cat /proc/$$/oom_score)  oom_score_adj=$(cat /proc/$$/oom_score_adj)"
Expected output
sshd (PID 1234): oom_score=0    oom_score_adj=-1000
chronyd (PID 876): oom_score=1  oom_score_adj=0
My shell: oom_score=3            oom_score_adj=0

oom_score: 0–1000. Higher = more likely to be killed.
oom_score_adj: -1000 to +1000.
-1000 = completely exempt from OOM killing.
sshd with adj=-1000 will never be chosen as an OOM victim.

A negative oom_score_adj is how system daemons protect themselves during job-induced memory crises. If the OOM killer has killed sshd on a compute node, the daemon protection was insufficient — the node was under extreme memory pressure beyond what the adj value could protect against.

Ex 5

Read oom_score_adj for sshd — confirm it is negative

cat /proc/$(pgrep -o sshd)/oom_score_adj
systemctl show sshd --property=OOMScoreAdjust
Expected output
-1000
OOMScoreAdjust=-1000

The systemd unit file sets OOMScoreAdjust — this is how daemons
configure their OOM kill priority. -1000 = completely exempt.
The value in /proc and the systemd property should match.
Ex 6

Search dmesg for OOM events — read the constraint type

dmesg -T | grep -i "oom\|out of memory\|killed process" | tail -10
Expected output — two possible outcomes
OUTCOME A — no events (healthy node):
(no output)
This is the expected result on a lab instance with no memory pressure.

OUTCOME B — OOM event present:
[timestamp] oom-kill:constraint=CONSTRAINT_MEMCG,...
            task=python3,pid=xxxxx,uid=xxxxx
[timestamp] Out of memory: Killed process xxxxx (python3)
            total-vm:xxxxxkB, anon-rss:xxxxxkB

CONSTRAINT_MEMCG = job's --mem limit was hit → user issue
CONSTRAINT_NONE  = node ran out of RAM → operator issue

On a healthy lab instance with no memory pressure, no OOM events should appear. In A4/T35, when a user submits a ticket about exit code 137, this is the first command you run on the compute node where the job ran. The constraint type determines whether the resolution is "ask the user to increase --mem" or "investigate node-level memory exhaustion."

Ex 7

Read /proc/pressure/memory — record PSI averages

cat /proc/pressure/memory
Expected output — idle node
some avg10=0.00 avg60=0.00 avg300=0.00 total=xxxxxxxx
full avg10=0.00 avg60=0.00 avg300=0.00 total=xxxxxxxx

some: at least one process was stalled waiting for memory
full: ALL non-idle processes were simultaneously stalled

All zeros = no memory pressure. This is correct for an idle lab instance.
Nonzero full avg60 would mean the entire system stalled on memory
for some fraction of the last minute — serious distress requiring
immediate investigation on a production node.
If /proc/pressure/memory does not exist

PSI requires kernel 4.20+ and CONFIG_PSI enabled. Run uname -r to check the kernel version and grep PSI /boot/config-$(uname -r) to check the config. RHEL 9 and Rocky 9 include PSI by default.

Checkpoint — Section 21 Type done in chat when this passes
awk '/^MemAvailable/{print}' /proc/meminfo && cat /proc/$(pgrep -o sshd)/oom_score_adj && echo "Section 21 complete"
Expected: the MemAvailable line from /proc/meminfo · sshd's oom_score_adj (should be negative) · Section 21 complete. Both values confirm memory state is readable and sshd has OOM protection configured.

Lab 22 / 22 · 15 minutes · NUMA

Topology, numastat, Memory Locality

Follows: NUMA topology and distance matrix, lscpu, numactl --hardware, numastat and numa_miss, /sys/devices/system/node/, /proc/pid/numa_maps, THP policy, memory bandwidth and STREAM connection.

Ex 1

Read NUMA node count and CPU-to-node mapping

lscpu | grep -i numa
Expected output
NUMA node(s):               2
NUMA node0 CPU(s):          0-47,96-143
NUMA node1 CPU(s):          48-95,144-191

Or on a single-socket instance:
NUMA node(s):               1
NUMA node0 CPU(s):          0-3

A single NUMA node means uniform memory access — all CPUs are
equidistant from all RAM. On dual-socket servers, two nodes means
each CPU set has a local and a remote memory pool.

On a cloud instance or a single-socket lab VM, you will likely see one NUMA node. The topology-reading skill applies regardless — you are building the habit of checking the topology before interpreting memory or performance data.

Ex 2

Read the full NUMA topology with numactl --hardware

numactl --hardware
Expected output — dual-socket example
available: 2 nodes (0-1)
node 0 cpus: 0 1 2 ... 47 96 97 ... 143
node 0 size: 257857 MB
node 0 free: 218432 MB
node 1 cpus: 48 49 50 ... 95 144 145 ... 191
node 1 size: 257985 MB
node 1 free: 196608 MB
node distances:
node   0   1
  0:  10  21
  1:  21  10

Distance 10 = local (always 10 by convention).
Distance 21 = remote access costs 2.1x relative to local.
Per-node free: if one node is exhausted, allocations spill
across the link at the remote-access cost.

Record: how many NUMA nodes, what the remote distance is, how much free memory each node has. On a single-node lab instance, the distance matrix will show only distance 10 — all local.

Ex 3

Read numastat — record numa_hit and numa_miss

numastat
Expected output
                           node0      node1
numa_hit               123456789  234567890   ← satisfied from local node
numa_miss                    432         87   ← fell back to remote node
numa_foreign                  87        432   ← remote allocated on this node
interleave_hit              4321       3210   ← interleaved policy hits
local_node             123451234  234561890   ← local process, local memory
other_node                  5555       6000   ← local process, remote memory

numa_miss is the diagnostic counter.
High and growing numa_miss = locality is being violated.
On a single-node instance, numa_miss should be zero.
Per-node numastat via /sys — same data, scriptable
for node in /sys/devices/system/node/node*/; do
    echo "=== $(basename $node) ==="
    cat ${node}/numastat
done
Ex 4

Read per-node memory from /sys/devices/system/node/

for node in /sys/devices/system/node/node*/; do
    name=$(basename $node)
    total=$(awk '/^Node.*MemTotal/{print $4, $5}' ${node}/meminfo 2>/dev/null)
    free=$(awk '/^Node.*MemFree/{print $4, $5}' ${node}/meminfo 2>/dev/null)
    echo "${name}: total=${total}  free=${free}"
done
Expected output
node0: total=257857 MB  free=218432 MB
node1: total=257985 MB  free=196608 MB

Or on a single-node instance:
node0: total=xxxx MB  free=xxxx MB

These per-node values are what numactl --hardware reads.
If one node's free approaches zero, allocations spill to the
other node at remote-access cost — even if the total node free
memory looks adequate.
Ex 5

Read /proc/<pid>/numa_maps for a running process

This shows which NUMA nodes back the mapped memory regions of a specific process — the ground truth of memory locality for that process.

SSHD_PID=$(pgrep -o sshd)
sudo cat /proc/${SSHD_PID}/numa_maps | head -10
Expected output
7f9a20000000 default anon=12 dirty=12 N0=10 N1=2 kernelpagesize_kB=4
7f9a21000000 default file=/usr/lib64/libssl.so anon=0 N0=8
7f9a22000000 default anon=4 dirty=4 N0=4

N0=10 N1=2 means: 10 pages on NUMA node 0, 2 pages on node 1.
Mostly local (N0) with minor spillage to remote (N1).
A process whose numa_maps shows mostly remote node numbers
is running with poor NUMA locality.

In A10 when investigating why a benchmark runs slower than expected, /proc/<pid>/numa_maps on the benchmark process is how you confirm whether its memory is locally allocated. High remote-node page counts confirm a NUMA locality problem.

Ex 6

Read the THP policy and AnonHugePages

cat /sys/kernel/mm/transparent_hugepage/enabled
Expected output
always [madvise] never

The value in brackets is the current policy.
madvise = pages promoted to 2 MiB huge pages only when the
          application explicitly requests it — RHEL 9 default.
always  = kernel promotes all eligible pages automatically.
never   = THP disabled — some sites set this to avoid
          background compaction latency spikes.
grep -E 'AnonHugePages|HugePages_Total|HugePages_Free|HugepageSize' /proc/meminfo
Expected output
AnonHugePages:   xxxxx kB   ← anonymous memory on THP right now
HugePages_Total:      0     ← explicit pre-allocated huge page pool
HugePages_Free:       0     ← pool is empty (or not configured)
HugepageSize:      2048 kB  ← page size for explicit pool (2 MiB)

AnonHugePages > 0: THP is actively in use.
HugePages_Total = 0: no explicit huge page pool configured.
Both can coexist — THP for regular allocations, explicit pool
for applications that specifically request MAP_HUGETLB.

If the node's THP policy differs from what the site standard specifies — for example, always when the site expects madvise — note it. Configuring THP policy is a Professional-scope operation, but recognising when it is misconfigured is an Associate-scope skill.

where this shows up — forward connections

The memory model built today surfaces in three specific places in the HPC modules with specific commands and specific outputs.

ConceptModule · TaskSpecific technique
Page cache / Cached field A5 · T37 — page cache effect grep '^Cached:' /proc/meminfo before and after dd with and without oflag=direct. Buffered write populates Cached. Direct I/O does not. The difference is the page cache absorbing the write.
OOM killer / exit code 137 A4 · T35 — confirm OOM, report MaxRSS dmesg -T | grep -i oom on the compute node · read constraint= field · sacct -j <id> --format=MaxRSS,ExitCode · compare peak to --mem request · write result to file per task spec. Day 3's cgroup model completes the cgroup path in the dmesg line.
NUMA topology / numastat A10 · T71 — STREAM interpretation numactl --hardware gives the topology map. STREAM Triad results are meaningful only against the hardware's expected bandwidth for the configured NUMA placement. numastat | grep numa_miss confirms whether locality was violated during the benchmark run.
