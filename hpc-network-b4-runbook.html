Two Networks, One Card

Two nodes, one network adapter each, and two completely different ways of using it. You will measure both, find out how much the choice is worth, and then work out how to tell which one a job actually used — which is the part nobody checks until something is mysteriously slow.

—Before you startread once · 7 min

The thing that makes this lab worth doing

You have two nodes. Each has one network adapter, one cable, one bandwidth ceiling. There is no second network and no second wire.

But there are two entirely different ways for a program to send a message across that one adapter, and the difference between them is large enough to decide whether a job finishes overnight or over a weekend.

Because the hardware is identical on both paths, every difference you measure today is purely the software stack. That is a cleaner experiment than you would get comparing two real networks, and it is the reason this lab is two instances rather than a cluster.

The two paths

The ordinary path — TCP over the kernel. Your program hands a message to the operating system. The kernel copies it, wraps it in TCP and IP headers, passes it to the driver, and the card sends it. At the far end the same happens in reverse. Every message involves the kernel twice, a context switch each way, and at least one copy of your data.

The fast path — OS bypass. The program writes directly into a queue the adapter is already watching, and the adapter sends it. The kernel is not involved at all. No system call, no context switch, no copy. On AWS this is called EFA, Elastic Fabric Adapter; on a physical cluster it is usually InfiniBand or RoCE. The idea is the same everywhere.

An EFA is not a second card. It is the ordinary adapter with the bypass capability switched on, which is why ip link will show you exactly one interface today and the fast path will not appear in it.

Why the gap is different for different work

The overhead the fast path removes — system calls, context switches, copies — is a fixed cost per message. It does not grow with message size.

  • Small messages: the overhead is a large share of the total time, so removing it shows up directly.
  • Large messages: the overhead is a rounding error. What decides the time is how fast each path can push bytes — and on AWS the two paths are not equal there. A single TCP connection between two instances is limited to roughly 10 Gbps; the fast path spreads one stream of messages across many network paths and can use the whole adapter.

So the honest claim is not "the fast path is faster". It is "the fast path is faster by different amounts, for different reasons, and which one matters depends entirely on how your application talks". An application sending millions of tiny messages — which is most tightly-coupled scientific code — pays the fixed cost on every one. An application moving large blocks of data runs into the bandwidth limit instead.

You will measure both ends of that today and work out the ratio yourself.

What a parallel job actually is

Everything you run today is a real multi-node MPI job: two processes, one on each node, exchanging messages and timing them. mpirun starts a process on each host in the hostfile and gives them a way to find each other.

Three distinct things are happening and it is worth keeping them apart. The launch goes over ordinary SSH. The startup handshake between ranks uses whatever MPI decides. The message traffic uses the transport MPI selected. Only the third is being measured, and only the third changes between your two runs.

The trap, which is task 4

If the fast path is unavailable — a missing library, a security group rule, a configuration that does not match, a node where the installer never ran — MPI does not fail. It quietly falls back to TCP and runs correctly.

No error. No warning. Correct results. Several times slower, for weeks, until somebody benchmarks it.

This is the single most valuable diagnostic pattern in the module, and it is why a cluster administrator checks which transport a job used rather than trusting that it worked. Task 4 is about learning to check.

2Latency, on both paths12 min

Round-trip time for a small message, measured on each transport, with evidence of which transport actually ran.

What is being measured

osu_latency bounces a message between the two ranks many times and reports half the average round trip, for a range of message sizes from 1 byte upward. The small sizes are the interesting ones: at 1 byte there is essentially no data to move, so what you are timing is almost entirely overhead.

What your numbers show
The fast path wins at 1 byte — on these nodes by roughly a third, a ratio near 1.4. Write your own ratio down; it is one of the two headline numbers of this lab and it is yours, not a figure from a slide.
Why

At one byte there is no data worth moving. On the ordinary path you are timing the kernel: two system calls, two context switches, the TCP and IP headers, and a copy — none of which the fast path performs. Remove them and what is left is the network's own cost: the adapter, the switches between the two instances, and the protocol the fast path uses to deliver reliably. On a cloud network that remainder is still most of the time, which is why the ratio here is modest. On an InfiniBand cluster, where the network itself takes a microsecond or two, removing the same kernel cost is worth several times.

And now look at the bottom of the table

Scroll to the largest message sizes in your paste output. The gap has not narrowed — it has grown. Same two transports, same two nodes, same run — a different answer to "how much faster is it", for a different reason, which task 3 explains.

That is why "which is faster" is never the right question. Faster at what? is the question, and task 3 makes it concrete.

The evidence line

You now have a device name from step 2.1 sitting next to a latency figure. Either on its own can mislead; together they are proof. That pairing is the method in task 4.

3Bandwidth, and a real collective14 min

Bandwidth on both paths, then a collective operation on both paths — the pattern that actually dominates scientific applications.

Why two more benchmarks rather than one

Bandwidth streams large messages as fast as it can and reports megabytes per second. It is the opposite end of the spectrum from the 1-byte latency you just measured, and it should behave differently.

A collective is an operation every rank takes part in together. osu_allreduce combines a value from every rank and gives the result back to all of them — every rank waits for every other. Real parallel applications are full of these, and they are where network behaviour shows up most brutally, because the whole job runs at the speed of the slowest participant.

With two ranks a collective is almost a round trip. At two hundred ranks it is not, and the gap you see here would widen considerably. That is worth knowing and cannot be shown on two nodes.

Stop · task 3the comparison is the lesson
Line your ratios up
The bandwidth ratio is the largest — around five times. The latency ratio is modest. That is the reverse of what most people expect, and the reason is not per-message overhead. On AWS a single TCP connection between two instances is limited to roughly 10 Gbps, so your TCP bandwidth figure flattens out near 1,200 MB/s however large the message gets. The fast path spreads one stream across many network paths and fills the adapter. The small-message collective looks like the latency result, which is the point of running it.
What this means for a user

A user whose job moves large blocks of data between nodes would notice the most — several times slower on the ordinary path. A user running a tightly-coupled simulation that exchanges small messages thousands of times a second would notice too, a fixed cost on every message. Both would describe it as "the cluster is slow", not as a transport problem, because from inside the application there is nothing to see.

So the first question when somebody reports a slow parallel job is not "how big is your data" on its own. It is how their code talks — how often and how much — and whether it is on the path it should be.

What two nodes cannot show you

Your collective had two participants. At scale, every rank waits for the slowest, and the per-message overhead you measured is paid on every exchange by every rank. The gap widens with node count — sharply. You cannot measure that here, but it is the reason sites pay for fast interconnects at all.

4Which path did it use?9 min

A verdict on a run whose transport you were not told, with the evidence that settles it.

The situation

A user tells you their job runs, produces correct results, and is slower than they expected on the new cluster. Nothing in their output says anything is wrong — because nothing is wrong, as far as the application knows.

There is a third wrapper on this system. Nobody will tell you what it does. Find out which transport it uses, and prove it two different ways — because one piece of evidence can mislead and two agreeing cannot.

4.1 Run it

Stop · task 4the point of the whole lab
How the two kinds of evidence differ
The numbers tell you how it behaved. The provider line tells you what it used. You need both. A number can be slow for a dozen reasons that have nothing to do with transport — a busy node, a thermal limit, somebody else benchmarking. A provider line names the mechanism. Agreeing, they are conclusive.
Why this matters more than the ratio you measured

Nothing failed. There was no error, no warning, no exit code, no log entry. The job produced correct results. The only symptom was a number that somebody had to go and look for.

On a real cluster this happens for mundane reasons — a node where the fabric package was never installed, a security group missing a rule, a container image without the right libraries, a user who copied an mpirun line from a blog post. All of them produce exactly what you just saw.

What you do about it

Two things, and they are the deliverables of this session rather than the numbers. Know how to check — a provider line and a comparison against a known-good figure takes two minutes. And keep the known-good figure, which is why section 2's numbers belong in a file rather than in your head. A baseline you measured on a healthy day is the most useful diagnostic artefact you will ever produce, and nobody has one until they have needed it twice.

—Glossary
bandwidth
How many bytes per second a link can carry. Dominates large-message transfers.
collective
An MPI operation every rank takes part in together — a broadcast, a reduction, an all-reduce. Runs at the speed of the slowest participant.
context switch
The processor changing between your program and the kernel. Cheap individually, expensive millions of times.
EFA
Elastic Fabric Adapter. The OS-bypass capability on this cluster's network adapter. Not a separate card.
fabric
The network carrying messages between a job's processes, as distinct from the management network.
hostfile
The list of hosts and slot counts mpirun places processes onto.
latency
Time for one small message to get there. Dominated by per-message overhead, not by the wire.
libfabric
The library sitting between MPI and the network, choosing a provider.
MPI
Message Passing Interface. How the processes of a parallel job communicate.
OS bypass
Writing to the network adapter directly, without the kernel. The reason the fast path is fast.
OSU micro-benchmarks
A standard set of MPI measurements. osu_latency, osu_bw, osu_allreduce and others.
provider
libfabric's word for a transport implementation — efa, tcp, shm and so on.
rank
One process of a parallel job, numbered from zero.
RDMA
Remote direct memory access — one machine reading or writing another's memory without involving its CPU.
transport fallback
MPI quietly using a slower path when the fast one is unavailable. Correct results, no error, much slower.
